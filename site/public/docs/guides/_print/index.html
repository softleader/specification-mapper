1 - Asynchronous Processing

非同步處理的實作模式

Configuring Async Thread Pool

在 Kapok 應用程式的啟動階段, Core 核心模組會啟動並進行 Async 相關的配置, 同時也整合了 Tracing 和 Security 等許多機制, 以確保整個非同步的過程可以順暢無誤的執行

因此, 在開發上核心概念是: 應盡可能的使用 Core 模組所提供的非同步配置, 避免自行建立及維護 Thread Pool

Asynchronous Processing

當你在實作非同步作業時, 以下提供了一些方式的參考:

Creating Async Methods

你可以設計使用 @Async 的 method, 例如:

@Service
public class MyService {

  @Async // 利用 Core 的非同步配置進行處理
  public CompletableFuture<String> getData() { // 建議返回 CompletableFuture, 以便使用者使用
    var results = myApi.getData();
    return CompletableFuture.completedFuture(results);
  }
}

這樣, 你可以像使用一般的 Spring Bean 那樣使用它, 例如:

@RestController
@RequiredArgsConstructor
public class MyController {

  private final MyService myService;

  @GetMapping("/data")
  public String getData() throws ExecutionException, InterruptedException {
    var future = myService.getData();
    // 操作 future 或忽略
    return future.get(); // 或 blocking thread 等待結果
  }
}

需要注意的是, 使用 @Async 的方法會透過 AOP 來進行非同步, 因此在使用這些方法時必須遵守 AOP 的規範

Publishing Async Events

設計並監聽 @Async Event, 例如:

public record MyEvent(long id) {} // 依序需求設計事件

@Service
public class MyService {

  @Async // 非同步執行
  @EventListener // 宣告這是一個事件監聽器
  public void onMyEvent(MyEvent event) {
    // handle async
  }
}

在應用程式的任何地方, 你可以在需要時發送事件, 例如:

@RestController
@RequiredArgsConstructor
public class MyController {

  private final ApplicationEventPublisher publisher;

  @GetMapping("/just-do-it")
  public void doIt() {
    publisher.publishEvent(new MyEvent(...)); // 發送事件
  }
}

使用 Spring 事件有許多好處, 如方便擴充, 增加靈活性和減少程式碼耦合等, 但需注意此模式無法取得回傳值, 同樣, @Async 和 @EventListener 都依賴於 AOP, 所以使用時也需遵守 AOP 的規範

Submitting Async Futures

如果你需要直接操作 Thread Pool, 例如你不能修改目標方法, 你可以在程式中注入 AsyncTaskExecutor 並使用它的 API 去呼叫目標方法, 例如:

@RestController
@RequiredArgsConstructor
public class MyController {

  private final AsyncTaskExecutor executor;
  private final MyService myService;

  @GetMapping("/just-do-it")
  public void doIt() {
    var future = executor.submitCompletable(() -> myService.myMehtod(...));
    // 操作 future, 或不理會
  }
}

2 - Building Extensions

如何建立 Kapok 擴充模組

本章節將說明建立擴充模組的步驟及注意事項, 開始開發前, 請先閱讀並遵守以下原則:

  • 可關閉性 (Disableable): 擴充模組中的邏輯或配置必須能夠被關閉, 當使用者不需要該模組時, 應能輕鬆地停用其配置和邏輯
  • 可配置性 (Configurable): 擴充模組中的邏輯或配置應盡量做到靈活且可替換, 當使用者需要客製化時, 能透過簡單的方式插入自己的實現, 例如註冊自訂的 Bean

Create the Extension

首先, 為擴充模組選擇適合的 artifactId, 建議使用少量單字 (1~2 個單字), 格式上使用小寫並避免空格, 若包含多個單字, 應以 - 連接，例如: hello-world

接下來, 進入 Start Kapok 頁面, 在 Project 選單中選擇 Maven - Extension, 產生並下載專案

Important

建議避免擴充模組之間的相互引用, 若建立時在 Dependencies 中選擇了其他擴充模組, 請務必仔細考量必要性

完成以上步驟後, 即可成功建立一個空白的擴充模組, 並開始進行開發, 接下來將列出相關的程式碼注意事項及規範, Happy Hacking!

Package

Package 的最後一層應以 {artifactId} 為名, 以便使用者識別, 例如:

tw.com.softleader.kapok.hello_world

若 {artifactId} 包含多個單字, 請避免使用駝峰命名, 建議以底線 _ 或 . 隔開, 或直接移除 - 當作是單一單字處理, 如:

  • tw.com.softleader.kapok.hello_world (可)
  • tw.com.softleader.kapok.helloworld (可)
  • tw.com.softleader.kapok.hello.world (可, 但意義稍有不同)
  • tw.com.softleader.kapok.helloWorld (不建議)

在 ...{artifactId} 下, 應包含了幾個主要目錄層級, 如下所示:

tw
└── com
    └── softleader
        └── kapok
            └── hello_world        # 這邊是擴充模組的 root package
                ├── aot            # 這邊放配置 aot 的內容
                ├── autoconfigure  # 這邊放配置的內容, 如 properties, configs 等
                │   ├── HelloWorldProperties.java
                │   └── HelloWorldAutoConfiguration.java
                ├── another        # 這邊開始往下, 就都是擴充模組自己的 sub packages
                │   └── Another.java
                └── others
                    └── Others.java

Auto Configuration

Extensions 的自動配置是很重要的環節, 請遵守以下原則來進行設定, 此外, 開始前建議參考 Creating Auto-configuration 來獲取更多細節

Properties

在 ...{artifactId}.autoconfigure 下, 會放置自動配置所需的 Properties, 用於收集使用者的配置, 以便於 Runtime 時進行判斷

Properties 的命名應為 {Xxx}Properties, 並遵守以下原則:

  • 需精確描述配置內容, 如: MicrometerAutoConfiguration
  • 不應包含 Kapok 相關的前綴或後綴
  • 避免模糊字眼, 如: SpecialAutoConfiguration
  • 唯唯一可接受的模糊字眼為 {artifactId}AutoConfiguration, 如: HelloWorldAutoConfiguration

在 Properties 中應設置 prefix 路徑, 建議包含 {artifactId}, 例如: kapok.hello-world, 範例如下:

@Data
@ConfigurationProperties(prefix = "kapok.hello-world")
public class HelloWorldProperties {
  
  /** 是否啟用 Hello World */
  private boolean enabled = true;
}

Tip

Properties 中欄位的 javadoc 會自動產生成 IDE 提示, 因此請充分撰寫說明

Config Candidates

在 ...{artifactId}.autoconfigure 下放置自動配置的候選邏輯, 程式命名應為 {Xxx}AutoConfiguration, 並參考 Properties 中的原則說明

在該 class 中, 應設計模組總開關: ...{artifactId}.enabled, 例如: kapok.hello-world.enabled

此外, 為避免擴充模組功能被任意啟用, 此 class 應加上 @ConditionalOnKapokApplication 以限制僅在啟動 Kapok Application 時進行配置, 完整範例如下:

@AutoConfiguration 
@ConditionalOnKapokApplication
@ConditionalOnProperty(prefix = "kapok.hello-world", name = "enabled", matchIfMissing = true)
@EnableConfigurationProperties(HelloWorldProperties.class)
public class HelloWorldAutoConfiguration {
}

Extending Configuration

Kapok Core 模組允許擴充模組啟動時改變 Spring 或其他第三方 Library 的預設配置, 請依以下步驟進行設定

Default Configuration

Runtime 的預設配置應放在 src/main/resources/META-INF/kapok/application-default.properties 中, Kapok 在啟動時會自動的讀取, 在該檔案中, 直接放入你希望的配置, 例如:

spring.application.name=Hello World!

完成後, 使用該擴充模組的 App 就會以上述設定作為預設配置啟動, 當然 App 都還是可以覆蓋掉的!

建議擴充模組額外提供 Log Group 的預設配置, 以方便使用者設定, 格式為 logging.group.{artifactId}={package}, 例如:

# src/main/resources/META-INF/kapok/application-default.properties
logging.group.hello-world=tw.com.softleader.kapok.hello_world

Test Configuration

測試時的預設配置應放在 src/main/resources/META-INF/kapok/application-test.properties 中, Kapok 在啟動時會自動的讀取, 在該檔案中, 直接放入你希望的配置, 例如:

spring.application.name=Hello Test!

Note

注意, 是 src/main/ 下!

完成後, 使用該擴充模組的測試就會以上述設定作為預設配置啟動, 當然每個測試 class 都還是可以覆蓋掉的!

SafeMode Configuration

SafeMode 的預設配置應放在 src/main/resources/META-INF/kapok/application-safemode.properties 中, Kapok 在啟動時會自動的讀取, 在該檔案中, 直接放入你希望的配置, 例如:

spring.application.name=Hello SafeMode!

Note

注意, 是 src/main/ 下!

完成後, 使用該擴充模組的 SafeMode 就會以上述設定作為預設配置啟動!

Application Customizer

Kapok 在 App 啟動時, 有提供一個 callback 擴充點來客製化配置底層的 Spring, 一般來說不太容易遇到, 但如果你的擴充模組需要用到, 則:

  1. 實作 tw.com.softleader.kapok.core.Customizer<SpringApplication>, 且須提供一個無參數的建構值
  2. 在該擴充模組的 src/main/resources/META-INF/kapok/ 下建立 application.customizers 檔案
  3. 在這檔案中, 放入你實作的 class 全名 (包含 package), 若有多個則換行撰寫

完整範例如下:

class MyApplicationCustomizer implements Customizer<SpringApplication> {

  @Override
  public void customize(SpringApplication application) {
    // 加上我的客製化
  }
}

在 src/main/resources/META-INF/kapok/application.customizers 中:

tw.com.softleader.kapok.hello_world.MyApplicationCustomizer
tw.com.softleader.kapok.hello_world.OtherApplicationCustomizer

完成以上設定後, 任何使用這個擴充模組的 App 在啟動階段就會自動的套用所撰寫的客製化邏輯, 一個簡單的使用場景範例可參考: ApplicationBanner

Application Customizer Ordering

Kapok 在載入所有模組的 application.customizers 之後, 預設是不保證順序的執行, 若你有需要控制順序, 建議重新檢視一下擴充邏輯, 應該儘可能的避免, 因為這是在 Runtime 載入模組的設定後才排序的, 而我們又無法預期使用端會挑選使用了哪些模組, 順序的控制上相對困難

若還是真的有控制順序需求, 請改成實作 tw.com.softleader.kapok.core.OrderedCustomizer, 如:

class MyApplicationCustomizer implements OrderedCustomizer<SpringApplication> {
  ...
}

這時候你就可以複寫 getOrder() 方法來影響執行順序: 數字越小越優先, 範例如下:

class First implements OrderedCustomizer<SpringApplication> {

  ...

  @Override
  public int getOrder() {
    return 1;
  }
}

class Second implements OrderedCustomizer<SpringApplication> {

  ...

  @Override
  public int getOrder() {
    return 2;
  }
}

這樣在執行時的結果會是:

  • First 會優先於 Second
  • First, Second 都會優先於其他沒有預設排序的 Customizer<SpringApplication>

3 - Calculating Java Memory in Container

在容器中計算 Java 應用程式的最佳記憶體配置

控制 Java 應用程式的記憶體配置時, 例如 Heap, 我們經常會用到 -Xmx, -XX:MaxRAMPercentage 等參數, 然而, 這些參數若固定的配置不一定會適合所有環境, 舉例來說, 若設定了記憶體上限 -XX:MaxRAMPercentage=70, 並將其部署在不同記憶體配置的容器中:

  • 在 2GB 的容器中, 70% 的記憶體配置相當於 1.4GB, 這樣容器中剩餘的可用記憶體為 0.6GB
  • 在 4GB 的容器中, 70% 的配置則為 2.8GB, 剩餘的可用記憶體增加到了 1.2GB

由此可見, 在擁有更高記憶體上限的環境中, 應用程式未使用的記憶體 (也許造成浪費) 會更多; 相對的, 在記憶體較少的環境中, 反而有可能遇到容器本身 (非應用程式) 的記憶體不足, 因此, 面對不同環境, 我們通常需要進行針對性的調整, 以確保應用程式在各種環境下都能適當運行

為了避免這些煩惱, 公司推出了 memory-calculator, 並整合了 Jib 容器建置工具, 它可以根據啟動時當下的狀況, 例如容器所被分配的記憶體上限, 應用程式的 class 數量等, 計算出建議的最佳化記憶體配置

本章節會 Step by Step 的介紹如何整合 memory-calculator, 適用於較舊的 Kapok 升級上來的 Project 跟著配置, 若你是從最新的 Start Kapok 所建構的 Kapok Project, 預設已經包含了此章節的所有設定, 你可以當作成理解這些配置的細節即可

Prerequisite

開始前, 請先確認專案有滿足最低需求:

  • 使用 Java 17 或以上版本
  • Jib 使用的是公司提供的 Base Image, 檢查前綴應為: harbor.softleader.com.tw/library/

這些設定可以在 pom.xml 中的 properties 區塊中找到, 一般來說會在專案根目錄中的 pom.xml 中可以找到, 例如:

<properties>
  <java.version>21</java.version>
  <container-base-image>harbor.softleader.com.tw/library/...</container-base-image>
  ...
</properties>

Enable memory calculation

開啟 pom.xml, 在其中找到設定 Jib plugin 的區塊, 接著跟著設定:

  • 在 container 標籤中, 將 entrypoint 設定成 memory-calculator 提供的進入點
  • 加入 Jib JVM Flags extension
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apa.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  ...

  <build>
    <plugins>
      ...
        <plugin>
          <groupId>com.google.cloud.tools</groupId>
          <artifactId>jib-maven-plugin</artifactId>
          <version>${jib-maven-plugin.version}</version>
          <configuration>
            ...
            <container>
              <!-- 啟用計算最佳化記憶體配置-->
              <entrypoint>sh,/tmp/entrypoint.sh</entrypoint>
              ...
            </container>
            <!-- 設定 Jib JVM Flags extension 進入點-->
            <pluginExtensions>
              <pluginExtension>
                <implementation>tw.com.softleader.cloud.tools.jib.maven.JvmFlagsExtension</implementation>
              </pluginExtension>
            </pluginExtensions>
          </configuration>
          <!-- 加入 Jib JVM Flags extension dependency-->
          <dependencies>
            <dependency>
              <groupId>tw.com.softleader.cloud.tools</groupId>
              <artifactId>jib-jvm-flags-extension-maven</artifactId>
              <version>${jib-jvm-flags-extension-maven.version}</version>
            </dependency>
          </dependencies>
        </plugin>
    </plugins>
  </build>
</project>

以上就完成了設定

Disable memory calculation

若要在 Container 啟動時, 關閉自動計算建議記憶體配置的機制, 你可以添加系統參數 MEM_CALC_ENABLED=false, Kubernetes 的設定範例如下:

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: my-container
    image: my-image
    env:
    - name: MEM_CALC_ENABLED
      value: "false"

若要將 Image 完全恢復成 Jib 的預設行為來啟動, 只需移除 entrypoint 的設定, 無論是否有移除 Jib JVM Flags extension 都不會影響此操作, 要注意的是, 這樣包出來的 Image 就沒辦法再開啟最佳化記憶體配置了, 範例如下:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apa.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  ...

  <build>
    <plugins>
      ...
        <plugin>
          <groupId>com.google.cloud.tools</groupId>
          <artifactId>jib-maven-plugin</artifactId>
          <version>${jib-maven-plugin.version}</version>
          <configuration>
            ...
            <container>
         <!-- 移除 entrypoint 即可關閉最佳化記憶體配置, 恢復成 Jib 預設行為-->
         <!-- <entrypoint>sh,/tmp/entrypoint.sh</entrypoint>-->
              ...
            </container>
            ...
          </configuration>
          ...
        </plugin>
    </plugins>
  </build>
</project>

Use Cases

以下提供一些使用範例

Configure JVM environment

計算出來的最佳化記憶體配置會使用 JAVA_TOOL_OPTIONS 參數來配置 JVM, 使用者可以透過事先設定好的環境變數 JAVA_TOOL_OPTIONS 來增加更多的參數

例如, 我想覆寫 XX:MaxMetaspaceSize=128M, 並多設定 -XX:MinHeapFreeRatio=20 -XX:MaxHeapFreeRatio=40, 其他參數使用計算出來的建議值, 範例如下：

<configuration>
  ...
  <container>
    ...
    <environment>
      <JAVA_TOOL_OPTIONS>-XX:MaxMetaspaceSize=128M -XX:MinHeapFreeRatio=20 -XX:MaxHeapFreeRatio=40</JAVA_TOOL_OPTIONS>
    </environment>
  </container>
</configuration>

啟動 App 後可以看到訊息類似於:

Setting Active Processor Count to 5
Calculating JVM memory based on 7384388K available memory
For more information on this calculation, see https://paketo.io/docs/reference/java-reference/#memory-calculator
Calculated JVM Memory Configuration: -XX:MaxDirectMemorySize=10M -Xmx6792516K -XX:ReservedCodeCacheSize=240M -Xss1M (Total Memory: 7384388K, Thread Count: 200, Loaded Class Count: 9469, Headroom: 0%)
Picked up JAVA_TOOL_OPTIONS: -XX:MaxMetaspaceSize=128M -XX:MinHeapFreeRatio=20 -XX:MaxHeapFreeRatio=40 -XX:ActiveProcessorCount=5 -XX:MaxDirectMemorySize=10M -Xmx6792516K -XX:ReservedCodeCacheSize=240M -Xss1M

Tip

若使用者設定的參數與最佳化記憶體配置中的參數相同, 則會優先採用使用者的設定

Configure calculation variables

在計算的過程中會用到許多參數, 這些參數都會有預設值或是動態決定的邏輯, 幾個比較有機會調整的參數如下:

  • BPL_JVM_HEAD_ROOM
  • BPL_JVM_THREAD_COUNT
  • BPL_JVM_CLASS_ADJUSTMENT

要覆寫這些計算參數的值, 可以透過 environment 來傳入, 例如我想要將Thread Count 調整為 50, 範例如下:

<configuration>
  ...
  <container>
    ...
    <environment>
      <BPL_JVM_THREAD_COUNT>50</BPL_JVM_THREAD_COUNT>
    </environment>
  </container>
</configuration>

啟動 App 後可以看到訊息類似於:

For more information on this calculation, see https://paketo.io/docs/reference/java-reference/#memory-calculator

Passing JVM flags

在啟動時, 可以透過 jvmFlags 來傳入參數給 JVM , 例如, 我要傳入 -server 及 -Dmy.property=example.value, 範例如下:

<configuration>
  ...
  <container>
    ...
    <jvmFlags>
      <jvmFlag>-server</jvmFlag>
      <jvmFlag>-Dmy.property=example.value</jvmFlag>
    </jvmFlags>
  </container>
</configuration>

啟動的語法會為類似於:

java -server -Dmy.property=example.value -cp @/app/jib-classpath-file mypackage.MyApp

4 - Customizing Error for HTTP APIs

使用 Kapok 提供的 SPI 快速客製化 HTTP 錯誤結構

Kapok 在設計 HTTP APIs 的錯誤結構時, 遵循了 RFC 7807 - Problem Details for HTTP APIs 的規範, 在錯誤發生時, 提供一致性的伺服器端回應和呼叫端解析方法, 包含以下幾個核心原則, 但不限於這些:

  • 使用 Response Status Codes 來描述 API 呼叫的結果
  • 成功的情況下, API 回應規格由 API 自身定義, 包含 Media Types, Headers, Body 等 HTTP Protocol 中的規範
  • 失敗的情況下, 錯誤規格由 Kapok 統一定義, 並且符合 RFC 7807 規範

然而, 考慮到需求的多樣性, Kapok 支援了多種客製化的方式, 以下介紹兩個客製化範例:

  1. 不論是成功或失敗的回應, 所有的 Response Status Code 都只使用 2xx
  2. 在錯誤回應的 Body 中增加額外的欄位, 例如: time (錯誤發生的時間)

Customizing Response for APIs Provider

Kapok 將 API 提供方（即 Server 端）的錯誤訊息處理過程, 封裝在全域錯的誤處理器 (GlobalControllerExceptionHandler) 之中, 並且也提供了許多 Template Methods 來讓專案實作不同的客製化處理策略, 大致上包含了以下幾個方法:

  • wrapError - 將攔截到的 Exception 等資訊, 封裝成 Kapok 定義的錯誤格式 APIError
  • publishError - 負責發佈已攔截的 Exception 事件
  • logError - 進行 Exception 的記錄
  • postHandle - 處理 APIError 最後的攔截點, 透過此方法可以對其進一步的調整
  • wrapProblemDetail - 將 APIError 轉換成 ProblemDetail, 這是一個用來描述符合 RFC 7807 標準的物件, 該方法會在寫入 Response 之前被呼叫

在此範例中, 我們的目標是加上客製化錯誤訊息的內容, 這適合透過覆寫 postHandle 方法來完成, 完成後, 再註冊為 Spring Bean 即可, 程式範例如下:

@Component
class MyGlobalControllerExceptionHandler extends GlobalControllerExceptionHandler {

  public MyGlobalControllerExceptionHandler(
      @NonNull ServerProperties serverProperties,
      @NonNull WebProperties webProperties,
      @NonNull APIErrorLogger apiErrorLogger,
      @NonNull SafeMessageSource messageSource,
      @NonNull ObjectProvider<APIErrorExceptionHandler> handlers,
      @NonNull ApplicationEventPublisher applicationEventPublisher) {
    super(
        serverProperties,
        webProperties,
        apiErrorLogger,
        messageSource,
        handlers,
        applicationEventPublisher);
  }

  @Override
  protected APIError postHandle(
      Exception exception, @NonNull WebRequest request, @NonNull APIError error) {
    // 將 Http Status 固定設定為 200
    error.setStatus(HttpStatus.OK);

    // 將底層的錯誤物件封裝成自定義的錯誤物件, 這樣就可以加入更多自定義的欄位
    // 當然若沒有增加欄位的需求, 這邊是不需要額外封裝的
    var myError = new MyAPIError(error);
    myError.setTime(LocalDateTime.now());
    return myError;
  }
}

@Setter // 提供給 Jackson 反序列化時使用
@NoArgsConstructor // 提供給 Jackson 反序列化時使用
class MyAPIError extends APIError {

  private LocalDateTime time; // 自定義的欄位

  public MyAPIError(@NonNull APIError other) {
    super(other);
  }

  @Override
  public ProblemDetail toProblemDetail() {
    var problem = super.toProblemDetail();

    // 在這裡, 透過設定 properties 提供更多資訊來描述錯誤
    problem.setProperty("time", time);
    return problem;
  }
}

Customizing FeignErrorDecoder

接下來, 我們將針對 API 呼叫方（即 Client 端）的 error decoder 進行調整, 以支援客製化的解析邏輯, 在 FeignErrorDecoder 中, 我們已經提供了許多 Template Methods 來實作不同的處理策略, 大致上包含了以下幾個方法:

  • readBody - 嘗試讀取 Response Body
  • deserializeError - 將 Response Body 反序列化成 Kapok 定義的錯誤格式 APIError
  • wrapException - 將 Response 和 APIError 等資訊封裝成一個將要拋出的例外物件

在此範例中, 我們的目標是要反序列化成自定義的 MyAPIError, 這適合透過覆寫 deserializeError 方法來完成, 完成實作後, 只需將其註冊為 Spring Bean 即可, 範例如下:

@Slf4j
@Component
class MyFeignErrorDecoder extends FeignErrorDecoder {

  @Override
  protected APIError deserializeError(String body) {
    try {
      // 嘗試將 Response Body 反序列化為自定義的錯誤類型
      return getObjectMapper().readValue(body, MyAPIError.class);
    } catch (JsonProcessingException e) {
      // 如果反序列化失敗, 則跳過處理
      log.error("Failed to deserialize response body to MyAPIError, skipping", e);
      return null;
    }
  }
}

5 - Customizing Security Filter Chain

透過 Kapok SPI 客製化安控流程, 或配置多重安控流程

在 Kapok 的安控模組中, 內建的安控核心流程是依據大部分公司的使用場景來設計的, 在此流程中, Kapok 還預留了許多可客製化的插入點, 我們可以根據不同的使用情境, 一定程度上的調整流程細節

  1. 如果請求符合 /admin/**, 則進入一個完全客製化的流程

    .securityMatcher("/admin/**") // 此組設定只適用於指定路徑

    ...
  ;

更多時候我們不需要全部重零開始配置, 例如, 我希望直接套用部分的核心流程的設定, 你可以從 Spring 注入 CoreHttpSecurity 來取得相關配置, 例如:

CoreHttpSecurity core = ...; // 從 Spring 注入
var configurer = core.configurer(); // 取得核心的配置

在 configurer 物件中, 不帶參數的方法用來取得特定項目的配置, 例如:

@Bean
@Order(CoreHttpSecurity.CORE_AUTH_ORDER - 10)
SecurityFilterChain adminSecurityFilterChain(HttpSecurity http, CoreHttpSecurity core) throws Exception {
  http
    .securityMatcher("/admin/**")
    .exceptionHandling(core.configurer().exceptionHandling()) // 套用核心的例外處理
    .anonymous(core.configurer().anonymous()) // 套用核心的匿名處理
    .authorizeHttpRequests(authorize -> authorize...) // 配置我的設定
    ...
  ;
  return http.build();
}

若如果你想要以整個核心流程作為基底, 再進行調整並自訂部分設定, 則可以使用帶參數的方法, 範例如下:

@Bean
@Order(CoreHttpSecurity.CORE_AUTH_ORDER - 10)
SecurityFilterChain adminSecurityFilterChain(HttpSecurity http, CoreHttpSecurity core) throws Exception {
  http.securityMatcher("/admin/**");
  core.configurer() // 取得核心的配置
      .authorizeHttpRequests(authorize -> authorize...) // 客製化我的設定
      ...
      .configure(http); // 套用到 http 中
  return http.build();
}

configurer() 每次回傳的都是一個新的物件, 這可以讓你控制哪些設定不互相影響

Bearer Configurer

在我們目前的 API 設計中, Bearer Authentication 是主要的認證方式, 如果你需要使用 Bearer Token 但有自定義 Token 解析邏輯的需求, 除了完全的自行控制外, 也可以參考 Kapok 提供的 BearerAuthenticationFilter

BearerAuthenticationFilter 負責從請求中擷取出 Bearer Token, 並將其提交給 PreAuthenticatedUserDetailsService, 這是 Kapok 擴展的認證流程的開始, 你可以在此基礎上進行調整和客製化, 以降低完全客製化配置的複雜度

透過使用 CoreHttpSecurity, 你可以快速的對這個流程進行配置, 例如:

@Bean
@Order(CoreHttpSecurity.CORE_AUTH_ORDER - 10)
SecurityFilterChain adminSecurityFilterChain(HttpSecurity http, CoreHttpSecurity core) throws Exception {
  http.securityMatcher("/admin/**");
  core.configurer() // 取得核心的配置
    .bearer( // 調整 Bearer
        bearer ->
            bearer.preAuthenticatedUserDetailsService(
                uds -> uds.tokenIntrospection(myTokenIntrospection()))) // 使用客製化的 TokenIntrospection
    .authorizeHttpRequests(authorize -> authorize.anyRequest().authenticated())
    .configure(http);
  return http.build();
}

Kapok 在整合 Docker Compose 時, 期望每次啟動都能有一致且乾淨的環境, 因此與 Spring Boot 的預設配置稍有不同, 調整後的配置如下:

spring.docker.compose.start.skip=never
spring.docker.compose.stop.command=down

如果你希望還原成 Spring Boot 的預設配置, 請設定:

# application.yml
spring:
  docker:
    compose:
      start:
        skip: if_running
      stop:
        command: stop

7 - Inherit Maven Config

將 Maven 專案繼承 Kapok 的設定管理

在 Maven Project 中, <parent> 和 <dependencyManagement> 都是常見的依賴管理配置方式, 但它們的使用有所不同, 以下是兩者的差異:

Using Parent

透過 <parent> 繼承配置, 可以包含 <dependencies>, <plugins>, <properties> 和 <build> 等區塊的內容, 這種方式可以減少重複的配置, 並便於統一管理不同專案的 Maven 配置架構

例如, 在建立 Spring 專案時, 經常使用以下配置:

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.3.3</version>
  <relativePath/> <!-- lookup parent from repository -->
</parent>

Using dependencyManagement

<dependencyManagement> 更專注於依賴套件的集中管理, 例如套件的版本號 (Version) 和範圍 (Scope) , 與直接引入 <parent> 不同, <dependencyManagement> 不會自動引入依賴套件, 而是提供依賴版本和範圍的控制, 這種方法不會直接影響 <dependencies>, <plugins>, <properties> 或 <build> 區塊的配置, 從而保留了更大的自主空間和彈性

例如, 建立 Quarkus 專案時, 通常使用以下配置:

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>${quarkus.platform.group-id}</groupId>
      <artifactId>${quarkus.platform.artifact-id}</artifactId>
      <version>${quarkus.platform.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

Kapok’s Choice

考慮到 Maven 的 <parent> 只支援單一繼承的特性, 以及專案多樣性的需求, 我們在 Start Kapok 中所提供的程式碼模板使用了 <dependencyManagement> 配置, 這樣可以為專案提供最靈活的依賴管理和版本控制

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>tw.com.softleader.kapok</groupId>
      <artifactId>kapok-bom</artifactId>
      <version>${kapok.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

雖然這種方式在 <plugins>, <properties> 或 <build> 等部分可能需要更多的配置, 但這些設定調整的頻率相對較低, 因此, 我們在 Start Kapok 中提供了更完整的配置方案, 以供專案參考

此外, 使用 Kapok 的專案還可以根據具體需求, 決定是否建立和維護專屬的 Parent POM, 以做最完整的客製化配置, 這樣可以針對特定的專案需求進行深度定制, 確保配置和管理更符合實際業務的需求

Liquibase 的使用指南

8.1 - Generate Changelog

透過 Maven Plugin 產生 Liquibase ChangeLog, 並套用到目標資料庫

Liquibase 官方提供了一個方便的 Maven Plugin, 它可以輕鬆的整合到開發環境或 CI/CD Workflow 中, 本節將介紹如何使用此 Plugin 來快速的產生 ChangeLog

此外, 如果你的開發環境是 IntelliJ IDEA, 我們還推薦使用 JPA Buddy Plugin, 它同樣可以快速地從程式碼中產生 ChangeLog

Liquibase Maven Plugin設定

Step1. 加入Liquibase依賴於Maven Plugin當中

根據需要的版本修改<version>以及指定Liquibase啟動時的參數檔案路徑於<propertyFile>，這邊我們使用resources路徑做測試。

<build>
  <plugins>
    <plugin>
      <groupId>org.liquibase</groupId>
      <artifactId>liquibase-maven-plugin</artifactId>
      <version>4.26.0</version>
      <configuration>
        <propertyFile>src/main/resources/liquibase.properties</propertyFile>
      </configuration>
    </plugin>
  </plugins>
</build>

Step2. 設定Liquibase參數於liquibase.properties

要使用Liquibase產生diff changelog的參數設定主要有三類，分別是參考資料庫連線，目標資料庫連線以及diffChangelog檔案路徑。

#參考資料庫(產生更新的ChangeLog)
referenceDriver=org.h2.Driver
referenceUrl=jdbc:h2:tcp://localhost:9090/mem:kapok
referenceUsername=sa
referencePassword=
#目標資料庫(要套用ChangeLog的資料庫)
driver=com.mysql.cj.jdbc.Driver
url=jdbc:mysql://localhost:3306/mydatabase
username=myuser
password=mypassword
changeLogFile=src/main/resources/db/changelog/db.changelog-master.yaml
diffChangeLogFile=src/main/resources/db/changelog/db.changelog-diff.yaml

  1. 目標資料庫設定：Data Migration的資料庫，需要資料庫的driver, URL, username 以及 password。

  2. 參考資料庫設定：產生diffChangeLog的資料庫，需要資料庫的driver, URL, username 以及 password。 note:這邊參考資料庫使用 embedded h2 資料庫時，要開啟tcp mode，可參考教學。

  3. Changelog設定：

    1. changeLogFile: Liquibase update 等指令執行時檢查的ChangeLog檔案位置。Note：雖然liquibase:diff不會用到changeLogFile設定，但這是啟動時必備的。

    2. diffChangeLogFile: Liquibase diff指令執行後產生的Diff Log檔案位置。

Step3. 執行mvn Liquibase:diff指令

開啟Terminal執行 mvn liquibase:diff ，執行成功後於 diffChangeLogFile 位置產生資料庫比對後的changelog檔案。

Step4. 將比對後的diffChangeLogFile加入changeLogFile

更新ChangeLogFile：將產生的DiffChangeLog加入ChangeLog當中，可參考如下：

#db.changelog-master.yaml
databaseChangeLog:
  - include:
      # liquibase:diff 產生的 changelog
      file: db/changelog/db.changelog-create-employee.yaml

Step5. 執行Liquibase Update

最後一步我們執行 mvn liquibase:update 即可將改動加入目標資料庫完成Data Migration。當參考資料庫與目標資料庫版本不同時，請務必先在測試環境執行一次，以確保Data Migration如預期結果。要確定changelog語法是否支援對應的資料庫，可於Liquibase文件-Change Types查詢。

8.2 - Generate Changelog By JPA Buddy

透過 JPA Buddy 產生 Liquibase ChangeLog, 並套用到目標資料庫

JPA Buddy 是一個 IntelliJ IDEA 的插件，它可以根據程式中撰寫的 JPA Entity 來產生 Liquibase 的 ChangeLog 檔案

Install JPA Buddy

首先需要安裝JPA Buddy插件，安裝方式如下：

  1. 打開IntelliJ IDEA，點擊File -> Settings -> Plugins。
  2. 在Marketplace中搜索JPA Buddy，點擊Install按鈕安裝插件。
  3. 安裝完成後重啟IntelliJ IDEA。
  4. 安裝完成後在View -> Tool Windows中可以看到JPA Explorer的選項。

Generate Init ChangeLog

產生第一份ChangeLog檔案

首先我們需要生成第一份ChangeLog檔案，該檔案是Spring-Liquibase主要參考的ChangeLog Root檔案，用於管理所有的ChangeSet。生成ChangeLog檔案的步驟如下：

  1. 打開JPA Explorer視窗。
  2. 點選+號(All New Action)後選擇Liquibase Empty Changelog。
  3. 資料夾選擇生成的ChangeLog檔案的存放位置，
    1. Source root: .../src/main/resources。
    2. Directory: db/changelog
    3. File name: db.changelog-master
    4. File type: yaml
  4. 點擊OK按鈕生成ChangeLog檔案。

生成Entity對應的ChangeLog檔案

生成Entity對應的ChangeLog檔案的步驟如下：

  1. 打開JPA Explorer視窗。
  2. 點選+號(All New Action)後選擇Liquibase Init ChangeLog。
  3. 選擇DB Type
  4. Init Schema Changelog: Source type 選擇 Model，因為要使用Entity生成ChangeLog檔案。
  5. Changelog Preview:
    1. dbChangelog: 選擇第一步生成的ChangeLog檔案。
      1. Save as: 生成ChangeLog檔案類型, 選擇File。
      2. Directory: ChangeLog檔案位置。
      3. File name: ChangeLog檔案名稱。
    2. changeSet:
      1. 可以選擇要生成ChangeLog檔案的Entity，可以修改ID, Author, Context, Labels。
      2. 可以整併多個Entity生成一個ChangeSet。
  6. 點擊Save按鈕生成ChangeLog檔案。
  7. 將生成的ChangeLog檔案加入到db.changelog-master檔案中。 
    databaseChangeLog:
- include: 
    id: baseline
    author: Nick
    context: baseline 
    file: db/changelog/changelog-baseline.yaml

執行APP後，Liquibase會根據db.changelog-master檔案中的ChangeSet來執行資料庫的變更。確認變更後記錄結果至DatabaseChangeLogTable中。

Generate Diff ChangeLog

當Entity有變更與資料庫狀態不同時，需要生成Diff ChangeLog檔案，該檔案是用於管理Entity的變更。生成Diff ChangeLog檔案的步驟如下：

生成Entity對應的Diff ChangeLog檔案

生成Entity對應的Diff ChangeLog檔案的步驟如下：

  1. 打開JPA Explorer視窗。
  2. 點選+號(All New Action)後選擇Liquibase Diff ChangeLog。
  3. Diff Database Changelog
    1. Source type 選擇 Model，因為要使用Entity生成ChangeLog檔案。
    2. Target(URL) 選擇 DB ，選取DB Connection對應的URL。
  4. Changelog Preview:
    1. dbChangelog: 選擇Diff生成的ChangeLog檔案。
      1. Save as: 生成ChangeLog檔案類型, 選擇File。
      2. Directory: ChangeLog檔案位置。
      3. File name: ChangeLog檔案名稱。
    2. changeSet:
      1. 可以選擇要生成ChangeLog檔案的Entity，可以修改ID, Author, Context, Labels。
      2. 可以整併多個Entity生成一個ChangeSet。
  5. 點擊Save按鈕生成ChangeLog檔案。
  6. 將生成的ChangeLog檔案加入到db.changelog-master檔案中。 
    databaseChangeLog:
- include: 
    id: baseline
    author: Nick
    context: baseline 
    file: db/changelog/changelog-baseline.yaml
- include: 
    id: diff
    author: Nick
    context: diff-v1
    file: db/changelog/changelog-diff-v1.yaml

執行APP後，Liquibase會根據db.changelog-master檔案中的ChangeSet來執行資料庫的變更。確認變更後記錄結果至DatabaseChangeLogTable中。

註記： 當需要Liquibase Pro的功能時會有無法顯示的錯誤，這時需要自行手動產生Changelog，例如Constraints-addCheckConstraint

結論

Jpa Buddy是使用Liquibase時的一個很好的輔助工具，可以根據Entity生成ChangeLog檔案，並且可以根據Entity生成Diff ChangeLog檔案。這樣可以大大減少開發人員的工作量，提高開發效率。但是Jpa Buddy也有一些缺點，例如無法產生Liquibase Pro限定的功能，生成的ChangeLog檔案可能不夠靈活，需要開發人員手動修改。另外，Jpa Buddy只支持IntelliJ IDEA，不支持其他IDE。

9 - Makefile

Kapok 提供了常用指令的 Makefile

從 Start Kapok 建立的 Kapok Project 在根目錄都會附帶一個 Makefile 的檔案, 其中收錄了常用的指令, 這樣做的好處不僅可以簡化複雜的指令, 還可以確保在不同環境中執行時可以維持一致的結果

舉例來說, 不論是在本機開發環境還是在 CI/CD Pipeline 中執行, 都可以使用 Makefile 中的相同指令, 來確保執行結果的一致性, 這種集中的方式也可以讓維護更加方便, 因為所有指令都位於同一個地方

我們使用 make 工具來執行 Makefile 中的指令, 在 Linux 或 Mac 系統中通常都內含了這工具, 因此你可以直接使用; 但在 Windows 系統中, 需要先安裝 GNU make 才能使用

當然, 你也可以用任一文字編輯器來開啟 Makefile 檔案, 查看並直接執行其中的原生指令

Getting Started

在 Makefile 檔案中, 是使用 target 去封裝一至多組原生指令, 語法類似於:

target: 
<tab>原生指令

決定好 target 後, 透過以下指令來執行:

make <target>

例如, 我要執行 target run:

make run

若你有需要新增或調整 target, 請注意以下事項：

  • 在原生指令之前, 必須使用一個 <tab> (/t), 不能是 2 或 4 個 <space> (/s)
  • 原生指令可能會涉及不同的作業系統 (OS), 請盡量使用能跨作業系統的指令, 如 mvn 等
  • 若原生指令無法跨作業系統, 由於 CI/CD Pipeline 中是使用 Linux 作業系統, 請優先考慮使用 Linux 指令

10 - Multi Module Project

將 Single Module 的 Kapok 架構轉換為 Multi Module 架構

從 Start Kapok 建構的 maven project, 預設是 single-module 架構, 因為這配置夠簡潔易懂, 非常適合作為 Getting Started 的預設架構.

然而在公司專案有時候會需要使用 multi-module, 這章節就會 Step by Step 的說明如何將一個 single-module with Kapok 轉換成 multi-module 架構

本章節會 Step by Step 的介紹, 適用於已經建立好的 Project, 若你正要到 Start Kapok 上建立專案, 可以在 Project 的選單中選擇 Maven - Multi Module, 下載後預設就已經包含了此章節的所有設定, 你可以當作成理解這些配置的細節即可

Before You Start

在開始前, 若你還沒建立專案, 請先到 Start Kapok 下載一個 Kapok Project, 本篇是沒有加入任何一個 dependencies 直接下載作為範例

本範例會以一個乾淨的 Kapok Project 作為 Parent Module, 並且在其中建立 2 個 modules:

  • API Module - 類似 libraries 套件, 需要包成 jar release 出去
  • App Module - 進入點 module, main class 會在這邊, 會打包成 Image

11.1 - Generate OpenAPI

產生完整版的 OpenAPI Specification

這一章節將介紹如何透過 Maven 產生完整版的 OpenAPI Specification, 與輕量版相比, 完整版提供了更多一些資訊, 但在執行速度和資源需求方面相對消耗的較高

Before You Start

我們使用 Springdoc 在 Runtime 來掃描註冊在 Spring 中的 @Controller, 以產生 OpenAPI description, 因此整個流程大概是: 先把應用程式啟動, 打一個 REST API 取得 OpenAPI description 並儲存檔案, 最後把應用程式關閉

然而, 當應用程式的程式碼變得越來越複雜且龐大時, 要確保應用程式仍能快速啟動, 並在啟動的過程中可以排除對外部服務的依賴 (例如資料庫或某個 API 呼叫等), 是一項相當具挑戰性的事

這是需要提前規劃, 並不斷持續維護的, 若控制的好, 完整版的效能或資源的消耗都一定可以很貼近輕量版, 但若想要更方便一點, 建議也可以參考使用輕量版

在產生的過程中, 需要應用程式提供一種配置, 要可以:

  • 在啟動的過程中沒有任何外部服務的依賴, 例如資料庫或某個 API 呼叫等 (必須)
  • 可以加速啟動的時間, 以及節省啟動的資源 (盡可能)

請在開始之前, 務必找到上述需求的配置方式

另外, 由於這一章節的所有配置僅適合特定流程, 建議在實作中將這些配置集中到一個 Maven Profile 中, 需要時再啟用即可

這一章的配置範例都將使用 Maven Profile generate-api 作為參考

Maven Structure

完整的設定方式會因為 Maven Structure 的配置差異而有所不同, single-module 較為單純, 配置都在一起不會有分別; 而 multi-module 所有的設定會在進入點 module

這邊開始以下我們都會以 Creating a Multi Module Project 中的內容作為範例:

.        # parent module
├── api  # api module
└── app  # app module -> 進入點 module, 在這邊設定

11.2 - Generate Lightweight OpenAPI

產生輕量版的 OpenAPI Specification

這一章節將介紹如何透過 Maven 產生輕量版的 OpenAPI Specification, 與完整版相比, 輕量版提供的資訊稍微少了一些, 但在執行速度和資源消耗方面相對具有優勢

Before You Start

我們使用 Springdoc 在 Runtime 來掃描註冊在 Spring 中的 @Controller, 以產生 OpenAPI description, 因此整個流程大概是: 先把應用程式啟動, 打一個 REST API 取得 OpenAPI description 並儲存檔案, 最後把應用程式關閉

然而, 當應用程式的程式碼變得越來越複雜且龐大時, 要確保應用程式仍能快速啟動, 並在啟動的過程中可以排除對外部服務的依賴 (例如資料庫或某個 API 呼叫等), 是一項相當具挑戰性, 需要提前規劃, 並不斷的持續維護一件事

輕量版的核心概念是, 我們不會啟動應用程式中的所有複雜配置, 而是啟動 SafeMode, 這是 Kapok 提供的一種啟動模式, 會儘可能使用最小化配置來啟動應用程式, 然後針對要給 Springdoc 產生 OpenAPI description 的那些 @Controller, Kapok 會使用動態代理來實作

這樣的做法可以加速啟動並降低資源消耗, 所以相對的也有一些注意事項及限制:

  • 程式碼會需配合稍作調整: 要在 Proxy 的目標上標記 @APIDoc, 作為識別的依據
  • 使用的是 JDK Proxy 機制, 因此 @APIDoc 只能掛在 Interface 上, 不支援 class 或 record, 且 Interface 必須是 public
  • 由於 Proxy 是基於 Interface, 因此標記在實作 class 上的註釋, 如 @PreAuthorize(...) 等, 就會遺失 (這也就是輕量版所稍微缺少的資訊)
  • SafeMode 啟動是不會載入任何的 application*.(yml|yaml|properties), 若你有特別的設定要配置, 請新增並配置在 safemode.(yml|yaml|properties) 檔案中

以上會結合 Kapok 提供的幾項功能來完成, 開始前請先閱讀過相關的說明文件：

  • SafeMode
  • @APIDoc

另外, 由於這一章節的所有配置僅適合特定流程, 建議在實作中將這些配置集中到一個 Maven Profile 中, 需要時再啟用即可

這一章的配置範例都將使用 Maven Profile generate-api 作為參考

Maven Structure

完整的設定方式會因為 Maven Structure 的配置差異而有所不同, single-module 較為單純, 配置都在一起不會有分別; 而 multi-module 就會依照 module 性質的不同在配置上有所區分, 相對較為複雜

這邊開始以下我們都會以 Creating a Multi Module Project 中的內容作為範例:

.        # parent module
├── api  # api module -> Library 類型的 module, 負責產生 Jandex index
└── app  # app module -> 進入點 module, 負責產生 OpenAPI description

Api Module

App Module 負責產生 Jandex index, Jandex 是一套在 compile 時期處理的工具, 會依照設定產生 classes 清單跟詳細的資訊, 這樣可以避免在 Runtime 才去掃描造成效能的浪費, 編輯 api/pom.xml 加上:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  ...

  <profiles>
    <profile>
      <id>generate-api</id>
      <build>
        <plugins>
          <plugin>
            <groupId>io.smallrye</groupId>
            <artifactId>jandex-maven-plugin</artifactId>
            <version>3.1.3</version> <!-- 記得查看最新的版號 -->
            <executions>
              <execution>
                <id>make-index</id>
                <goals>
                  <goal>jandex</goal>
                </goals>
              </execution>
            </executions>
          </plugin>
        </plugins>
      </build>
    </profile>
  </profiles>
</project>

接著確認這個 Module 中的所有 API interfaces:

  • 宣告的是 public
  • 都有加上了 @APIDoc, 這是一個標記讓 Kapok 來識別 Proxy 的目標

程式碼範例如下:

@APIDoc // <- 確認都有加上標記以識別 Proxy 目標
@Tag(name = "Home")
public interface HelloApi { // <- 確認宣告的是 public

  @Operation(summary = "Hello", description = "Say Hi!")
  @ApiResponses(value = {
      @ApiResponse(responseCode = "200", description = "Success operation"),
  })
  @GetMapping("/hello")
  String hello(
      @Parameter(description = "Your name") @RequestParam("name") Optional<String> name);
}

12 - Packaging Container Image

將 Kapok 應用程式建構成 Container Image

這一章節將介紹如何透過 Maven 建制 Container Image, 以及如何在 Source Code, 構建的 Container Image, 和 Runtime 之間安全的管理版本關係

本章節會 Step by Step 的介紹, 適用於較舊的 Kapok 升級上來的 Project 跟著配置, 若你是從最新的 Start Kapok 所建構的 Kapok Project, 預設已經包含了此章節的所有設定, 你可以當作成理解這些配置的細節即可

Concept

整個設計的基礎, 建立在 Source Code 是維護在單一的 Git SCM 下, 如只維護在公司的 GitHub 中, 若你的 Source Code 需要在公司和客戶端的 SCM 上相互遷移, 可能無法達到預期的效果

在 Git 中, 每次 Commit 都會產生一個唯一的 ID, 這個 ID 具有不可變的特性, 通常被稱為 SHA 或 hash, 它可以用來識別至少包含了:

  • 具體的變更內容
  • 變更是何時進行的

核心概念是, 我們使用 Commit ID 在 Source Code, Container Image 和 Runtime 之間建立關聯:

  • 在打包時, 產生成當下的 Git 資訊檔案
  • 在 Build Image 時, 收錄 Git 資訊檔案到 Image 中, 也將 Git 資訊一併的添加到 Image Metadata 中
  • 通過 Kapok 的機制, 在 Runtime 提供多種檢視 Git 資訊的方式

Get Git Info

我們使用 git-commit-id-maven-plugin 來取得當前的 Git 資訊, 請編輯 pom.xml 加入以下的設置:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apa.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  ...

  <build>
    <plugins>
      ...
      <plugin>
        <groupId>io.github.git-commit-id</groupId>
        <artifactId>git-commit-id-maven-plugin</artifactId>
        <version>6.0.0</version> <!-- 記得查看最新的版號 -->
        <configuration>
          <generateGitPropertiesFile>true</generateGitPropertiesFile>
          <generateGitPropertiesFilename>${project.build.outputDirectory}/META-INF/git-info.properties</generateGitPropertiesFilename>
          <failOnNoGitDirectory>false</failOnNoGitDirectory>
          <validationProperties>
            <validationProperty>
              <injectAllReactorProjects>true</injectAllReactorProjects>
            </validationProperty>
          </validationProperties>
        </configuration>
        <executions>
          <execution>
            <id>get-the-git-infos</id>
            <phase>initialize</phase>
            <goals>
              <goal>revision</goal>
            </goals>
          </execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</project>

以下是一些重要設置的說明:

  • generateGitPropertiesFile - 設定需要產出檔案, 檔案會一起被收錄在 Image 中, 以便 Kapok 可以在 Runtime 時讀取並提供檢視
  • generateGitPropertiesFilename - 設定產出檔案的目錄及檔名, 這是 Kapok 所支援讀取的 Git Info 目錄及檔名, 不可更改
  • injectAllReactorProjects - 向 Maven 注入 Git 資訊, 以便後續的 plugin 可以參考使用, 目的是將資訊添加到 Image Metadata 中。

Build Image

我們使用 jib-maven-plugin 來打包 Image, 並將包版當下的 Project 及 Git 等資訊壓到 Image Metadata 的 labels 中, 請編輯 pom.xml 加入以下設置:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apa.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  ...

  <build>
    <plugins>
      ...
      <plugin>
        <groupId>com.google.cloud.tools</groupId>
        <artifactId>jib-maven-plugin</artifactId>
        <version>3.4.0</version> <!-- 記得查看最新的版號 -->
          ...
          <container>
            ...
            <labels> <!-- 這邊設定要壓哪些資訊到 Image Metadata 中 -->
              <tw.com.softleader.kapok.version>${kapok.version}</tw.com.softleader.kapok.version>
              <tw.com.softleader.image.group>${project.groupId}</tw.com.softleader.image.group>
              <tw.com.softleader.image.artifact>${project.artifactId}</tw.com.softleader.image.artifact>
              <tw.com.softleader.image.version>${project.version}/${git.commit.id}</tw.com.softleader.image.version>
            </labels>
          </container>
        </configuration>
      </plugin>
    </plugins>
  </build>
</project>

13 - Uploading Files

介紹檔案上傳的範例

本篇介紹了檔案上傳範例, 並且可以同時上傳檔案及傳入指定的物件格式

Creating a Controller

我們時常會設計 MultiPart API 來處理檔案上傳, 在 Spring MVC 中, 會使用 MediaType.MULTIPART_FORM_DATA_VALUE 及 @RequestPart

例如, 設計一個 API 用來建立客戶, 同時上傳頭像檔案 (avatar), 程式範例如下:

@PostMapping(value = "/customers/{id}/profile", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
String createProfile(
  @PathVariable("id") long id,
  @RequestPart(name = "profile") CreateProfile profile,
  @RequestPart(name = "avatar") MultipartFile avatar) {
  ...
}

CreateProfile 是用來接收參數的物件範例, 只是一個純 POJO, 例如:

@Data
@Builder
class CreateProfile {
  String name;
  int age;
  ...
}

OpenAPI Spec

在 OpenAPI 3.0 中, 也定義了 multipart requests 的標準, 在上述範例中, 我們必須讓 Client 端知道 CreateProfile 需要用 application/json 來處理

預期的 OpenAPI Spec 內容將會是:

requestBody:
  content: 
    multipart/form-data: # Media type
      schema:            # Request payload
        type: object
        properties:      # Request parts
          profile:       # Part1 (object)
            ...
          avatar:  # Part 2 (an image)
            type: string
            format: binary
      encoding: # The same level as schema
        profile: # Property name (see above)
          contentType: application/json

為了完整產生上述的 OpenAPI 規格, 在 Controller 必須增加更多 annotation 以達成上述定義:

@Operation(requestBody = @io.swagger.v3.oas.annotations.parameters.RequestBody(
  content = @Content(encoding = { // 這邊定義每個 Part 的 content-type
    @Encoding(name = "profile", contentType = MediaType.APPLICATION_JSON_VALUE)
  })))
@PostMapping(value = "/customers/{id}/profile", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
String createProfile(
  @PathVariable("id") long id,
  @RequestPart(name = "profile") CreateProfile profile,
  @RequestPart(name = "avatar") MultipartFile avatar) {
  ...
}

如果要支援上傳多個檔案, 將欄位開成 MultipartFile[] 即可, 例如:

String createProfile(
  @PathVariable("id") long id,
  @RequestPart(name = "profile") CreateProfile profile,
  @RequestPart(name = "avatar") MultipartFile[] avatars) {
  ...
}

File Upload Limits

在配置檔案上傳時, 設定檔案大小的限制非常重要, 這有助於防止處理過大的檔案而耗盡系統資源, 建議在配置檔案上傳限制時, 採取謹慎且保守的態度, 在 properties 中你可以依照以下方式進行設定:

spring:
  servlet:
    multipart:
      max-file-size: 2MB     # 單一檔案的大小上限, 預設 1MB
      max-request-size: 20MB # 總請求的大小上限, 預設 10MB
