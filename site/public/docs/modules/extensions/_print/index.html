1 - Bpm

Integration with JBPM.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-bpm</artifactId>
</dependency>

相容於 JBPM 標準, 提供簡單且易於使用的 JBPM API 串接方式

Getting Started

本模組是以 feign client 為主體呼叫 jBPM 的 Rest API, 在 pom.xml 中放入 BPM 依賴後, 透過 properties 設定 kapok.bpm.enabled 來啟動:

# application.yaml
kapok:
  bpm:
    # 啟動BPM模組, 預設是 false
    enabled: true
    # 設定主要路徑, 原則上只有 host 需要被變動
    kie-server:
      rest-url: http://192.168.1.242/kie-server/services/rest

Process Registration

在使用前要先註冊 process, 透過 properties 設定 kapok.bpm.processes 可以設定一或多組 process, 每一組 process 都是 Map 結構:

  • Key: 要註冊到 Spring 的 Bean Name, 不可重複, 也不可跟既有任何 Bean 名稱重複
  • Value: Process 資訊, 包含 containerId 及 processId

範例如下:

# application.yaml
kapok:
  bpm:
    processes:
      # 中括號是避免在命名上用到 Spring 的保留字需要跳脫而加的, 如果你確定沒有用到保留字則可不加
      "[qot-policy-audit-process]":
        containerId: kapok-gi_1.0.0-SNAPSHOT
        processId: kapok-gi.QotPolicyAudit
      "[some-other-process]":
        containerId: ...
        processId: ...

在程式中, 就可以 Autowired 名為 qot-policy-audit-process 的 ProcessApi 來操作 Bpm

@Service
@RequiredArgsConstructor
class MyService {

  @Qualifier("qot-policy-audit-process")
  final ProcessApi qotPolicyAuditProcessApi;
  
  ...
}

Start Process

啟動流程, 並得到 piid

var piid = qotPolicyAuditProcessApi.startProcess(Map.of(
  "callbackUrl", "http://b9d8-118-163-91-247.ngrok.io",
  "policy", Map.of("tw.com.kapok.QotPolicy", QotPolicyBpmRequest.builder() // 宣告QotPolicy在BPM的形別
  .id(policyId)
  .premiumYear(new BigDecimal("500000"))
  .amountTl(new BigDecimal("1500000"))
  .amountAd(null)
  .amountDd(null)
  .benefitRetentionRate(null)
  .build())
  ));

要點:

  1. 夾帶物件需要描述該物件於 jBPM 的 fullname, 如 tw.com.kapok.QotPolicy
  2. 承上, 若該 Data Object 有於 process 中 import, 則可以只描述 classname, 如 QotPolicy

Signal

qotPolicyAuditProcessApi.signal(piid, "GO", "");

要點:

  1. 需提供 piid 作為參數, piid 於 start process 時可獲得
  2. signalName 需與 process 圖上設定一致, 並且流程需走到已經在等待接收
  3. signalValue 目前約定僅能為純文字, 且不得為null, 最低限度都必須要帶空字串

Testing

在執行單元測試時, Bpm 模組預設是關閉的, 關閉的狀態下 Bpm 模組仍會建立一個空殼 ProcessApi 給 Spring, 因此程式上任何透過 Spring 注入了 ProcessApi 的地方都不會出錯!

有了上述機制, 你可以放心的測試那些沒有用到 ProcessApi 的程式碼, 但要注意的是, 空殼 ProcessApi 若真的被執行了就會拋出 UnsupportedOperationException, 畢竟 Bpm 都沒啟動怎麼能夠執行呢!

遇到這種情況, 首先務必先思考單元測試的情境是否過大? 是否變成 End to End 測試了, 造成涵蓋的程式碼涵蓋過大!?

Mocking BpmClient

如果測試的內容包含了使用 ProcessApi 的區段, 那我們需要針對該單元測試單獨的設定 kapok.bpm.enabled=true 將 Bpm 啟動.

Bpm 啟動過程中會要求提供 kie-server.rest-url, 但我們不希望單元測試需要依賴 Bpm 服務, 因此建議將 BpmClient mock 掉, BpmClient 是底層真正連接 Bpm 的實作, mock 掉以後請記得設定模擬的連線行為.

範例程式碼如下:

@SpringBootTest({
  "kapok.bpm.enabled=true"
})
class MyUnitTest {

  @MockBean
  BpmClient client;

  @Test
  void myTest() {
    var expectedPiid = ... // 預期 bpm server 會回覆的 piid
    when(client.startProcess(anyString(), anyString(), any(Map.class)))
      .thenReturn(expectedPiid);
      
    ...
  }
}

透過以上設定, 有用到 ProcessApi 區段的程式碼就會如期拿到 expectedPiid 進行原本的邏輯處理!

2 - Data JPA

ORM layer based on JPA.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-data-jpa</artifactId>
</dependency>

整合 JPA, 提供統一的標準介面, 以及資料庫操作的監控和歷程紀錄等擴充功能

Abstract Auditing Entity

Data JPA 擴充模組提供了一個個標準的 Entity 結構, 包含了以下系統欄位:

  • createdDate: 新增時間
  • createdBy: 新增人員
  • lastModifiedDate: 最後修改時間
  • lastModifiedBy: 最後修人員
  • versionNum: 資料儲存的版本

型態或對應的資料庫欄位等更詳細的資訊, 請直接參考 AbstractAuditingEntity

其中新增人員及最後修改人員也整合了 Security 擴充模組, 當前有登入資訊時就會自動的帶入, 若無登入則為空, 透過 properties 中的 kapok.data.jpa.auditing.auditor-if-not-authenticated 可以設定未登入時的人名

如在沒有登入情況下, 我希望資料庫中的資增人員及最後修改人員為 robot, 則設定如下:

# application.yml
kapok:
  data:
    jpa:
      auditing:
        auditor-if-not-authenticated: robot

程式在使用上, 除了將自己的 Entity 去繼承 AbstractAuditingEntity 外, 只需要再定義好 @Id 欄位即可使用, 範例程式碼如下:

@Data
@Entity
@Table(name = "MY_TABLE")
public class MyEntity extends AbstractAuditingEntity<String> {

  @Id @GeneratedValue Long id;
  
  // some other field...
}

Wrapper Models

在實際應用中, 我們通常不會直接在 API 中暴露 Entity, 而是先將它們轉換為 DTO 物件, 再輸出到 API 的回應中, DTO 中的欄位通常只針對該 API 定義的規範進行設計, 通常包含的欄位數量會少於或等於 Entity 中的欄位

假設我們的 Entity 定義如下:

@Data
@Entity
@Table(name = "MY_TABLE")
public class MyEntity extends AbstractAuditingEntity<String> {

  @Id @GeneratedValue Long id;
  String idno;
  String firstname;
  String lastname;
  String address;
  String phone;
}

如果 API 規範中要求的輸出格式如下:

{
  "firstname": "Matt",
  "lastname": "Ho"
}

那麼相應的 DTO 設計將會是:

@Data
public class MyDto {

  String firstname;  
  String lastname;
}

但有時候, 我們在 GET 相關的 API 中可能希望包含資料的唯一識別欄位, 如 id:

{
  "firstname": "Matt",
  "lastname": "Ho",
  "id": 1
}

在這種情況下, 可能需要定義另一個物件, 例如:

@Data
public class MyDtoWithId extends MyDto {
  Long id;  
}

針對這類需求, Data JPA 擴展模組提供了一些 Wrapper Models, 幫助你實作上述的情境, 而無需為此額外定義物件

Important

這類的 Wrapper Models 為了方便 JSON 序列化而設計, 而不是特別針對反序列化而規劃

若你的場景中需要做 JSON 的反序列化, 例如, 你是 API 的 Client 端需要從 JSON 轉回物件, 使用前請務必先評估並做完整的測試, 以確保反序列化結果符合預期, 例如: 後續會提到的欄位重複的處理邏輯

WithId

使用 WithId<T, ID> 物件時, 輸出 JSON 時會在原本的物件欄位外, 固定多帶一個 id 欄位, 範例如下:

// mapstruct mapper
@Mapper
interface MyEntityMapper {

  MyDto toDto(MyEntity entity);
  
  default WithId<MyDto, Long> toDtoWithId(MyEntity entity) {
    return new WithId<>(toDto(entity), entity.getId());
  }
}

// API
@RestController
record MyController(MyRepository repository, MyEntityMapper mapper) {

  @GetMapping("/my-resources")
  List<WithId<MyDto, Long>> getAllWithId() {
    return repository.findAll().stream().map(mapper::toDtoWithId).toList();
  }
}

輸出將會是:

[
  {
    "firstname": "Matt",
    "lastname": "Ho",
    "id": 1
  }
]

如果欄位重複, 例如: MyDto 中也包含 id 欄位, 則:

  • 序列化時: 會忽略 MyDto.id, 以傳入的 id 為主
  • 反序列化時: MyDto.id 及傳入的 id 都會有一樣的值

WithMeta

使用 WithMeta<T, M> 物件時, 可以定義一個額外的類型 (以下稱 Meta) , 在輸出 JSON 時, 會在原本的物件欄位外, 額外包含所有 Meta 中的欄位, 範例如下:

record MyMeta(Long id, String idno) {}

// mapstruct mapper
@Mapper
interface MyEntityMapper {

  MyDto toDto(MyEntity entity);
  
  MyMeta toMeta(MyEntity entity);
  
  default WithMeta<MyDto, MyMeta> toDtoWithMeta(MyEntity entity) {
    return new WithMeta<>(toDto(entity), toMeta(entity));
  }
}

// API
@RestController
record MyController(MyRepository repository, MyEntityMapper mapper) {

  @GetMapping("/my-resources")
  List<WithMeta<MyDto, MyMeta>> getAllWithId() {
    return repository.findAll().stream().map(mapper::toDtoWithMeta).toList();
  }
}

輸出將會是:

[
  {
    "firstname": "Matt",
    "lastname": "Ho",
    "id": 1,
    "idno": "A123456789"
  }
]

如果欄位重複, 例如: MyDto 中也包含了 MyMeta 中的欄位, 則:

  • 序列化時: 會忽略 MyDto 的欄位, 以傳入的 MyMeta 欄位為主
  • 反序列化時: MyDto 及 MyMeta 中的欄位都會有一樣的值

在實際應用中, 你還可以設計共用的 Meta 物件, 以達到更好的共用性

Entity Revisions

Data JPA 擴充模組預設整合了 Spring Data Envers 來追蹤 Entity 的版本歷程。若需要使用，請依照以下步驟來啟用：

首先，在應用程式的進入點加上 @EnableEnversRepositories，例如：

@SpringBootApplication
@EnableEnversRepositories
public class MyApplication {

  public static void main(String[] args) {
    SpringApplication.run(MyApplication.class, args);
  }
}

接著，在需要追蹤版本紀錄的 Entity 中，加上 @Audited：

@Audited
@Data
@Entity
@Table(name = "MY_TABLE")
class MyEntity extends AbstractAuditingEntity<String> {

  @Id @GeneratedValue Long id;
  
  // some other field...
}

這樣就完成了設定，在每次資料異動時，都會自動追蹤 MyEntity 及 AbstractAuditingEntity 中的所有欄位的異動歷程。

若你需要在程式中取得這些歷程資訊，在 Repository 中需要多做一些設定，如下所示：

interface MyRepository extends JpaRepository<MyEntity, Long>,
  RevisionRepository<MyEntity, Long, Integer> {
}

這樣你就可以在程式中方便地查詢某個 ID 的所有版本歷程：

Page<Revision<Long, MyEntity>> revisions = repository.findRevisions(id, pageable);

你可以注意到所有的歷程紀錄都被封裝在一個 org.springframework.data.history.Revision 物件中。如果你需要針對其中每次的歷程做轉換，Data JPA 擴充模組也提供了一些方式來協助你，例如：

import static tw.com.softleader.kapok.data.history.RevisionMapper.mapping;

Page<Revision<Integer, MyDomain>> mapped =
  repository.findRevisions(id, pageable).map(mapping(domainMapper::toDomain));

這樣就可以很方便的將版本歷程轉換到另一個 MyDomain 物件中。完整範例可以參考: examples/envers。

Datasource Micrometer

Data JPA 擴充模組也整合了 Datasource Micrometer SQL 監控機制, 預設會將 JPA 所執行的 SQL (包含 parameter 值) 完整印出:

  • 一般 SQL: 輸出到 tw.com.softleader.kapok.data.jpa.SQL 中的 DEBUG 等級
  • 超過 300 秒的 SQL: 輸出到 tw.com.softleader.kapok.data.jpa.SLOW_SQL 中的 WARM 等級

透過 logger level 可以控制是否印出, 範例如下:

# application.yaml
logging:
  level:
    kapok-data-jpa.sql: debug # 這行等於同時控制以下兩個路徑, 當然你也可以各別控制
#   tw.com.softleader.kapok.data.jpa.SQL: debug
#   tw.com.softleader.kapok.data.jpa.SLOW_SQL: warn
#   kapok-data-jpa: debug # 或直接設定整個 kapok-data-jpa 模組也行, 只是你可能會看到更多的 log

可以透過 jdbc.datasource-proxy.query.enable-logging 及 jdbc.datasource-proxy.slow-query.enable-logging 來控制開關

如在壓測時我想要關閉, 則設定如下:

# application.yml
jdbc:
  datasource-proxy:
    query:
      enable-logging: false
    slow-query:
      enable-logging: false

Jdbc Execution Listener

如果想要在 SQL 執行前後做些固定邏輯, 則可以實作 QueryExecutionListener 或 MethodExecutionListener, 並註冊成 Spring Bean, Data JPA 擴充模組在啟動階段就會自動的配置完成, 例如:

@Component
class MyQueryExecutionListener implements QueryExecutionListener {

  @Override
  public void beforeQuery(ExecutionInfo execInfo, List<QueryInfo> queries) {
    queries.forEach(query -> {
      var sql = query.getQuery();
      var params = query.getParametersList();
      // do something...
    });
  }

  @Override
  public void afterQuery(ExecutionInfo execInfo, List<QueryInfo> queries) {
    queries.forEach(query -> {
      var sql = query.getQuery();
      var params = query.getParametersList();
      // do something...
    });
  }
}

Naming Strategy

如果應用程式在不同環境有 Naming 調整的的需求, Data JPA 模組提供了以下幾個方便的 class 可以選用!

Case Sensitive

Spring 預設的處理是駱駝命名轉底線, 且不分大小寫 ( Case Insensitive ), 所謂的不分大小寫實際上預設實作就是全轉小寫, 但可能會跟一些資料庫的保留字眼有衝突, 因此 Data JPA 模組提供了一個一模一樣的處理模式但區分大小寫的版本 ( Case Sensitive ): CaseSensitiveNamingStrategy.

透過 properties 中的 spring.jpa.hibernate.naming.physical-strategy 可以設定, 範例如下:

# application.yml
spring:
  jpa:
    hibernate:
      naming:
        physical-strategy: tw.com.softleader.kapok.data.jpa.hibernate.naming.CaseSensitiveNamingStrategy

Prefixed

如果你需要在名稱前面加上前綴字眼, Data JPA 模組提供了 PrefixedNamingStrategy 協助你來實作! PrefixedNamingStrategy 預設是設定成區分大小寫的 (Case Sensitive), 如果需要調整可以順便複寫 isCaseInsensitive 方法

Note

這不能直接使用的, 這算是一個輔助方便實作前綴命名的 Class.

例如, 我想要在 Table, Column 都加上 HI_ 前綴, Sequence 加上 HELLO_ 前綴, 則完整範例如下:

首先要先定義自己的 class 並繼承 PrefixedNamingStrategy, 將你要加 Prefix 的方法複寫掉.

public class GreetingPrefixedNamingStrategy extends PrefixedNamingStrategy {

  private static final String HI = "HI_";
  private static final String HELLO = "HELLO_";

  @Override
  protected String getTablePrefix() {
    return HI;
  }

  @Override
  protected String getColumnPrefix() {
    return HI;
  }

  @Override
  protected String getSequencePrefix() {
    return HELLO;
  }

  @Override
  protected boolean isCaseInsensitive(JdbcEnvironment jdbcEnvironment) {
    // return true; // 不區分大小寫
    return false; // 區分大小寫, PrefixedNamingStrategy 的預設
  }

  // 是否要避免重複 prefixed, 預設: false
  @Override
  protected boolean preventDuplicatePrefixed() {
    // return true; // 會先判斷原名稱是否已經是指定 prefix 開頭, 不是才會加上
    return false; // 如論如何都加上 prefix
  }
}

並再透過 properties 中的 spring.jpa.hibernate.naming.physical-strategy 更換設定:

# application.yml
spring:
  jpa:
    hibernate:
      naming:
        physical-strategy: my.package.GreetingPrefixedNamingStrategy

3 - Liquibase

Liquibase database migration and source control library.

Kapok Liquibase 是一個整合了 Liquibase 的擴充模組，提供了一個更簡單的方式來管理資料庫的版本，並在 Spring Liquibase 的整合之上提供了更多元的控制模式。

Getting Started

開啟 pom.xml, 加入下述依賴後, App 啟動後就會自動配置 Liquibase:

<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-liquibase</artifactId>
</dependency>

若 App 有使用 JPA, 請確保 spring.jpa.defer-datasource-initialization 是關閉的，以避免 liquibase 和 entityManagerFactory發生循環依賴問題

spring:
  jpa:
    defer-datasource-initialization: false

接著你就可以開始撰寫 ChangeLog

Disabled Liquibase

Kapok 提供以下幾種關閉的模式

Disabled Extending Liquibase

若你想要關閉的是 Kapok 的擴充, 退回 Spring 原生的 Liquibase 行為, 透過 propertes 來設定如下:

kapok:
  liquibase:
    enabled: false

Disabled Liquibase

若你想要完全關閉所有 Liquibase 的行為, 透過 properties 設定如下:

spring:
 liquibase:
   enabled: false

ChangeLog

ChangeLog 是 Liquibase 的核心概念, 它是一個描述資料庫變更的 XML 或 YAML 檔案, 最上層的 ChangeLog 檔案預設位於 classpath:/db/changelog/db.changelog-master.yaml, 透過 properties 可以調整該檔案的位置:

spring:
  liquibase:
    # 預設在 classpath:/db/changelog/db.changelog-master.yaml
    change-log: classpath:/path/to/my-changelog.yaml

在這檔案中, 你可以設定再去引用更多其他的 ChangeLog 檔案, 或是設定一到多組 ChangeSet, 範例如下：

databaseChangeLog:
  # 引用一至多組其他 change log
  - include:
      file: db/changelog/2024/03/baseline-changelog.yaml
  # 設定一至多組 change set
  - changeSet:
      id: {unique_id}
      author: {user_name}
      context: {changes_group}
      changes:
        ... # support yaml, json, xml
      rollback:
        ... # support yaml, json, xml

每一個 ChangeSet 代表了一個資料庫的變更, 參數包含了:

  • id: 需唯一, 且必須
  • author: 作者, 可為任意文字, 必須
  • content: 用來做 ChangeSet 的分類使用, 可以應用在區分各個環境, 非必需但建議
  • changes: 一或多個的變更, 非必需, 語法請參考連結
  • rollback: 一或多個回滾, 非必需但建議, 語法請參考連結
  • 其他更多 ChangeSet 有關的設定, 請參考連結, 非必須

ChangeLog 檔案中的每個 ChangeSet 都是獨立的, Liquibase 會根據 ChangeLog 檔案中宣告的順序依序執行所有的 ChangeSet 來執行資料庫的變更，執行成功後記錄結果至 Tracking Table 中。

ChangeLog File Structure

我們推薦以下的 ChangLog 檔案結構, 當然, 實際上的運用請依照專案需求考量優先:

resources/db
└── changelog
    ├──  db.changelog-master.yaml   # 進入點, 這邊只放 include, 不放任何的 change set
    └── 2024
        ├── 03                      # 依照年月區分資料夾
        │   └── baseline.yaml       # 年月下的 change log 只放 change set, 不 include 其他檔案
        └── 04

            ├── feature-#001.yaml
            └── ...

Tracking Table

Liquibase 會在資料庫中建立 Tracking Table, 包含了:

  • Database Change Log Table - 用來記錄用執行結果
  • Database Change Log Lock Table - 用來做 Leader Election, 以避免多個 Process 同時進行

上述 Table 可以透過 properties 調整名稱, 相關的設定範例及預設值如下:

spring:
  liquibase:
    # 無預設設定
    liquibase-schema: MY_SCHEMA
    # 預設為: ${spring.application.name}_CHANGELOG
    database-change-log-table: MY_CHANGELOG
    # 預設為: ${spring.application.name}_CHANGELOGLOCK
    database-change-log-lock-table: MY_CHANGELOGLOCK

Database Change Log Table

此 Table 用來記錄用執行結果, 且服務於下次啟動時, Liquibase 會根據 ID 對應的 ChangeSet 去計算 MD5SUM 是否與 Table 中紀錄的相同，若不同即會拋出錯誤例外中斷服務啟動。

Liquibase Mode

Spring 的 Liquibase 整合只提供了一種啟動模式, 預設是 Update 模式, 當服務啟動時會自動執行 ChangeLog 檔案中的 ChangeSet，並且記錄執行結果至 Tracking Table 中

Kapok 的 Liquibase 擴充模組提供了更多的起動模式, 讓使用者可以更方便的應用於各種情境, 透過 properties 可以設定, 如:

kapok:
  liquibase:
    mode: UPDATE

模式包含了:

  • UPDATE - 當服務啟動時會自動執行ChangeLog檔案中的ChangeSet，並且記錄執行結果至 Tracking Table 中 (預設)
  • CHANGE_LOG_SYNC - 此模式用於將所有 ChangeSet 標記為在資料庫中已執行，更新至 Tracking Table 中
  • ROLLBACK - 此模式用於回滾應用於資料庫的變更
  • VALIDATE - 此模式用於驗證 ChangeSet 的正確性，透過 MD5SUM 檢查資料庫中的 ChangeSet 是否與 ChangeLog 檔案中的一致。

在啟動應用程式時, 你可以於 Console 查看 INFO 等級的訊息來確認啟動的模式, 內容類似如下:

... t.c.s.k.l.a.LiquibaseBeanPostProcessor : Initializing liquibase with mode: UPDATE

Intercepting Liquibase

Kapok 加入了攔截器的機制, 可在操作 Liquibase 的前後執行客製化的邏輯, 此外, Kapok 還提供了一些實作選項, 以提供使用者在不同的情境中來使用

Spool

Spool 功能設計用來在操作 Liquibase 的前或後, 依據該次執行的 ChangeSet IDs, 在指定目錄下尋找與這些 IDs 對應的 SQL 指令, 執行這些 SQL 指令並將執行結果輸出

配過配置 kapok.liquibase.spool.* 下的參數, 可以配置 Spool 功能:

  • pre-sql.enabled - 啟動 pre-sql spool 機制 (預設: false)
  • pre-sql.location - 存放 SQL 指令檔案的目錄, 使用 Resource Pattern 格式
  • pre-sql.output - SQL 指令執行結果的輸出目錄, 使用 Resource Pattern 格式
  • pre-sql.ids - 指定要尋找的 ChangeSet IDs, 若未設定則尋找該次所有的 ChangeSet IDs
  • post-sql.enabled - 啟動 post-sql spool 機制 (預設: false)
  • post-sql.location - 存放 SQL 指令檔案的目錄, 使用 Resource Pattern 格式
  • post-sql.output - SQL 指令執行結果的輸出目錄, 使用 Resource Pattern 格式
  • post-sql.ids - 指定要尋找的 ChangeSet IDs, 若未設定則尋找該次所有的 ChangeSet IDs

SQL Location

在 SQL 指令檔案的目錄下 (*-sql.location), 檔案結構應遵循 ${changeset-id}/{任意檔名}.sql 的格式, 每個 SQL 指令檔案中可包含一個或多個 SQL 指令, 不同的 SQL 之間應以分號 (;) 分隔, 範例如下:

/path/to/my/*-sql.location
├── id1
│   ├── any_filename_is_acceptable.sql
│   └── another_file.sql
├── id2
│   ├── a.sql
│   └── b.sql
└── id3
    └── ...

應用程式啟動後, 將根據當前 Liquibase 執行的 ChangeSet IDs 的順序, 搜尋 SQL 目錄下符合的 ID 子目錄, 讀取並執行其中的 .sql 檔案

預設情況下 Kapok 不保證每個 ID 子目錄中檔案的讀取順序, 若需要控制執行順序, 請將檔案命名為 {整數}_{任意檔名}.sql, Kapok 就會使用檔名中的整數作為排序的基礎, 數字越小的檔案越優先的執行, 例如:

/path/to/my/*-sql.location
└── id1
      ├── a.sql
      ├── b.sql
      ├── 01_x.sql
      ├── 002_y_1.sql
      └── 3_z.sql

在此情況下, 執行順序將確保為 01_x.sql, 002_y_1.sql, 3_z.sql, 其餘檔案的執行順序則不作保證

Output

當未提供輸出檔案目錄 (*-sql.output) 時, 將固定輸出到 Console 的 INFO 等級, 若指定了輸出目錄, 則會將結果寫入到該指定目錄中, 並按照 ${changeset-id}/{原檔名}.{時間戳記} 的模式命名檔案, 舉例來說:

/path/to/my/*-sql.output
├── id1
│   ├── any_filename_is_acceptable.sql.1709602631
│   └── another_file.sql.1709631499
├── id2
│   ├── a.sql.1709631828
│   └── b.sql.1709631840
└── id3
    └── ...

若你需要客製化 Output 邏輯, 可以實作 SqlQueryConsumer 並將其註冊成 Spring Bean, 以完全複寫上述的行為, 如:

@Component
class MySqlQueryConsumer implements SqlQueryConsumer {

  @Override
  public void accept(@NonNull SqlQuery query) {
    // 實作客製化邏輯
  }
}

Example

舉例來說, 我希望同時啟用 pre-sql 和 post-sql 功能, 並同時尋找 classpath 下的 /db/patch 目錄中的 SQL 檔案, 也將執行結果都同時輸出至 OS 的 /path/to/patch-result 目錄中, 則可以進行以下的設定:

kapok:
  liquibase:
    spool:
      pre-sql:
        enabled: true
        location: classpath:/db/patch
        output: file:/path/to/patch-result
      post-sql:
        enabled: true
        location: classpath:/db/patch
        output: file:/path/to/patch-result

Extending Interceptor

如果你想要加入自定義的攔截邏輯, 你需要實作 PerformUpdateInterceptor:

class MyPerformUpdateInterceptor implements PerformUpdateInterceptor {

  @Override
  public boolean preUpdate(Collection<String> changeSetIdsToRun) throws LiquibaseException {
    // do something
    return true; // 返回 true 代表要允許後續執行 Liquibase, 返回 false 則不會執行 Liquibase
  }

  @Override
  public void postUpdate(Collection<String> changeSetIdsToRun) throws LiquibaseException {
    // do something
  }

  @Override
  public void afterCompletion(Collection<String> changeSetIdsToRun, Exception ex)
      throws LiquibaseException {
    // do something
  }
}

接著透過實作 PerformUpdateInterceptorFactory 並註冊成 Spring Bean 即可:

@Configuration
class MyConfig {

  @Bean
  PerformUpdateInterceptorFactory myPerformUpdateInterceptor() {
    return liquibase -> new MyPerformUpdateInterceptor();
  }
}

Auto Stop

Kapok 擴充模組還提供了自動關閉的機制, 可以在 Liquibase 執行完畢後會自動停止當前的應用程式, 透過 kapok.liquibase.auto-stop.* 下的參數可以啟用:

kapok:
  liquibase:
    auto-stop:
      # 啟用自動關閉 (預設 false)
      enabled: true
      # 關閉時的離開狀態 (預設 0)
      exit-status: 0

此機制主要用於容器中, 特別是 Kubernetes 的 Init Container, 當 Init Container 中的 App 啟動且完成 Liquibase 的執行後, 即自動的關閉 Process, 讓 Kubernetes 可以執行後續的 Container App

4 - Multicache

Caching data in cross-application shared pool.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-multicache</artifactId>
</dependency>

MulitCache 擴充模組提供了在 Container Platform 中, 同服務跨 Replicas 或跨服務之間的共享快取機制

Overview

一般常見的 Cache (如 Sprign Cache, Google Guava 等) 是 Local Cache 機制, 當你的服務開在 Container Platform 中 (如 Kubernetes) 且又被開 Replicas N 個時, 被啟動的這些 Instance 都會有自己的 Local Cache, 且這些 Cache 之間互相是沒有互動的, 所以實際上資料的載入就會被執行至多 N 次

例如: 我們的服務對於資料庫 Table A 的資料做了 Cache, 若這時候服務被 Replicas 到了 5, 則一共會出現 5 個服務 Instance, 而 Table A 實際上最多就會被 IO 5 次

MultiCache 擴充模組除了管理 Local Cache 之外, 還同時支援 Remote Cache 的互動, 作為這些 Instance 之間的共享機制 (Cache Shared Pool), 即支援了跨 Replicas 之間甚至跨服務之間的使用!

當其中一個 Instance 取回 Cache 資料後, 就會放入這個 Shared Pool, 其他的 Instance 就可以直接使用這些 Cache 資料!

Compatible with Spring Caching

MultiCache 模組是基於 Spring Caching 所擴充發展的, 因此完全相容於 Spring 提供的 Caching API, 例如: Annotation-based Caching, 本文介紹的是在其基礎上所擴充的功能, 若你想要使用 Spring 提供的的 Caching API, 可參考使用情境中的程式範例

Configuring the Cache

在開始之前, 首先需要定義一到多個 Cache Name, 這是一個獨特且不可重複的字串, 程式中在操作或設置快取時, 都會基於這個 Cache Name 進行, 在每個 Cache Name 下, 可以存放一到多個 Key:Value 的快取組合, 在此結構中, Cache Name + Key 形成關聯特定 Value 的唯一識別, 示意圖如下:

cache-name-1
├── key-1 ..... <value>
├── key-2 ..... <value>
└── ...
cache-name-2
├── key-1 ..... <value>
├── key-2 ..... <value>
├── key-3 ..... <value>
└── ...

對於 Cache Name 或 Key 的命名, 我們推薦使用類似於 Redis 風格的命名方式: 通過冒號（:）來分隔多個名詞, 例如：my:cache:name

一旦 Cache Name 被確定, 下一步就是配置 kapok.cache 下的參數, 以此來控制快取的行為:

  • cache-prefix - 在所有 Cache Name 前統一都加上前綴字串 (預設: 空字串, 即不加)

Note

若不同服務之中會使用到相同的 Cache Name, 則各自服務應加上不同的 Prefix 以避免互相干擾

Local Cache 的相關參數:

  • caffeine.expire-after-access - 存取後的過期時間，單位 ms 或 Duration (預設: 0, 不過期)
  • caffeine.expire-after-write - 寫入後的過期時間，單位 ms 或 Duration (預設: 0, 不過期)
  • caffeine.refresh-after-write - 更新後的過期時間，單位 ms 或 Duration (預設: 0, 不過期)
  • caffeine.expire-policy - 以程式控制清除策略, 指定客製化的 ExpirePolicy class 完整名稱, 設置此設定將忽略 caffeine.expire-after-access 及 caffeine.expire-after-write
  • caffeine.initial-capacity - 初始化快取大小 (預設: 0, 初始不預留記憶體)
  • caffeine.maximum-size - 最大 cache 數量 (預設: 0, 不限制)
  • caffeine.maximum-weight - 最大 weight 數量 (預設: 0, 不限制)
  • caffeine.weigher - 指定客製化的 Weigher 的 class 完整名稱

可閱讀 Caffeine 官方文件以詳細了解各項參數

Remote Cache 的相關參數:

  • redis.expire - 寫入後的過期時間，單位 ms 或 Duration (預設: 0, 不過期)
  • redis.expire-policy - 以程式控制清除策略, 指定客製化的 ExpirePolicy class 完整名稱, 設置此設定將忽略 redis.expire

上述 properties 皆可在 caffeine.names 或 redis.names 下針對 Cache Name 設定個別的快取模式, 可配置的內容皆跟上述的參數一樣.

例如, 針對 my:cache:name 設定一組快取行為, 其餘的 Cache Name 都使用預設的快取行為, 則設定範例如下:

# application.yaml
kapok:
  cache:
    caffeine: # Local cache 預設設定, 單位 ms 或 Duration (建議)
      expire-after-write: PT10S
      names:
        "[my:cache:name]":
          expire-after-write: PT1M
    redis: # Remote cache 預設設定, 單位 ms 或 Duration (建議)
      expire: PT10M
      names:
        "[my:cache:name]":
          expire: PT1H

Tip

建議 Local cache expiration 設定為可接受的最大 dirty read 時間, Remote cache expiration 依期望的 cache value 不變化時間設定

Redis Serializer

Remote Cache 的底層實作就是 Redis, 在操作 Redis 時, Value 物件會透過 ObjectMapper 進行 JSON 格式的轉換, 請注意: 用於快取的 ObjectMapper 與系統中註冊的是分開的

你可以透過 kapok.cache.redis.jackson.* 下的參數來控制轉換細節, 這些參數源自於 spring.jackson.*, 此外, 你也可以點擊這裡查看 MultiCache 擴充模組中配置的預設值, 以下是一些關鍵的參數說明:

  • default-property-inclusion - 序列化時包含哪些屬性的控制
  • time-zone - 格式化日期時使用的時區
  • date-format - 日期格式的 Pattern 字串, 或日期格式 formatter 的 class name
  • serialization.* - 物件序列化功能的 on/off
  • deserialization.* - 物件反序列化功能的 on/off
  • mapper.* - 一般用途相關功能的 on/off
  • parser.* - 解析器相關功能的 on/off
  • generator.* - 產生器相關功能的 on/off
  • visibility.* - 可見性閾值, 用於限制自動檢測的方法 (和欄位)

例如, 我想要增加設定: 讓 enum 在轉換時, 使用 index 而不是 name, 則設定範例如下:

# application.yml
kapok:
  cache:
    redis:
      jackson:
        serialization:
          write-enums-using-index: true

Note

在 kapok.cache.redis.jackson.* 下開出的是較常見的設定參數, 並非包含完整的 spring.jackson.* 參數

若你有想要設定的參數沒開出來, 請改成註冊自定義的 tw.com.softleader.kapok.cache.support.CacheRedisSerializer 成 Spring Bean, 以達到完全的客製化, 範例如下:

@Configuration
class MyConfig {

  @Bean
  CacheRedisSerializer myCacheRedisSerializer() {
    var myMapper = Jackson2ObjectMapperBuilder.json()
      ... // 完整的配置你適用的 mapper
      .build();
    return new CacheRedisSerializer(myMapper);
  }
}

Expire Policy

ExpirePolicy 是 MultiCache 模組所提供的擴充介面, 讓應用程式可以動態的來決定每次放 Cache 的到期時間. 例如, 我想要每次放 Cache 時, 都只到午夜 12 點且最少 1 秒, 則範例如下:

首先實作 ExpirePolicy, 並必須提供一個無參數的建構值:

public class UntilMidnightExpirePolicy implements ExpirePolicy<MyKey, MyValue> {

  @Override
  public Duration expireAfterCreate(MyKey key, MyValue value) {
    var midnight = LocalDate.now().plusDays(1).atStartOfDay();
    var secondsToMidnight = Math.max(
      LocalDateTime.now().until(midnight, ChronoUnit.SECONDS),
      1L // 若回傳 Duration.ZERO 代表快取將永不到期, 因此這邊我們最少快取 1 秒
    );
    return Duration.ofSeconds(secondsToMidnight);
  }
}

接著在 properties 中設定即完成設定:

# application.yml
kapok:
  cache:
    caffeine:
      names:
        "[my:cache:name]":
          expire-policy: some.package.UntilMidnightExpirePolicy
    redis:
      names:
        "[my:cache:name]":
          expire-policy: some.package.UntilMidnightExpirePolicy

Using the Cache

MultiCacheManager

MultiCache 擴充模組提供了 MultiCacheManager 物件讓程式可以方便的操作 Cache, 你只需要透過 Spring 注入即可取得, 如:

@Autowired
MultiCacheManager cacheManager;

Population

透過下述 API 可以取得 Cache 資料, 當 Key 不存在時才會去執行所傳入的 CACHE_LOADER 來取得資料!

cacheManager.get(CACHE_NAME, CACHE_KEY, CACHE_TYPE, CACHE_LOADER);

此 API 固定回傳 Optional

例如, 我想要 Cache 資料庫查詢 findByCode 的結果, 完整程式碼如下:

@Repository
interface MyRepository extends JpaRepository<MyEntity, Long> {
  Optional<MyEntity> findByCode(String code);
}

@Service
@RequiredArgsConstructor
class MyService {
  static final String CACHE_NAME = "my:cache:name";

  final MyRepository repository;
  final MultiCacheManager cacheManager;
  
  Optional<MyEntity> getByCode(String code) {
    return cacheManager.get(
        CACHE_NAME,
        code,
        MyEntity.class,
        repository::findByCode);
  }
}

Cache Key

Cache Key 可以是任何類型的 Object, 由於不同的底層快取實作方式, 運作方式也因此有所不同, 如下圖所示:

                                                                  
          Local Cache  ───────────────────────────► Caffeine Cache
                                                                  
Key ────►                                                         
                            ┌─────────────────┐                   
          Remote Cache ────►│ Type Conversion ├───► Redis Cache   
                            └─────────────────┘
  • Local 端: 直接將物件交由底層快取實作處理
  • Remote 端: 物件先經由 Type Conversion 機制轉換成 String, 再由底層實作處理

為了提升快取 Key 的比對效率和準確性, 建議使用 Java 的基本型別作為 Cache Key, 如 String, Long, int 等, 這樣可以避免因不同快取實作造成的問題

Cache Key Type Conversion

如果你需要使用非基本型別作為 Cache Key, 請在設計自定義 Key 物件前, 務必瞭解核心提供的型態轉換規則:

  1. 如果物件實作了 JsonSerializableCacheKey, 則由 Redis Serializer 轉換成 JSON 字串, 請務必瞭解: 使用 JSON 時, 可靠性可能會因底層實作而受影響, 例如: 轉換後的欄位順序
  2. 如果物件實作了 SerializableCacheKey, 則使用 #toCacheKey() 方法轉換成字串
  3. 如果 Spring 的 DefaultConversionService#addDefaultConverters 能夠處理該物件, 則使用其進行轉換
  4. 如果物件有 #toString() 方法, 則直接使用此方法進行轉換
  5. 如果以上方法均無法處理, 則 log 相關的錯誤信息, 不做遠端的快取

例如, 我想使用 Entity 中的 ID 作為 Key, 範例如下:

@Data
class MyEntity implements SerializableCacheKey {

  private Long id;

  @Override
  public String toCacheKey() {
    return Objects.requireNonNull(id, "id must not be null to convert to cache key").toString();
  }
}

另一個例子, 若希望直接以 JSON 格式轉換 Key 物件, 可以如下實作:

record MyKey(String hello) implements JsonSerializableCacheKey {}

Cache Loader

MultiCacheManager 一共支援以下幾種 Cache Loader:

  • t.c.s.kapok.cache.CacheLoader: 傳入 Key 回傳 Optional 物件, 當回傳 Optional.empty() 時代表該 Key 不做 Cache
  • t.c.s.kapok.cache.CacheSupplier: 無傳入回傳 Optional 物件, 當回傳 Optional.empty() 時代表該 Key 不做 Cache

上面幾個 Interface 也都提供了方便的 static method 以快速的介接不是回傳 Optional 的 Java Function 或 Supplier:

  • CacheLoader.from(Function) - 串接 java.util.function.Function<K, V>
  • CacheLoader.fromCollection(Function) - 串接 java.util.function.Function<K, Collection<V>>
  • CacheLoader.fromMap(Function) - 串接 java.util.function.Function<K, Map<MK, KV>>
  • CacheSupplier.from(Supplier) - 串接 java.util.function.Supplier<V>
  • CacheSupplier.fromCollection(Supplier) - 串接 java.util.function.Supplier<Collection<V>>
  • CacheSupplier.fromMap(Supplier) - 串接 java.util.function.Supplier<Map<MK, MV>

Cache Type

MultiCacheManager 一共支援以下幾種 Cache Type:

  • java.lang.Class: 指定 Cache 的型態
  • c.f.jackson.core.type.TypeReference: 指定有泛型的 Cache 型態, 如 Collection 等

例如, 我想要 Cache 資料庫查詢 findByCodeLike 的結果, 型態為List<MyEntity>, 完整程式碼如下:

@Repository
interface MyRepository extends JpaRepository<MyEntity, Long> {
  List<MyEntity> findByCodeLike(String code);
}

@Service
@RequiredArgsConstructor
class MyService {
  static final String CACHE_NAME = "my:cache:name";

  final MyRepository repository;
  final MultiCacheManager cacheManager;
  
  List<MyEntity> getByCodeLike(String code) {
    return cacheManager.get(
        CACHE_NAME,
        code,
        new TypeReference<>() {
        },
        CacheLoader.fromCollection(repository::findByCodeLike))
      .orElseGet(Collections::emptyList);
  }
}

Eviction

透過以下 API 可以將 Cache 中的資料清除

// 清除 CACHE_NAME 下所有的 Cache
cacheManager.evict(CACHE_NAME);

// 清除 CACHE_NAME + CACHE_KEY 一筆 Cache
cacheManager.evict(CACHE_NAME, CACHE_KEY);

// 依照自定義條件清除 CACHE_NAME + CACHE_KEY
cacheManager.evictIf(CACHE_NAME, KEY_PREDICATE);

由於 Cache Key 可能會受到底層實作的影響, 當使用 cacheManager.evictIf() 方法時, 如果 Key 為自定義類型時, 請特別注意傳入的 Predicate 應該根據不同情況進行判斷, 例如:

cacheManager.evictIf(CACHE_NAME, key -> {
  if (key instanceof MyKey localKey) {
    return ...; // 針對 Local Cache 的判斷邏輯
  }
  if (key instanceof String remoteKey) {
    return ...; // 針對 Remote Cache 的判斷邏輯
  }
  throw new UnsupportedOperationException("Unsupported key type: " + key);
});

Predefined Loading Cache

當 Cache 被很多地方使用時, 你可以透過以下 API 預先定義好 Cache 怎麼被使用, 接著你就可以方便的重複使用!

// LoadingCache<CACHE_KEY_TYPE, CACHE_TYPE>
cacheManager.loadingCache(CACHE_NAME, CACHE_TYPE, CACHE_LOADER);

// SupplyingCache<CACHE_TYPE>
cacheManager.loadingCache(CACHE_NAME, CACHE_KEY, CACHE_TYPE, CACHE_SUPPLIER);

假設, 現在有段非常浩效能的邏輯想要被 Cache: 將文字轉小寫

java.lang.String#toLowerCase()

我們想要先預定好這個 Cache 讓一段程式碼間可以重複使用, 則程式碼範例:

@Service
@RequiredArgsConstructor
class MyService {
  static final String LOWER_CASE_CACHE = "example:lower-case:cache";
  
  final MultiCacheManager cacheManager;
  
  String myExpensiveLogic(String in) {
    LoadingCache<String, String> lowerCaseCache = cacheManager.loadingCache(
      LOWER_CASE_CACHE,
      String.class,
      CacheLoader.from(String::toLowerCase));

    lowerCaseCache.get(in);

    // brah brah brah

    lowerCaseCache.get(in);

    // brah brah brah

    lowerCaseCache.evict(in);
  }
}

這個機制也可以運用在 Spring Bean 準備的期間, 如 @PostConstruct, 讓整個 Bean 後續都可以方便的使用已預定好的 Cache, 程式碼範例如:

@Service
@RequiredArgsConstructor
class MyService {
  static final String LOWER_CASE_CACHE = "example:lower-case:cache";
  
  final MultiCacheManager cacheManager;
  LoadingCache<String, String> lowerCaseCache;
  
  @PostConstruct
  void setupCache() {
    lowerCaseCache = cacheManager.loadingCache(
      LOWER_CASE_CACHE,
      String.class,
      CacheLoader.from(String::toLowerCase));
  }
}

進一步也可以在 App 啟動階段就先預定好 Cache, 需要的程式透過 Spring 拿到就可以使用, 程式碼範例如:

@Configuration
public class MyCacheConfig {
  public static final String LOWER_CASE_CACHE = "example:lower-case:cache";

  @Bean(LOWER_CASE_CACHE)
  LoadingCache<String, String> lowerCaseCache(MultiCacheManager cacheManager) {
    return cacheManager.loadingCache(
      LOWER_CASE_CACHE,
      String.class,
      CacheLoader.from(String::toLowerCase));
  }
}

@Service
@RequiredArgsConstructor
class MyService {

  @Qualifier(MyCacheConfig.LOWER_CASE_CACHE)
  final LoadingCache<String, String> lowerCaseCache;
}

Predefined Cache Definition

當 Cache 會被用在多個使用 Kapok 為基底應用程式中時, 你可以透過以下方式預先定義好 Cache API (快取怎麼被使用), 甚至是先定義好 Cache 行為 (多久打掉之類的)

首先決定要實作 LoadingCache<K, V> 或 SupplyingCache<V>, 例如, 還是一樣有段非常耗效能的邏輯: 將文字轉小寫

java.lang.String#toLowerCase()

則我們選擇實作 LoadingCache<String, String> 來定義 Cache API:

// 這個 class 由 Cache 提供方提供

@RequiredArgsConstructor
public class LowerCaseCache implements LoadingCache<String, String> {

  public static final String CACHE_NAME = "string:lower-case";

  final MultiCacheManager cacheManager;

  @Override
  public Optional<String> get(String cacheKey) {
    return cacheManager.get(
        CACHE_NAME,
        cacheKey,
        String.class,
        CacheLoader.from(String::toLowerCase));
    }

  @Override
  public void evict() {
    cacheManager.evict(CACHE_NAME);
  }

  @Override
  public void evict(String cacheKey) {
    cacheManager.evict(CACHE_NAME, cacheKey);
  }

  @Override
  public void evictIf(Predicate<? super Object> keyPredicate) {
    cacheManager.evict(CACHE_NAME, keyPredicate);
  }
}

完成就可以以 lib 方式 release 出, 這邊注意一下, 提供方需要放的應該僅有 libraries 模組, 而不是整個 multicache 模組, 畢竟提供方不應該該強迫使用方一定要使用甚至啟動整個 cache, 而應該是可選擇性的

<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-libraries</artifactId>
</dependency>

其他同樣使用 Framework 的應用程式只要將之註冊成 Spring Bean 就可以使用了:

// 以下是 Cache 使用方的設定

@Configuration
public class MyCacheConfig {

  @Bean
  LowerCaseCache lowerCaseCache(MultiCacheManager cacheManager) {
    return new LowerCaseCache(cacheManager);
  }
}

@Service
@RequiredArgsConstructor
class MyService {

  final LowerCaseCache lowerCaseCache;
}

依照上述範例, 現在 “string:lower-case” 這個 Cache API 已經由 Cache 提供方提供了, 但其Cache 的行為還是必須由 Cache 使用方去定義

Predefined Cache Config

Cache 提供方可以進一步的透過實作 CacheConfigFactory, 提供事先定好的 Cache 行為給使用方

// 這個 class 由 Cache 提供方提供

public class LowerCaseCacheConfigFactory implements CacheConfigFactory {

  @Override
  public CacheConfig create(String name) {
    if (!name.equals(LowerCaseCache.CACHE_NAME)) {
      return null; // 如果 cache name 不是我們的目標, 就 return null 代表不處理
    }
    return CacheConfig.builder()
        .caffeine(CaffeineConfig.builder()
            .expireAfterWrite(Duration.ofMinutes(10))
            ... // 設定更多本地端的參數 
            .build())
        .redis(RedisConfig.builder()
            .expire(Duration.ofMinutes(60))
            ... // 設定更多遠端的參數 
            .build())
        .build();
  }
}

其他同樣使用 Framework 的應用程式, 若想要使用 Cache 提供方的建議設定只要將之註冊成 Spring Bean 就可以生效了

// 以下是 Cache 使用方的設定

@Configuration
public class MyCacheConfig {

  @Bean
  LowerCaseCacheConfigFactory lowerCaseCacheConfigFactory() {
    return new LowerCaseCacheConfigFactory();
  }
}

當然使用方也可以選擇不要註冊, 而是透過自身的 properties 來控制 Cache 的行為!

Disabling the Cache

關閉 MultiCache 可以有幾種模式, 如下所示:

  • 只關閉遠端快取, 保留本地快取功能
  • 完全關閉快取機制, 包括遠端和本地快取

Only Disable the Remote Cache

啟動 MultiCache 模組後, 會自動引入 Spring Data Redis, 應用程式就會在啟動時嘗試連線到 Redis, 即使當前環境中沒有 Redis, 也不會影響使用, 但會持續出現連線失敗的 log 訊息

在沒有 Redis 的環境中, 你可以選擇只關閉 Redis, 這樣 MultiCache 仍將運作, 但只保留本地端的快取行為, 例如:

spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration

或者, 也可以在 pom.xml 中直接排除 Spring Data Redis:

<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-multicache</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-data-redis</artifactId>
    </exclusion>
  </exclusions>
</dependency>

Full Disable the Cache

透過設定 kapok.cache.enabled, 可以控制 MultiCache 模組的開啟或關閉, 預設情況下是啟用的, 關閉快取後, 程式中所有使用 MultiCacheManager 的部分都不會受影響, 只是應用程式在執行時相當於沒有快取的效果, 以下是關閉快取的設定範例:

kapok:
  cache:
    enabled: false

如關閉遠端快取所述, 如果你也想要同時關閉背後的 Redis 機制, 可以同時配置兩種關閉的設定, 例如:

spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration

kapok:
  cache:
    enabled: false

REST API

MultiCache 模組提供了一組 REST API 來控制 MultiCacheManager 部分的操作, 方便應用在不同的業務情境中, 例如: 透過 API 排程器在固定時間打掉指定 Cache name.

這組 API 預設沒有啟動, 透過配置 kapok.cache.rest-api.* 下的參數可以啟用及做更多的控制:

  • enabled: 是否啟用 MultiCache REST API (Default: false)
  • skip-security: 若有啟動安控, 是否要從中排除 MultiCache REST API (Default: false)

啟動的範例如下:

# application.yml
kapok:
  cache:
    rest-api:
      enabled: true

啟動後, 會自動的註冊一組路徑開頭為 /multicaches/** 的 REST API, 你可以到 Swagger UI 上查看更多的說明

Important

此 API 的 URL 路徑是固定的, 啟用前請確保你的應用程式中沒有路徑上的衝突

5 - Mutation

Declarative definition of bean mutations.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-mutation</artifactId>
</dependency>

Mutation 模組提供了一種通過聲明式 (declaration) 的方式來定義變化規則, 使用它即可在執行時期, 依照這些規則為 Java Bean 進行調整, 除了內置的規則外, 你也可以定義自己的變化規則

Important

變化是直接改變物件中欄位的值

若一個欄位被標記為 final, 即表示這個欄位的值一旦賦值後便不能改變, 這會使得該變化規則無法應用於該欄位上, 此外, Java 中的 record 類型也是不可變的, 同樣不適合應用變化規則, 在為 Java Bean 定義變化規則時, 請留意這些限制

Usage

首先, 為你的物件宣告變化規則, 例如:

@Data
class PersonInfo {

  private String name;

  @StringMask(start = 2, end = 7)
  private String idno;
}

這個例子中, 我們為 PersonInfo 類別的 idno 屬性定義了一個變化規則, 使用 @StringMask 注解來指定字符串的一部分應該被遮蔽

接下來, 你可以通過以下兩種方式之一來進行屬性的變化:

Inject Mutator

你可以 Autowired 來注入 Mutator, 然後在任何地方使用它來對對象進行變化, 例如:

@Service
public class MyService {

  @Autowired
  private Mutator mutator;

  public PersonInfo getPerson() {
    PersonInfo person = ...; // 假設這裡是從某處獲取的 PersonInfo
    return mutator.mutate(person); // 使用 mutator 對 person 進行變化
  }
}

Using @Mutated

另一種方式是在 method 上使用 @Mutated, 當你這樣做時, Mutation 模組會自動對該 method 的返回值進行變化, 這意味著你不需要直接調用 mutator, 只需返回原始對象即可, 變化過程會自動發生, 例如:

@Service
public class MyService {

  @Mutated
  public PersonInfo getPerson() {
    PersonInfo person = ...; // 假設這裡是從某處獲取的 PersonInfo
    return person; // 返回 person 實例, @Mutated 注解將觸發對其進行變化
  }
}

Customizing Mutation Rule

每一個 Mutation Rule 都由兩個部分組成:

  • 一個 @tw.com.softleader.kapok.mutation.rule.Rule annotation 來定義處理變化的實作
  • 一個 tw.com.softleader.kapok.mutation.rule.RuleHandler 實作變化的邏輯, 這會在每次變化時被呼叫, 實作上請特別注意效能問題

假設我們想要定義一個處理文字的客製化變化規則, 以下為程式碼範例, 首先定義客製化的 MyRule 規則:

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Rule(handledBy = MyRuleHandler.class)
public @interface MyRule {
}

然後實作 MyRuleHandler, 你可以選擇以下其一方式註冊皆可生效:

  • 提供一個無參數的建構值
  • 註冊成 Spring Bean
class MyRuleHandler implements RuleHandler<MyRule, String> {

  @Override
  public String apply(@NonNull MyRule rule, @Nullable String value) {
    // 處理變化的邏輯, 注意 value 可能為 null
    return value; // 返回處理後的結果
  }
}

這樣就完成了, 接著我們就可以開始使用:

@Data
class PersonInfo {

  @MyRule // 使用我們自定義的規則
  private String name;
}

Composed Mutation Rule

變化規則是可以組合的, 你可以利用這一特性, 重複使用一至多個已設計好的規則, 例如:

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@ReplacePattern(regex="\\r\\n", replacement="\n")
@StringMask(start = 2, end = 7)
public @interface MyComposedRule {
}

如上述示例, 將會先執行 @ReplacePattern, 接著執行 @StringMask, 而在組合的規則變化中也支援設計變數, 更加的有使用的彈性, 例如:

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@ReplacePattern(regex="\\r\\n", replacement="\n")
@StringMask(start = 2, end = 7)
public @interface MyComposedRule {

  @AliasFor(annotation = StringMask.class)
  int start() default 0;
}

如上述示例, @StringMask 的參數預設將會是 start = 0, end = 7

Execution Order of Rules

組合規則既靈活又具有彈性, 但在使用時必須留意規則的執行順序, 這將依照以下邏輯進行:

  1. 距離變化欄位的距離 (接近程度), 越近的優先執行
  2. 宣告的順序, 越早宣告的優先執行

讓我們來看幾個例子來說明:

假設我們在組合規則中定義了 @Rule, 如下所示：

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@ReplacePattern(regex="\\r\\n", replacement="\n")
@StringMask(start = 2, end = 7)
@Rule(handledBy = MyComposedRuleHandler.class)
public @interface MyComposedRule {
}

執行的順序將會是:

  1. MyComposedRuleHandler - 距離: 1, 順序: 1
  2. @ReplacePattern - 距離: 2, 順序: 1
  3. @StringMask - 距離: 2, 順序: 2

當組合規則中包含另一組合規則時, 例如:

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@ReplacePattern(regex="\\r\\n", replacement="\n")
@StringMask(start = 2, end = 7)
@Rule(handledBy = MyComposedRuleHandler.class)
public @interface MyComposedRule {
}

@Documented
@Target({ElementType.FIELD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@MyComposedRule
@StringMask(start = 0, end = 3)
@Rule(handledBy = MyComposedRule2Handler.class)
public @interface MyComposedRule2 {
}

使用 @MyComposedRule2 時, 執行順序將是:

  1. MyComposedRule2Handler - 距離: 1, 順序: 1
  2. MyComposedRule.MyComposedRuleHandler - 距離: 2, 順序: 1
  3. @StringMask - 距離: 2, 順序: 2
  4. MyComposedRule.@ReplacePattern - 距離: 3, 順序: 1
  5. MyComposedRule.@StringMask - 距離: 3, 順序: 2

Testing Mutation Rule

要對自定義的變化規則進行測試, 並不需要啟動整個應用程式, 在進行最小範圍的測試時, 你只需針對 RuleHandler 的實作測試即可, 以下是一個範例:

class MyRuleTest {

  @Test
  void testMyRule() {
    var rule = Mockito.mock(MyRule.class);
    // 若需要, 設定更多的 mock 規則
    // 如: Mockito.when(rule.xxx).thenReturn(...);

    var mutated = new MyRuleHandler().apply(rule, "my-input");
    Assertions.assertThat(mutated).isEqualTo("my-expected");
    // 更多的 assertion 驗證
  }
}

Inherited

Mutation 模組支援父類別上的欄位繼承使用

@Data
class SuperClass {

  @MyRule
  private String name;
}

@Data
class SubClass extends SuperClass {
}

然而, 欄位上的註解不會隨欄位一起繼承, 這表示如果子類別重新定義了相同名稱的欄位, 該欄位不會自動繼承父類別的註解

@Data
class SuperClass {

  @MyRule
  private String name;
}

@Data
class SubClass extends SuperClass {

  private String name;
}

如上例所示, SubClass 中的 name 欄位雖然與父類別相同, 但不會受到 @MyRule 註解的影響

Nested

在欄位上使用 @Mutate 註解, Mutation 模組就會進一步的處理該 field 欄位的變化, 支援的類別型態一共有:

  • Map
  • Iterable
  • Array
  • Object

例如:

import tw.com.softleader.kapok.mutation.rule.annotation.StringMask;

@Data
class MyWallet {

  @Mutate
  private List<CreditCard> cards; // 可以是上述任一支援的類別型態
}

@Data
class CreditCard {

  @MyRule
  private String cardNumber;
}

在這個範例中, @Mutate 註解告訴 Mutation 模組要對 cards 欄位進行處理, 而 cards 是一個 List 類型, 符合支援的類別範圍, 因此 List 中每個 CreditCard 物件中的 cardNumber 欄位也都會根據 @MyRule 變化

Mutate Listener

Mutation 模組在處理過程中, 支援了掛載變化過程的監聽器 (MutateListener), 我們預設提供了幫助問題查找的 Logging 監聽器, 以及監控緩慢效能的監聽器, 當然你也可以加入更多自定義的監聽器

Logging Mutate Listener

Logging 監聽器會將欄位值的變化前後, 及其中詳細的步驟等資訊, 預設以物件 package logger 及 trace 等級來輸出, 可以有效的幫助查找問題, 你只需要將變化物件的 logger level 設定到 trace 即可, 如

# application.yml
logging:
  level:
    tw.com.softleader.example.PersonInfo: trace

輸出類似於:

... [main] TRACE tw.com.softleader.example.PersonInfo -- [Mutation] PersonInfo.mobile: [0912345678] -> [09******78] (in 1 steps)
StringMask(maskChar='*', start=2, end=8): [0912345678] -> [09******78] (0 ms)

配過配置 kapok.mutation.logging 下的參數, 可以做更多的 logging 控制:

  • level - 要輸出的 Logger 等級 (Default: trace)
  • impersonate-logger - 是否要偽裝 logger, 若開啟將會用實際的變化 object 的 logger, 反之使用 Mutation 模組的處理這段程式的 logger (Default: true)

例如我想要輸出到 INFO 等級, 則設定範例如下:

# application.yml
kapok:
  mutation:
    logging:
      level: info

Slow Mutate Listener

緩慢效能監聽器負責為效能把關, 在預設情況下, 它會監控物件中的每個欄位, 當發現變化過程中有任一步驟花費超過 500ms, 就會將這些訊息以實際的變化 object 的 logger 輸出到日誌的 WARN 等級中

輸出類似於:

... [main] WARN tw.com.softleader.example.PersonInfo -- [Mutation] PersonInfo.mobile spend 1022 ms in 1 steps, over 500 ms threshold
StringMask(maskChar='*', start=2, end=8): [0912345678] -> [09******78] (1022 ms)

配置 kapok.mutation.slow-step-logging 下的參數, 可以做更多的 logging 控制

  • level - 要輸出的 Logger 等級 (Default: warn)
  • impersonate-logger - 是否要偽裝 logger, 若開啟將會用實際的變化 object 的 logger, 反之使用 Mutation 模組的處理這段程式的 logger (Default: true)
  • threshold - 門檻, 格式為 Duration

例如, 將門檻調整成 1 秒, 範例如下:

# application.yml
kapok:
  mutation:
    slow-step-logging:
      threshold: 1s

Customizing Mutate Listener

你可以實作 MutateListener, 並將之註冊成 Spring Bean, 即可加入更多的客製化監聽器, Mutation 模組會在啟動階段自動的使用之, 以下是程式範例:

@Component
class MyMutateListener implements MutateListener {

  @Override
  public void beforeMutation(Object object, Field field, Object value, Collection<MutateStep> steps) {
    // 在變化前, 加入更多客製化邏輯
  }

  @Override
  public void afterMutation(Object object, Field field, Object value, Collection<MutateStep> steps) {
    // 在變化後, 加入更多客製化邏輯
  }
  
  @Override
  public int getOrder() {
    // 若需要, 可以控制監聽器註冊的順序, 越小越先執行
    return 0;
  }
}

Best Practice

在使用上, 或是實作 Mutation rule 時, 我們建議遵循一些最佳實踐, 可以幫助並確保這些變化規則有高的效率且易於維護

Stateless

確保你的 Mutation rule 是無狀態的, 即規則的實作不應依賴於任何外部狀態, 也不應該維護狀態信息, 用一樣的輸入一定會得到一樣的結果, 無狀態的規則更容易理解和測試

Avoid I/O

避免在 Mutation rule 中進行 I/O 操作, 如: 存取檔案系統, 進行網路請求, 或讀取資料庫等, I/O 操作通常較慢, 並且可能引入不必要的性能瓶頸和複雜性

如果還是必須使用外部數據或服務, 考慮在規則之外先取得這些資訊, 並以參數的方式傳遞給規則

Avoid Engaging Persistence API

應避免物件參與, 或直接使用到 Persistence API, 例如 Hibernate Session 管理之中, 這樣都可能會導致與資料庫的不必要 I/O, 增加效能負擔, 甚至可能導致 Transaction 管理等發生未預期的問題

此外, 依賴於 Hibernate 或其他 Persistence framework API, 一定會增加程式碼的耦合度及複雜度, 必然會降低其可重用性和測試性

6 - Rules

Simplified API to run with rule engine.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-rules</artifactId>
</dependency>

整合規格引擎, 提供更精簡的方式來串接及控制規則引擎

Getting Started

本模組使用 Drools 來實作業務規則管理, 在 pom.xml 中依賴後, 透過 properties 設定 kapok.rules.enabled 來啟動 (預設是 false).

# application.yaml
kapok:
  rules:
    # 啟動規則引擎, 預設是 false
    enabled: true

規則引擎模組在建置規則庫的過程中, 會先載入 DRL 資源, 載入的途徑有很多種, 後續會陸續介紹到, 你可以挑選一種或多種混合使用, DRL 資源載入後會交給 Drools 進行編譯, 這個過程是最花效能跟時間的, 在這個過程中遇到任何問題就會立刻拋出例外.

預設建置規則庫的時間點會在應用程式啟動階段, 也就是若遇到任何問題就會立即中斷應用程式的啟動. 透過 properties 設定 kapok.rules.fast-fail=false 可以延後至第一次使用規則前才建置規則庫 (當然第一次使用時就會比較花時間):

# application.yaml
kapok:
  rules:
    # 立即建置規則庫, 遇到錯誤亦立即中斷, 預設是 true
    fast-fail: false

Caution

使用本模組的應用程式應評估建置規則庫的資源消耗, 視情況調整部署資源或 readiness 等配置.

Setting Up DRL File Locations

透過 properties 設定 kapok.rules.drl-locations 可以來指定一或多個 DRL 路徑, 若指定多組路徑請以逗號 (,) 分隔:

# application.yaml
kapok:
  rules:
    # 設定一或多個 DRL 路徑
    drl-locations: classpath:rules/**/*.drl,classpath:another-rules/**/*.drl

drl-locations 支援 Spring 的 Resource strings 及 Ant-style Patterns, 提供幾個範例如下:

/WEB-INF/*.drl
com/mycompany/**/*.drl
file:C:/some/path/*.drl
classpath:com/mycompany/**/rules/*.drl
classpath*:some/path/**/*.drl

Defining PackageDescr

規則模組也支援 Drools 的 PackageDescr, 將你準備好的 PackageDescr 註冊成 Spring Bean, 規則模組在啟動階段就會自動的載入, 範例如下:

@Configuration
class MyConfig {

  @Bean
  PackageDescr myRule() {
    return DescrFactory.newPackage()
        .name("my.rules")
        .newGlobal().type("org.slf4j.Logger").identifier("log").end()
        .newRule().name("Xyz")
        .lhs()
        .pattern("Applicant").id("$a", false).constraint("age>=18").end()
        .end()
        .rhs("log.info(\"is an adult!\"); $a.setValid(true);")
        .end()
        .getDescr();
  }
}

Customizing KieFileSystem

如果上述載入途徑都不適用, 你可以實作 KieFileSystemCustomizer, 並將之註冊成 Spring Bean, 規則模組在啟動階段會自動的使用之來客製化 KieFileSystem.

例如, 我要把 DRL 文字存放在資料庫中, 資料如下:

insert into my_rule(path, content)
values ('my/rules/abc.drl', 'package my.rules

import tw.com.softleader.kapok.rules.Applicant

global org.slf4j.Logger log

rule "Abc"
when
    $a : Applicant( age>=18 )
then
log.info("is an adult!"); $a.setValid(true);

end');

Persistence 相關的程式有:

@Data
@Entity
@Table(name = "my_rule")
class MyRuleEntity {
  @Id
  @GeneratedValue(strategy = IDENTITY)
  Long id;
  String path;
  String content;
}

@Repository
interface MyRuleRepository extends JpaRepository<MyRuleEntity, Long> {
}

以下為實作範例:

@Component
class MyKieFileSystemCustomizer implements KieFileSystemCustomizer {

  @Autowired MyRuleRepository repository;

  @Override
  public void customize(KieFileSystem kieFileSystem) {
    repository.findAll().stream()
        .map(
            rule -> {
              var resource = ResourceFactory.newByteArrayResource(rule.getContent().getBytes());
              // 設定寫入 KieFileSystem 的檔案完整路徑
              // 路徑建議跟 Rule Content 中的 package 一樣, 檔名須以 '.drl' 副檔名結尾
              // e.g. my/rules/abc.drl
              resource.setTargetPath(rule.getPath());
              return resource;
            })
        .forEach(kieFileSystem::write);
  }
}

Validating DRL

如果你有完整的 DRL 內容, 且想要透過程式來驗證編譯是否正確, 可以利用 KieHelper 來測試, 這個測試不用啟動 Spring, 例如:

class ValidatingDrlTest {

  @Test
  void testCompile() {
    var results =
        new KieHelper()
            .addContent(
                """
            package my.rules
            rule "MyRule"
            when
            then
            end
            """,
                "my-test-rule.drl")
            .verify();
    Assertions.assertThat(results.hasMessages(Message.Level.ERROR)).isFalse();
  }
}

若你的想要測試透過 DRL Locations, PackageDescr, 或 KieFileSystemCustomizer 定義好的 Rules, 則可使用 KieContainerBuildPlan 來驗證編譯是否正確, 這個測試就必須啟動 Spring, 例如:

@SpringBootTest
class ValidatingDrlTest {

  @Autowired DrlLocationsCustomizer drlLocationsLoader;

  @Autowired PackageDescrsCustomizer packageDescrsLoader;

  @Autowired KieFileSystemCustomizer myRuleLoader;

  @Test
  void testCompile() {
    var buildPlan =
        KieContainerBuildPlan.builder()
            .kfsCustomizer(drlLocationsLoader) // 核心的 DRL Locations 載入器, 需要驗證才放
            .kfsCustomizer(packageDescrsLoader) // 核心的 PackageDescr 載入器, 需要驗證才放
            .kfsCustomizer(myRuleLoader) // 自定義的載入器
            .build();
    var results = buildPlan.verify();
    Assertions.assertThat(results.hasMessages(Message.Level.ERROR)).isFalse();
  }
}

var session = kieOperations.newStatelessKieSession();

session.execute(collection);

更多 StatelessKieSession 的說明請參考官方文件

Configuring Logging Event Listeners

透過 kieOperations.newStatelessKieSession() 建構的 Session, 預設已經註冊好了以下 Logging Event Listener 幫助問題查找

  • LoggingAgendaEventListener - 將 agent 相關的 event 印出, 預設 INFO
  • LoggingProcessEventListener - 將 process 相關 event 印出, 預設 OFF
  • LoggingRuleRuntimeEventListener - 將 rule runtime 相關 event 印出, 預設 OFF

透過 properties 的 kapok.rules.event-listener.logger-level.* 下的參數, 可以控制各個 listener 所印出的等級:

  • agenda - 控制 LoggingAgendaEventListener 印出的等級
  • process - 控制 LoggingProcessEventListener 印出的等級
  • rule-runtime - 控制 LoggingRuleRuntimeEventListener 印出的等級

例如, 我想將所有 event 都在印 warn, 則設定如下:

# application.yaml
kapok:
  rules:
    event-listener:
      logger-level:
        agenda: warn
        process: warn
        rule-runtime: warn

Important

這是改變印出的等級, 仍需要應用程式的 logging level 配合設定

更多 Event Listener 的說明請參考官方文件

Refreshing KieOperations

透過 kieOperations.refresh() 可以立即重新建構規則庫, 也就是所有的規則都會被重新載入且進行編譯:

try {
  kieOperations.refresh();
} catch (Exception e) {
  // handling errors properly...
}

Customizing KieOperations Refreshing

refresh() 的主要目的是重新建構底層的 KieContainer, 這是用來建立執行規則所需的 StatelessKieSession, 整個過程中包含多個步驟, 規則模組提供了一些介面, 允許在特定階段進行自訂調整, 介面及執行順序如下:

  1. KieFileSystemPostProcessor - 在 KieFileSystem 物件被建立前後調整 (此階段用於載入規則)
  2. KieBuilderPostProcessor - 在 KieBuilder 物件被建立前後調整 (此階段用於編譯規則)
  3. KieContainerPostProcessor - 在 KieContainer 物件被建立前後調整

將自訂的處理邏輯註冊為 Spring Bean, 規則模組在啟動時會自動載入, 例如, 想在建立 KieContainer 之前設定更多的系統參數, 範例如下:

@Component
class MyConfigKieContainerPostProcessor implements KieContainerPostProcessor {

  @Override
  public void postProcessBeforeKieContainerCreation(
      KieServices kieServices, KieFileSystem kieFileSystem, KieBuilder kieBuilder) {
    System.setProperty("drools.dateformat", "yyyy-MM-dd HH:mm:ss");
  }
}

Fluent API

本模組提供了一系列容易易懂的操作方式, 來幫助工程師設定並執行 Rule 檢查以取得結果!

透過 kieOperations.rules() 可以開始進行 Fluent API 操作, 這是建構在 kieOperations.newStatelessKieSession() 之上的, 換言之, Fluent API 提供的容易易懂的操作方式是在幫助工程師設定 StatelessKieSession 並執行之!

Fluent API 語意大致為:

rules
  .that(). ...
  .with(). ...
  .fire();
  • that() - 設定過濾條件, 只能設定一次, 預設沒有設定, 即全部執行 (選填)
  • with() - 配置 Runtime 環境, 可設定一或多次, 例如: 變數, 監聽器等 (必填)
  • fire() - 啟動點, 執行規則並返回結果

Firing All Rule

我們直接以例子來說明: 有一個駕照檢查規則 (DRL), 會檢查申請人 (Applicant) 的年齡是否能夠申請, 在本次執行檢查中, 我們沒有要過濾任何條件!

首先, Applicant 物件中有兩個欄位:

@Data
@Builder
public class Applicant {

  int age; // 申請人年齡
  boolean valid; // 是否能申請
}

接著我們會在 DRL (driver-license.drl) 中撰寫規則, 並將結果放回申請人物件:

package examples.rules;

import examples.rules.Applicant;

rule "Is valid age"
when
  $a : Applicant(age >= 18)
then
  $a.setValid(true);
end

rule "Too young to drive car"
when
  $a : Applicant(age < 18)
then
  $a.setValid(false);
end

接的我們透過 Fluent API 進行規則檢查, 執行完後, 原申請人物件中的 valid 將會被改成 true

var applicant = Applicant.builder().age(18).build();

kieOperations.rules()
        .with().fact(applicant)
        .fire();

// applicant.isValid() should be true!

Rule Filtering

透過 rules().that()... 可以過濾要執行的規則, Fluent API 中已經提供了以下角度的過濾條件:

  • haveRuleName...(..) - 判斷 DRL 中 Rule Name
  • resideIn...(..) - 判斷 DRL 中 Rule Package, 支援 Ant Path Matching Pattern

例如, 本次我只想要執行 DRL 中, Rule Name 是 policy- 開頭的規則:

kieOperations
        .rules().that().haveRuleNameStartingWith("policy-")
        .with().fact(applicant)
        .fire();

另外一個例子, 我想要執行 DRL 中 Rule Package 宣告符合 tw.com.**.policy.** 的規則:

kieOperations
        .rules().that().resideInPackage("tw.com.**.policy.**")
        .with().fact(applicant)
        .fire();

Important

規則過濾底層是橋接 Drools 的 AgendaFilter, 依照其官方文件的說明, 執行的順序是: 先找到 match rules -> 進行過濾 -> 執行 rule

因此所有 DRL 中的 when 區塊都一定會執行的, 請務必確保所有 DRL when 中的條件都不可以丟出任何 Exception, 常見例如: 缺少某些 Factor 物件還繼續操作就爆出 NPE

Customizing Rule Filters

如果上述都不適用, 你可以實作自己的RulePredicate (過濾器), 這是一個在 Drools 的 AgendaFilter 之上又提供了更多控制的過濾器介面, 工程師完全可參考 AgendaFilter 的官方的說明來撰寫實作, 然後將之傳入 rules().that(filter)... 來過濾.

例如, 我這次只想要執行在 Rule Condition (when) 中有用到 Applicant 物件的規則, 則程式範例如下:

kieOperations
        .rules().that(this::useApplicantInRuleCondition)
        .with().fact(applicant)
        .fire();
        
boolean useApplicantInRuleCondition(org.kie.api.runtime.rule.Match match) {
  return match.getObjects().stream().anyMatch(Applicant.class::isInstance);
}

Compound Rule Filters

透過自定義過濾器還可以組合多組過濾條件, 並定義要用 or, and 或 not 等來串接, 建議可以從 RulesThat.Predicates 開始使用 API!

例如, 我想要執行 Rule Package 符合 tw.com.**.policy.** 且 Rule Name 結尾不為 -tmp 的規則, 則設定範例如下:

// 推薦 import static 以取得最佳閱讀體驗
import static tw.com.softleader.kapok.rules.lang.RulesThat.Predicates.*;

kieOperations
    .rules().that(
      resideInPackage("tw.com.**.policy.**")
        .and(haveRuleNameNotEndingWith("-tmp"))
    )
    .with().fact(applicant)
    .fire();

Configure Runtime

透過 rules().with()... 可以配置 Runtime 環境, 例如設定全域變數, 因子等, Runtime 變數是可以設定一到多組的, 透過 .and() 可以繼續下一個設定, 例如:

kieOperations.rules()
        .with().var("moneyUtil", moneyUtil)
        .and().fact(applicant)
        .and().fact(policy)
        .fire();

常見的設定如下:

  • .with().var() - 設定 Global Variables (全域變數)
  • .with().fact() - 設定 Factor (因子)
  • .with().listener() - 設定 Event Listener (監聽器)

Predefined Global Variables

以下事先定義好的 ID 及全域變數, 會固定在執行規則前放入全域變數 (Global Vars) 中, 當然如果你已經指定相同 ID 的全域變數則會優先使用

org.slf4j.Logger log

為了讓工程師在 DRL 中可以透過 slf4j 的 logger 印出資訊, 在執行規則前會固定放入一個 ID 為 log, 物件為 org.slf4j.Logger 的全域變數, 如:

package examples.rules;

import examples.rules.Applicant;

global org.slf4j.Logger log;

rule "Too young to drive!"
when
  $a : Applicant(age < 6)
then
  log.info("You're too young to drive car!");
  $a.setValid(false);
end

這個 log 的 package 會在 tw.com.kapok.rules 下, 如果你想要換成執行程式的 package, 則可以透過 .with().slf4j() 設定 Logger, 如:

class ValidationService {

  ...
  
  void validate(Applicant applicant) {
    kieOperations
          .rules()
          .with().slf4j(ValidationService.class) // 在 DRL 中就會以 ValidationService 的 logger 來印
          .and().fact(applicant)
          .fire();
  }
}

java.util.List results

為了方便工程師在 DRL 中可以產生並帶更多資訊回 Java 端, 在執行規則前會固定放入一個 ID 為 results, 物件為 java.utils.List 的全域變數, 這個 list 的泛型型態 (Generic Type) 完全由工程師撰寫 DRL 時決定, 當然透過 Fluent API 時啟動 Rule 也必須指定一樣的泛型型態.

Tip

建議一個應用程式定義一個適用於自己的 Results 的 Generic Type 即可, 過多種的 Generic Type 會影響使用體驗.

如 Policy App 可以定一個 PolicyResult 的 Generic Type, Product App 也可以定一個 ProductResult 的 Generic Type, 當然 Policy 跟 Product 的不用相同.

假設我有一個 DownstreamEvent 的 Generic Type, 範例如下:

public record DownstreamEvent(String event, String message) {
}

在 DRL 中我可以在需要的 then 區塊放入 results

package examples.rules;

import examples.rules.Applicant;
import examples.rules.DownstreamEvent;

global java.util.List results;

rule "Too young to drive!"
when
  $a : Applicant(age < 6)
then
  results.add(new DownstreamEvent("send_email", "Too young to drive car!"));
  $a.setValid(false);
end

在 Java 端就可以透過 .fire() 執行規則並取得結果:

var results = kieOperations
    .rules()
    .and().fact(applicant)
    .fire(DownstreamEvent.class); // 指定泛型型態, 若沒指定則為 List of Object
    
// handle downstream from results here...

Testing

在執行單元測試時, 規則引擎模組預設是關閉的, 關閉的狀態下本模組仍會建立一個空殼 KieOperations 給 Spring, 因此程式上任何透過 Spring 注入了 KieOperations 的地方都不會出錯! 有了這個機制, 你可以放心選擇要最小化規則載入還是關閉並 Mock 規則引擎兩個做法來實作 Test Class

Optimizing Rule Loading for Tests

當測試的內容包含了使用 KieOperations 的區段, 且我們也需要真的去執行規則時, 請先確保規則引擎是啟動的, 並務必將 drl-locations 在該 Test Class 中設定最小化設的範圍, 如:

@SpringBootTest({
  "kapok.rules.enabled=true",
  "kapok.rules.drl-locations=classpath:only-relate-to-current-test/**/*.drl",
})
class MyUnitTest {
}

Important

不推薦在測試中不論有沒有用到, 一次就將全部的規則都載入, 這樣會讓測試啟動速度大受影響

Mocking KieExecutor

如果測試的內容包含了使用 KieOperations 的區段, 且我們不關注規則的執行, 只想測試執行以後的邏輯段, 則該 Test Class 中是不需要啟動規則引擎的! 要注意的是關閉規則引擎後, 空殼 KieOperations 若真的被執行了就會拋出 UnsupportedOperationException, 畢竟規則引擎都沒啟動怎麼能夠執行呢!

在 KieOperations 底層會調用 KieExecutor 來執行規則, 因此我們需要將 KieExecutor mock 掉, 並指定預期的結果.

範例程式碼如下:

@SpringBootTest({
  "kapok.rules.enabled=false"
})
class MyUnitTest {

  @SpyBean
  KieOperations kieOperations;

  @Test
  void myTest() {
    List<MyResultType> expectedResults = ... // 預期 Rule 執行完的結果
    var executor = Mockito.mock(KieExecutor.class);
    Mockito.when(executor.fire()).thenReturn(expectedResults);
    Mockito.doReturn(executor).when(kieOperations).newKieExecutor();

    kieOperations
      .<MyResultType> rules()
      ...
  }
}

透過以上設定, 有用到 KieOperations 區段的程式碼不會真的執行規則引擎, 就可以如期拿到 expectedResults, 進行後續原本的邏輯處理!

Secure the web endpoints with authorizations.
<dependency>
  <groupId>tw.com.softleader.kapok</groupId>
  <artifactId>kapok-security</artifactId>
</dependency>

對暴露的 endpoints 進行認證與授權等安全管控, 並深度整合分散式服務架構下的跨服務安全控制

Getting Started

只要在 pom.xml 中放入 Security 依賴, 就會自動的啟動及配置 Kapok Security 擴充模組, 這基於 Spring Security 之上所設計的, 因此程式中我們仍一樣使用熟悉的 Spring Security API, 如:

取得登入資訊:

var currentUser = (UserDetails) SecurityContextHolder.getContext()
      .getAuthentication()
      .getPrincipal();

取得 Token:

var token = (String) SecurityContextHolder.getContext()
      .getAuthentication()
      .getCredentials();

取得授權:

var authorities = SecurityContextHolder.getContext()
      .getAuthentication()
      .getAuthorities();

或是限制存取:

@RestController
@PreAuthorize("hasRole('ADMIN') or hasAuthority('MOCK')")
class ProtectedResource {
}

Configuring Security Settings

透過 properties 中的 kapok.security.enabled 可以控制 Security 擴充模組的開關, 這設定預設是啟用的, 但在執行單元測試 (Unit Testing) 時會自動的關閉, 如要關閉安控範例如下:

# application.yml
kapok:
  security:
    enabled: false

Important

關閉 Security 擴充模組, 並不是關閉 Spring Security, 而是切換成匿名存取模式

Anonymous User Access

關閉 Security 擴充模組, 或存取忽略清單中的資源時, 若有收到 Token 也會試著解析及登入; 若無收到 Token 或解析登入失敗時, 會切換成匿名 (anonymous) 存取模式登入, 流程類似於:

      +----------------------------------+
------>  Authentication & Authorization  +-----------+
      +--------------+-------------------+           |
                     |                       +-------v---------+
                     | switch if failed      |  Access Control +----->
                     |                       +-------^---------+
            +--------v---------+                     |
            |  Anonymous User  +---------------------+
            +------------------+

匿名資訊可設訂於 properties 中:

  • kapok.security.anonymous.user: 匿名使用者名稱, 預設 anonymous
  • kapok.security.anonymous.groups: 匿名使用者群組, 可以逗號 (,) 分隔多組

範例:

# application.yml
kapok:
  security:
    anonymous:
      user: matt

使用匿名 (anonymous) 登入後, 匿名的資訊也會往後傳播, 後續的 Access Control 流程就如同一般正常的登入流程

Ignoring Paths

有些資源如果不需要被保護, 如: /resources/**, /static/** 等, 可以透過設定 properties 中的 kapok.security.ignoring 來將這些 APIs 加入忽略清單, Security 擴充模組在啟動期間會將忽略清單中的配置從 Spring Security 中忽略.

Note

忽略清單並非繞過 Spring Security, 而是先嘗試解析 Token 或使用匿名登入

在程式中從 Spring Security 取得當前使用者的資訊將會是:

  • 若有傳送 Token 資訊且解析成功, 將取得 Token 的解析結果
  • 若沒有傳送 Token 資訊, 或解析 Token 失敗, 將取得匿名資訊
// in ignoring resources
SecurityContextHolder.getContext().getAuthentication() // will return user or anonymous depends on the request token

忽略清單可以設定多組, 每組可包含了以下欄位:

  • method: 設定 HTTP method, 可選, 若不設則適用於所有 HTTP method
  • paths: 設定一到多組 path

如: 假設要設定忽略網址為 GET /swagger-ui.html, /swagger-ui 及 /swagger-ui/** 的所有請求, 則設定範例為:

# application.yml
kapok:
  security:
    ignoring:
      - method: GET
        paths:
          - /swagger-ui.html
      - paths:
          - /swagger-ui
          - /swagger-ui/**

Customizing Ignoring Paths

若有些要乎略的資源無法事先決定, 必須要在 runtime 透過程式判斷的, 則可以透過實作 SecurityIgnoringCustomizer, 並在將其註冊成 Spring Bean, 就可以讓 Security 擴充模組在啟動期間動態的進行配置

如: 想要將 SpringDoc 的 OpenAPI 的網址加入忽略清單, 而 OpenAPI Path 是設定在 properties 中可以調整的, 因此我們必須要透過程式在啟動階段才能取得當下的 Path 設定.

程式範例:

@Component
@RequiredArgsConstructor
@ConditionalOnBean(SpringDocConfigProperties.class)
class SpringDocConfigIgnoringCustomizer implements SecurityIgnoringCustomizer {

  final SpringDocConfigProperties properties;

  @Override
  public void customize(@NonNull Collection<Ignoring> ignoring) {
    if (!properties.getApiDocs().isEnabled()) {
      return;
    }
    ignoring.add(
      Ignoring.builder()
        .path(properties.getApiDocs().getPath())
        .path(UriComponentsBuilder
          .fromPath(properties.getApiDocs().getPath()).path("/**")
          .build().toUriString())
        .build());
  }
}

Security 擴充模組已自帶了多個常見的 SecurityIgnoringCustomizer 實作, 請點這裡查看更多

Authentication

啟動 Security 擴充模組後, 對任何對被保護的 APIs 發動請求就都需要認證且通過, 否則將進入 Reject Access 流程

Strategies

Security 擴充模組支援以下幾種認證方式, 擇其一即可:

Bearer Token

第一種方式是透過在 HTTP 請求放入 Token, 我們遵循 RFC 6750 - Section 2: Authenticated Requests 標準, 支援了兩種傳送方式:

  • Request Header: 呼叫端將 Token 放在 Authorization 的 HTTP Header 中, 其格式為 Bearer THETOKEN (若有傳送, 將優先使用)
  • Request Parameter: 呼叫端將 Token 放在名為 access_token 的 Parameter 中

Tip

依據 RFC 6750 的建議, 請優先考慮 Header 傳送方式

如: 假設 Token 為 31ada4fd-adec-460c-809a-9e56ceb75269, 則其出現在 HTTP Header 將為:

Authorization: Bearer 31ada4fd-adec-460c-809a-9e56ceb75269

完整的 HTTP 請求範例如下:

curl -X 'GET' \
  'http://localhost:8080/security/authentication' \
  -H 'accept: */*' \
  -H 'Authorization: Bearer 31ada4fd-adec-460c-809a-9e56ceb75269'

或放在 Parameter 的請求範例如下:

curl -X 'GET' \
  'http://localhost:8080/security/authentication?access_token=31ada4fd-adec-460c-809a-9e56ceb75269' \
  -H 'accept: */*'

在 Security 擴充模組收到 Token 後, 會委託 Token Introspection 進行解析, 並取得 Token 解析後的使用者資訊, 接著會再綁定對應的權限, 便成功登入系統!

User Impersonation

HTTP 請求可以通過偽裝 (Impersonation header) 來以另一個使用者的身份執行操作, 以下 HTTP Header 可以用來執行偽裝請求:

  • Impersonate-User: 要偽裝成的使用者名稱 (必填)
  • Impersonate-Group: 要偽裝成的使用者群組, 可用多個 Group Header 傳送, 或用一個 Group Header 以逗號 (,) 分隔傳送, 亦可混用 (必填)

完整的 HTTP 請求範例如下:

curl -X 'GET' \
  'http://localhost:8080/security/authentication' \
  -H 'accept: */*' \
  -H 'Impersonate-User: matt' \
  -H 'Impersonate-Group: admin,developer' \
  -H 'Impersonate-Group: guest'

偽裝設計的主要目的是提供給信任的但無法使用 Token 的請求, 如: 排程, 客戶既有系統介接, 或 Debug 使用等, 預設是關閉的, 若開啟偽裝請務必認知到這是有安控風險的, 畢竟這就可以繞過 Token 的驗證!

你可以透過 properties kapok.security.auth.impersonation.enabled 來開啟偽裝, 如:

# application.yml
kapok:
  security:
    auth:
      impersonation:
        enabled: true

Token Introspection

在 Security 擴充模組中, 將解析 Token 並轉換成登入資訊的這段邏輯, 給予一個抽象的定義: Token Introspection, 並支援了以下多種方式, 擇其一即可:

OpenID Connect

OpenID Connect (簡稱 ODIC) 是基於 OAuth2 的認證方式, 被許多 OAuth2 的提供方支援, 如 Google, Azure 等, Security 擴充模組支援了 OIDC 的 Token 驗證 (非串接 OIDC Flow), 透過驗證及解析 ID Token (或 Access Token) 來取得使用者資訊.

在 properties 設定 kapok.security.auth.oidc.enabled 來啟用 ODIC 的整合, 一個最基礎的設定範例如下:

# application.yml
kapok:
  security:
    auth:
      oidc:
        enabled: true
        issuer-url: "https://my.issuer.url"
        client-id: "my-client-id"

透過配置 kapok.security.auth.oidc 下的參數可以做更多的控制:

  • enabled: 是否啟用 OIDC 的 Token 驗證機制 (Default: false)
  • issuer-url: OpenID 的 Configuration Information 網址, 不包含 /.well-known/openid-configuration 路徑
  • client-id: Issuer 開的 Token 所使用的 ClientID
  • username-claim: JWT claim to use as the username. (Default: sub)
  • username-prefix: Prefix prepended to username claims to prevent clashes with existing name
  • groups-claim: JWT claim to use as the user’s group. (Default: groups)
  • groups-prefix: Prefix prepended to group claims to prevent clashes with existing names
  • reject-if-missing-groups-claim: 當 Token 中沒有 groups-claim 時是否要踢退, 若 false 則以 空的授權 登入, 此設定不影響 Token 有 groups-claim 但為空的情境 (Default: false)
  • required-claims: 指定更多的 JWT claim 驗證, 結構為 "claim": "claim value" (僅支援 string 類型的 claim value), 可設定多組以 and 串接且 case-sensitive 的比對
  • skip-issuer-check: 是否要忽略 Token 的 Issuer 檢查 (Default: false)
  • skip-client-id-check: 是否要忽略 Token 的 Client ID 檢查 (Default: false)
  • skip-expiry-check: 是否要忽略 Token 的 Expiry 及 Not Before 檢查 (Default: false)
  • accept-leeway: 檢查 Token 的 Not Before 時所容忍的時間差 (Default: PT5M)
  • skip-signature-check: 是否要忽略 Token 的 Signature 檢查, 如果設置了 provider.insecure-issuer-url=true, 則此驗證將被固定忽略 (Default: false)
  • provider.cache: 是否要快取 Provider 提供的 KeySets (Default: true)
  • provider.keys-cache-expire-after-write: Provider 提供的 KeySets 要快取多久 (Default: PT24H)
  • provider.keys-cache-size: Provider 提供的 KeySets 要快多少個 (Default: 10)
  • provider.connect-timeout: 連線到 Provider 的 connectionTimeout (Default: PT3S)
  • provider.read-timeout: 連線到 Provider 的 readTimeout (Default: PT3S)
  • provider.insecure-issuer-url: Provider 網址是否要忽略憑證驗證 (Default: false)
  • provider.skip-issuer-validation: 是否要忽略 Provider 中的 Issuer 名稱檢查 (Default: false)
  • provider.fail-fast: 若為 ture 會在啟動階段就試著對 Provider 連線, 若發生錯誤就中斷啟動; 若為 false 則會延後到被呼叫時才會連線 (Default: false)

Provider 是封裝 OIDC Server 端配置的一個抽象概念

以下提供幾個設定範例:

情境一:

  • 串接由 Keycloak 提供的 OIDC 協議
  • 限定只能接收 ID Token
  • 將 groups 視為 Spring 的角色:
# application.yml
kapok:
  security:
    auth:
      oidc:
        enabled: true
        issuer-url: "https://my.keycloak.url/realms/my-realms"
        client-id: "my-client-id"
        # 以 Keycloak 所提供的 preferred_username 視為 username
        username-claim: "preferred_username"
        # 將所收到的 groups 轉換成 Spring 的角色規則
        groups-prefix: "ROLE_"
        required-claims:
          # 限定只能接收 ID Token
          "typ": "ID"

情境二, 我要連線的 issuer 為自簽憑證:

# application.yml
kapok:
  security:
    auth:
      oidc:
        enabled: true
        issuer-url: "https://my.self-signed.url"
        client-id: "my-client-id"
        provider:
          insecure-issuer-url: true

Webhook

Security 擴充模組會透過 Webook 將 Token 委託給指定 API 來處理並取得使用者資訊. 這種情境適用於解析 Token 的邏輯是由第三方服務所提供, 如: 有個共用的安控服務, 負責提供 Webhook 的實作及串接客戶公司的 SSO 流程

Webhook 是透過 HTTP 調用, 其 OAS 3.0 規格如下:

paths:
  /token/introspect:
    post:
      requestBody:
        content:
          application/json:
            schema:
              type: string
        required: true
      responses:
        "200":
          content:
            '*/*':
              schema:
                type: object
                properties:
                 username:  # 使用者名稱
                   type: string
                 active:  # 使用者是否啟用
                   type: boolean
                 groups:  # 使用者群組 (授權資訊)
                   type: array
                   items:
                     type: string

規範實作可參考 tw.com.softleader.kapok.security.auth.IntrospectionApi

Webhook 的網址需設定在 properties 中 kapok.security.auth.url, 如:

# application.yml
kapok:
  security:
    auth:
      url: http://auth-server:8080

Customizing Introspection

在某些特定情境下, 上述可能都不適用, 例如: 自己服務就提供了認證 Token 的邏輯, 在這種情況下, 你可以通過實作以下其中一個介面來提供解析 Token 的邏輯, 並將其註冊為 @Spring Bean, 讓 Security 擴充模組進行配置.

  • tw.com.softleader.kapok.security.auth.TokenIntrospection - 完全客製化
  • tw.com.softleader.kapok.security.auth.IntrospectionApi - 適合於實作 Webhook Server 端的情境, 它也是一個 TokenIntrospection, 但增加了 Webhook 中定義的 OAS 規格

程式範例如下:

@Slf4j
@Service // 也可以是 @RestController, 只要註冊成 Spring Bean 即可生效
class TokenService implements TokenIntrospection {

  @Override
  public TokenMeta introspect(@NonNull String token) {
    // 實作自己的 Token 解析邏輯
    // 依照上述範例 Token 會是 31ada4fd-adec-460c-809a-9e56ceb75269
    return TokenInfo.builder()
      .active(true)
      .username("hello")
      ...
      .build();
  }
}

Note

若註冊了 TokenIntrospection 會最高優先的配置, 前述的所有其他方法將不再適用

In-Memory Token

若沒有配置上述任何一種解析 Token 的模式, 安控模組會自動的產生一組隨機的 Token 儲存在記憶體, 並在啟動應用程式時輸出在 Console 中

這組 Token 對應的使用者資訊可以透過 properties 的 kapok.security.user 下的參數來設定:

  • name: 使用者名稱, 預設 user
  • groups: 使用者群組, 預設空, 可設定多筆或以逗號 (,) 分隔

例如, 我想設定使用者名稱為 admin, 群組為 USER 及 ADMIN, 範例如下:

# application.yml
kapok:
  security:

Handling Hailure

所有認證失敗的請求, 除了 Ignoring Paths 的清單外, 預設都會 log 輸出作紀錄, 透過 kapok.security.auth.failure.logging.* 可以微調:

  • level: 要輸出的 log 等級 (Default: error)
  • short-summary: 是否只輸出概要訊息, 若否會印完整的 stacktrace (Default: true)

若我想關閉認證失敗的 log, 範例如下:

# application.yml
kapok:
  security:
    auth:
      failure:
        logging: 
          level: off

若你想要完全的客製化, 可以透過實作 AuthenticationFailureHandler 並註冊成 Spring Bean 即可生效, 如:

@Component
public class MyAuthenticationFailureHandler implements AuthenticationFailureHandler {

  @Override
  public void onAuthenticationFailure(HttpServletRequest request, HttpServletResponse response,
      AuthenticationException exception) {

}

Binding Authorities

此階段負責對使用者進行授權綁定, 除了 Token Introspection 所解析的權限之外, Security 擴充模組還進一步支援 App 層級的授權綁定, 這意味著你可以對所提供的權限進行更廣泛的解釋, 並添加專屬於自己應用程式的權限, 最終授權將是 Provider 提供的再加上 App 層級的授權, 兩者進行聯集並排除重複

App level Binding

App 層級的權限是以 Role-based 的方式授權控制 (RBAC), 透過 properties 的 kapok.security.auth.rbac 下的參數來設定授權綁定 (以下都是區分大小寫的比對):

  • enabled: 是否啟用 RBAC 的授權綁定, 預設: true
  • roles: 定義 role, 及其所綁定的 permissions, Key: role, Value: permissions (以逗號分隔一至多個)
  • role-prefix: 設定 role 在授權綁定時的前綴字眼 (Default: ROLE_)
  • rules.usernames: 設定 role 所對應 usernames 的規則, Key: role, Value: usernames (以逗號分隔一至多個)
  • rules.groups: 設定 role 所對應 groups 的規則, Key: role, Value: groups (以逗號分隔一至多個)

一個設定範例如下:

# application.yml
kapok:
  security:
    auth:
      rbac:
        roles:
          "god: "world-creator, world-dropper"
          "gm": "game-master"
          "traveller": "farming"
        role-prefix: "ROLE_"
        rules:
          groups:
            "god": "superuser, boss"
            "gm": "superuser"

在這範例中, 假設從 Token 解析出來的 groups 包含了 superuser, 登入後就有以下 Authorities

var authorities = SecurityContextHolder.getContext()
      .getAuthentication()
      .getAuthorities();

// Authorities 會包含:
// superuser (原本的 groups)
// ROLE_god, ROLE_gm (以 gorups 對應的 roles, 加上 prefix)
// world-creator, world-dropper, game-master (以 roles 對應的 permissions)

程式中的使用範例如下:

@PreAuthorize("hasRole('god') or hasAuthority('game-master')")

Customizing Binding

如果你想要以程式的控制更多的 RBAC 權限綁定邏輯, 可以透過實作 RuleBinding 並註冊成 Spring Bean 來生效, RuleBinding 負責將 Subject (授權對象) 與多個 BindRule (綁定規則) 關聯起來, 需要注意的是, 這隻程式會在每次驗證 Token 時被呼叫，因此需要特別注意實作上的效能表現

@Component
class MyRuleBinding implements RuleBinding {

  @Override
  public Collection<BindRule> bind(@NonNull Subject subject) {
    // 綁定 Subject 與 BindRule 集合
    // Subject 授權對象, 包含了 Token 解析出來的 username, groups 等資料
    // BindRule 綁定規則, 包含了授權相關的資料, 如: role, permissions 等
  }
}

Authorization

在 Authentication 階段中, 我們已經完成了對使用者所擁有權限的綁定, 這些權限可以透過 Spring 的 API 取得, 例如:

// Authorities 將會包含從 Provider 解析的 groups 欄位, 以及 App 層級的授權
var authorities = SecurityContextHolder.getContext()
      .getAuthentication()
      .getAuthorities();

接下來, 我們將依據使用者所擁有的權限, 執行一系列的存取規則驗證, 核心所提供的授權概念是, 只要使用者符合任何一項, 就可以進行接下來的行為邏輯, 透過 properties 中的 kapok.security.access.enabled 可以控制這些存取規則的開關, 預設是啟用的, 如要關閉則:

# application.yml
kapok:
  security:
    access:
      enabled: false

Important

關閉存取控制並非不允許存取, 而是不驗證存取控制直接允許通過

閱讀 Access - Matrix 章節以了解所有驗證規則設定的交叉組合結果

Builtin ACL

Security 擴充模組包含了一個內建 ACL 機制, 擴充了 hasPermission(...), 透過 properties 中的 kapok.security.access.acl.enabled 可以控制開關, 預設是啟用的, 如要關閉則:

# application.yml
kapok:
  security:
    access:
      acl:
        enabled: false

Fallback Strategy

若你關閉內建 ACL, Security 擴充模組會參考 properties 中的 kapok.security.access.acl.fallback-strategy 的設定決定要退回什麼模式:

  • PERMIT_ALL - 允許全部模式 (預設)
  • NATIVE - 使用 Spring 原生的預設判斷模式

預設是退回允許全部模式 , 如要改成 Spring 原生的判斷模式, 則範例如下:

# application.yml
kapok:
  security:
    access:
      acl:
        enabled: false
  #      fallback-strategy: PERMIT_ALL # 內建 ACL 的預設
        fallback-strategy: NATIVE # Spring 原生的預設

Note

Spring Boot 原生模式是 deny all, 未來版本都有可能會有異動, 使用原生模式前請先確認好該版本的 Spring Boot 邏輯是否符合需求

Current Principal’s Authorities

在內建 ACL 的實作中, hasPermission(TARGET, PERMISSION) 會以當前登入者作為目標, 檢查 Authentication.getAuthorities() 是否符合要求.

內建 ACL 實作在比對時, 會先將傳入 hasPermission 的參數以 _ 組合為 TARGET_PERMISSION, 再去跟所有 Authorities 做比對, 若任一 Authoritiy 比對成功則視為符合權限!

預設所有的比對都是區分大小寫的! 透過設定 kapok.security.access.acl.case-sensitive=false 可以調整成不區分大小寫!

透過設定 kapok.security.access.acl.strategy 可以指定比對模式, 支援的比對模式有:

  • ANT - Ant 比對模式, 此種模式下支援各種萬用字元 (預設)
  • FUZZY - 模糊比對模式, 使用 StartingWith 及 EndingWith 作為邏輯判斷

例如我想要調整為模糊比對模式, 則範例如下:

# application.yml
kapok:
  security:
    access:
      acl:
        strategy: FUZZY

PERMISSION 也支援了 * 視為允許全部, 或以 , 分隔傳入多筆, 透過 kapok.security.access.acl.permission-delimiter 可以調整分隔符號, 例如我想要調整為 . 範例如下:

# application.yml
kapok:
  security:
    access:
      acl:
        permission-delimiter: .

Customizing Access Control

如果你想要客製化自己的 hasPermission(...) 邏輯, 只需要實作 PermissionEvaluator 並在將其註冊成 Spring Bean 即可, 這個模式下還可以享有部分核心邏輯, 例如關閉 access 則退回 Fallback Strategy 設定等

配置範例如下:

@Component
class MyPermissionEvaluator implements PermissionEvaluator {

  @Override

  }

  @Override
  public boolean hasPermission(

  }

如果你想要完整的接手, 如使用 Spring Security ACL, 則需要配置 MethodSecurityExpressionHandler 並在將其註冊成 Spring Bean , 這個模式下此章節的所有設定或機制都會無效

Access Annotations

Security 擴充模組內建了多種存取控制的 Annotations, 方便你在 method 或 class 上標註:

  • @HasRole - 對應 @PreAuthorize("hasRole('...')")
  • @HasAnyRole - 對應 @PreAuthorize("hasAnyRole('...')")
  • @HasGroup - 對應 @PreAuthorize("hasAuthority('...')")
  • @HasAnyGroup - 對應 @PreAuthorize("hasAnyAuthority('...')")
  • @HasPermit - 對應 @PreAuthorize("hasPermission('...', '...')")

例如, 使用 @PreAuthorize 的寫法如下:

@PreAuthorize("hasRole('admin')")
void forAdmin() {}

@PreAuthorize("hasAnyAuthority('boss', 'gm')")
void forBoss() {}

@PreAuthorize("hasPermission('maintainer:*', 'read,write')")
void forMaintainer() {}

如果改用 annotation 來寫, 範例如下：

@HasRole("admin")
void forAdmin() {}

@HasAnyGroup({"boss", "gm"})
void forBoss() {}

@HasPermit(
    value = "maintainer:*",
    permits = {"read", "write"})
void forMaintainer() {}

Access within Distributed Traces

在預設的模式中, 任何綁上 @PreAuthorize(...) 的 API 不論透過任何方式存取, 都會執行存取驗證.

而 APIs 的存取還可以再區分為:

  • Inbound Access - Client 從外部存取 App 所暴露的 APIs (下圖 a, b)
  • Internal Access - 同一個 Trace 內, App 間的 APIs 存取 (下圖 c)

Internal Access 即被信任的 App 間的存取, Security 模組可以允許這類的存取直接通過驗證.

 |          |  a. CREATE,DELETE  | App A                  |

透過 properties 中的 kapok.security.access.permit-all-within-trace 可以控制開關, 預設是啟用的, 如要關閉則:

kapok:
  security:
    access:
      permit-all-within-trace: false

Squashing Authorities

在啟用 permit-all-within-trace 的情境下, Authorities 在 Internal Access 中會被壓縮後才傳播, 這樣除了內容變小可增加傳輸效率以外, 還可以避免權限設定過多 Request 過大被踢退的問題.

透過以下參數可以微調:

  • kapok.security.access.squash-authorities-within-trace - 是否要壓縮的權限, 預設: true
  • kapok.security.access.squashed-authority - 壓縮後的文字 (這個值基本上不會判斷到, 只是當你自己解開 token 看到的內容而已), 預設: *

Access Audit Events

Security 擴充模組針對 Inbound Access 和 Internal Access 提供了對應的稽核事件, 你可以透過 properties 中的 kapok.security.audit.events 參數控制是否要發佈這類事件:

  • publish-inbound-access-success - 是否發佈從 Trace 外的存取成功事件 (外部呼叫) (預設為 false)
  • publish-internal-access-success - 是否發佈 Trace 內的存取成功事件 (內部呼叫) (預設為 false)

啟用後, 你可以撰寫監聽器來處理這些事件:

@Service
class MyEventListener {

  @EventListener(condition = "#event.auditEvent.type == 'INBOUND_ACCESS_SUCCESS'")
  public void onInboundAccessSuccess(AuditApplicationEvent event) {
    // 處理外部存取成功事件
  }

  @EventListener(condition = "#event.auditEvent.type == 'INTERNAL_ACCESS_SUCCESS'")
  public void onInternalAccessSuccess(AuditApplicationEvent event) {
    // 處理內部存取成功事件
  }
}

建議發佈這些成功存取的事件需要根據業務需求來實作, 以避免應用程式產生了過多的事件, 例如, 你希望針對任何有 admin 角色的 Client 在存取了 API 後做後續的處理, 可以啟用外部存取成功事件:

# application.yml
kapok:
  security:
    audit:
      events:
        publish-inbound-access-success: true

接著撰寫符合需求的 AccessSuccessAuditEventMatcher 並註冊為 Spring Bean：

@Component
class MyAccessSuccessAuditEventMatcher implements AccessSuccessAuditEventMatcher {

  @Override
  public boolean matches(Authentication authentication) {
    return authentication.getAuthorities().stream()
        .map(GrantedAuthority::getAuthority)
        .anyMatch(authority -> authority.equals("ROLE_admin"));
  }
}

你也可以使用一些便捷的方法來簡化邏輯, 例如:

@Configuration
class MyConfig {

  @Bean
  AccessSuccessAuditEventMatcher myAccessSuccessAuditEventMatcher() {
    return AccessSuccessAuditEventMatcher.matchAuthorities(
        authorities -> authorities.contains("ROLE_admin"));
  }
}

Reject Access

任何在安控模組被拒絕的請求, 都會被應用程式中註冊的 APIErrorExceptionHandler 轉換成 Kapok 定義的標準錯誤結構

透過配置 kapok.security.reject.default-handlers 下的參數可以做更多的控制:

  • enabled: 是否啟用核心的預設處理器, 預設: true
  • authentication-error.status: 認證失敗的 HTTP 狀態碼, 預設: 401
  • authentication-error.code: 認證失敗的錯誤代碼, 預設: E401
  • authentication-error.message: 認證失敗的錯誤訊息, 預設: Authentication rejected
  • access-denied-error.status: 授權失敗的 HTTP 狀態碼, 預設: 403
  • access-denied-error.code: 授權失敗的錯誤代碼, 預設: E403
  • access-denied-error.message: 授權失敗的錯誤訊息, 預設: Forbidden

例如, 想要調整自己定義的認證失敗 error 訊息, 範例如下:

# application.yml
kapok:
  security:
    reject:
      default-handlers:
        authentication-error:
          code: "OOPS"
          message: "You cannot pass!"

Reject if No Handler Found

Spring Security 是實作於 Filter, Spring MVC 是 Servlet, 而 Filter 的執行一定會早於 Servlet 的. 在這先天條件下, 當呼叫端發出了一個錯誤的 URL 請求, 只要又撞到驗證不過的情境, 呼叫端收到的回覆將會是 401 而不是 404. 這可能會多少造成呼叫端往錯誤的方向查找問題.

Security 模組有微調這段, 在 Reject 過程中若又發現是一個錯誤的 URL (即沒有任何 Handler 可以處理), 預設會將回覆狀態改為 404, 這機制可以提供開發維運人員在除錯上更精確的資訊, 但請了解到, 若你的服務是部署於公開的網路上, 這些細微的資訊相對的也會是公開的, 請務必考量過相關的風險,

可以透過 properties 中的 kapok.security.reject.enable-not-found-error 來控制, 預設是啟用的, 若要關閉範例如下:

# application.yml
kapok:
  security:
    reject:
      enable-not-found-error: false # 預設是啟用的

Propagation

Security 擴充模組也整合了 Tracing 機制, 如:

在上圖中, SERVICE 1 在收到請求後會進行認證, 一旦通過後會將取回的使用者資訊往後傳播!

在接下來的服務中, 無論是透過 HTTP 或是 Queue 到呼叫, 只要在同一個 Tracing 鏈都會享有相同的登入資訊, 也就是以下這段程式碼在同一個 Tracing 鏈下的各個服務中, 所取得的結果都會是一樣的:

var currentUser = SecurityContextHolder.getContext()
      .getAuthentication()
      .getPrincipal(); // 在 Service 1, 2, 3, 4 中都會是相同的資訊

而 SERVICE 2, 3, 4 在收到請求後會自動的信任前面服務的認證資訊, 因此不用擔心在一個長流程中 Token 過期的例外.

Propagation Baggage Type

Security 擴充模組在傳播認證資訊共有以下模式:

  • JWT - JWT 模式 (預設)

透過 properties 的 kapok.security.auth.baggage.type 可以切換模式, 預設模式為 JWT

JWT

在 JWT 模式中，所有認證資訊會被簽發成一個 JWT Token，以確保資訊的完整性和不被篡改，該 Token 的有效期限是根據以下幾個標準來確定的：

  1. 預設保障期限為 24 小時，但可以透過設定檔案中的 kapok.security.auth.baggage.jwt-token-timeout 進行調整，其格式需遵循 Duration 的規範
  2. 原始身份提供者 (IdP) 簽發的 Token 所設定的有效期限
  3. 在前一服務中，Security 擴充模組簽發的 Token 的有效期限

最終會在上述所有期限中，選擇最長的一個作為簽發 Token 的有效期限。

這種設計不僅確保了 Token 的安全性和靈活性，還使其能夠在長時間交易（Long Transaction）過程中保持有效，同時避免了在跨越多個服務時產生的過期問題。此外，Token 的有效期限設定具有重要的安全作用：即使 Token 落入未經授權的人手中，它也無法被長期使用。一旦超過設定的有效期限，Token 便會自動失效，這有效地防止了 Token 的長期濫用，進一步增強了系統的安全性。

另外，所設定的保障期限 (例如目前預設的 24 小時) 是根據當前業務場景來確定的。開發人員應確保在任何業務情境中，都不會發生超過此保障期限的長時間交易。

例如, 我的應用程式會有超級長的交易, 想將 Token 的保障期限調整為 72 小時, 則範例如下:

# application.yml
kapok:
  security:
    auth:
      baggage:
        jwt-token-timeout: 72h

OpenAPI

Web 擴充模組整合了 OpenAPI, 你可以直接在 Rest API 上定義 OpenAPI 規格, 如:

import io.swagger.v3.oas.annotations.*;

@Tag(name = "Home")
@RestController
class HelloController {

  @Operation(summary = "Hello", description = "Say Hi!")
  @ApiResponses(value = {
      @ApiResponse(responseCode = "200", description = "Success operation"),
  })
  @GetMapping("/hello")
  String hello(
      @Parameter(description = "Your name") @RequestParam("name") Optional<String> name) {
    return format("Hello %s!", name.orElse("World"));
  }
}

啟動 App 後就會自動註冊以下 API Endpoint:

  • http://127.0.0.1:8080/swagger-ui.html - 可以連結到 Swagger UI
  • http://127.0.0.1:8080/v3/api-docs - 可以取得 OpenAPI 規格

Swagger UI 的路徑預設在 /swagger-ui.html, 透過 properties 中的 springdoc.swagger-ui.path 可以調整, 若我想改到 http://127.0.0.1:8080/my-api, 則可以設定:

# application.yml
springdoc:
  swagger-ui:
    path: /my-api

Swagger UI 預設是開啟的, 通常是測試時使用, 若想要關閉 (如在正式環境中), 可以透過 properties 中的 springdoc.swagger-ui.enabled 來控制:

# application.yml
springdoc:
  swagger-ui:
    enabled: false

APIDoc

@APIDoc 是一個標記, 用於標記某個 interface 是 OpenAPI 規格文件

在預設的情況下, 這個標記不會有任何的 Runtime 行為, 而若啟用了 Web 模組的 APIDocProxyRegistrar, 才會將這些標記了 @APIDoc 的 classes, 動態建立 Proxy 並註冊成 Spring Bean

此功能是設計給產生輕量版的 OpenAPI description 情境使用, 再配合啟用 SafeMode, 來讓一個複雜的 App 也可以快速且消耗更低資源的啟動, 並再動態的建立 Proxy 來讓 Springdoc 產出 OpenAPI description, 當然這樣有些限制的, 套用請務必閱讀過: Generate Lightweight OpenAPI

此功能預設沒有啟用, 配過配置 kapok.openapi.proxy 下的參數, 可以啟用或控制更多細節:

  • enabled - 是否啟用此功能 (Default: false)
  • interfaces - 指定一至多個掛 @APIDoc 的 interface classes 做 proxy
  • jandexLocations - Jandex index 的檔案位置, 可用逗號分隔一至多個, 會搜尋這些檔案中有掛 @APIDoc 的 interface classes 做 proxy (Default: classpath*:/META-INF/jandex.idx)

程式碼範例如下:

import io.swagger.v3.oas.annotations.*;

@APIDoc
@Tag(name = "Home")
public interface HelloApi {

  @Operation(summary = "Hello", description = "Say Hi!")
  @ApiResponses(value = {
      @ApiResponse(responseCode = "200", description = "Success operation"),
  })
  @GetMapping("/hello")
  String hello(
      @Parameter(description = "Your name") @RequestParam("name") Optional<String> name);
}

@RestController
class HelloController implements HelloApi {

  @Override
  String hello(Optional<String> name) {
    return format("Hello %s!", name.orElse("World"));
  }
}

Root Redirection

為了使用上的方便, Web 擴充模組預設設置了一個將 / 的請求進行轉址的轉址器, 透過設定 kapok.web.root-redirect 下的參數, 可以對轉址功能進行細節控制:

  • enabled - 是否啟用此功能 (Default: true)
  • path - 指定轉址路徑, 若有設定, 將最優先使用 (預設空)
  • type - 選擇轉址類型 (若 path 沒提供才使用這個設定)
    • app_info - 轉到 Application Info (預設)
    • swagger_ui - 轉到 Swagger UI (需啟用 Swagger UI 才會生效)

例如, 如果你希望轉址到 https://www.softleader.com.tw, 配置範例如下:

kapok:
  web:
    root-redirect:
      path: https://www.softleader.com.tw

Note

如果你的應用程式中也註冊了一個 / 的 API Endpoint 則會最優先的使用，此小節的設定將無作用

Response Headers

Web 擴充模組會在 Response 中埋入一些特定的 Header, 這些 Header 可以幫助我們在問題查找, 做 API 對接時等等, 可以更容易且準確的定位及追蹤每個 Request.

在啟動 App 後, 任何瀏覽器或 curl 等工具對 App 發送的 Request, 不論返回的是哪種 Http Status, 在 Response 中都應該都會包含了類似下述的 Headers:

$ curl -I http://localhost:8080/

HTTP/1.1 404 Not Found
Date: Wed, 17 May 2023 03:50:19 GMT
Content-Type: application/json

...

x-app-id: hello-example
x-app-group: tw.com.softleader.kapok.examples
x-app-version: 1.0.0/bf1f751
x-trace-id: 98213efaf252a5244fd21b4017c75833

如上述 x- 開頭的就是 Web 擴充模組所放入的 Headers, 若想要關閉此功能, 可以透過 properties 中的 kapok.web.response.headers.enabled 來控制:

# application.yml
kapok:
  web:
    response:
      headers:
        enabled: false # 預設是啟用的, 若關閉此章節後續所有功能都會關閉

App Info in Response

Web 擴充模組會將 Application Info 中的 build.* 資訊放入 Response Header, 透過配過配置 kapok.web.response.headers.app 下的參數, 可以控制更多細節:

  • enabled - 是否啟用此功能 (Default: true)
  • app-id - 要輸出的 app id, 若沒提供會嘗試使用 Application Info 的 build.artifact
  • app-group - 要輸出的 app group, 若沒提供會嘗試使用 Application Info 的 build.group
  • show-details - 是否要輸出詳細訊息; 若否只會輸出 app id (Default: true)
  • header-name.app-id - 要輸出的 app 名稱的 header name (Default: x-app-id)
  • header-name.app-group - 要輸出的 app group 的 header name (Default: x-app-group)
  • header-name.app-version - 要輸出的 app version 的 header name (Default: x-app-version)

例如, 我想要將輸出的 app id 設定成 spring.application.name, app group 設定為 Kapok Platform, 則範例如下:

# application.yml
kapok:
  web:
    response:
      headers:
        app:
          app-id: ${spring.application.name}
          app-group: Kapok Platform

Trace in Response

Web 擴充模組會將 Trace 資訊放入 Response Header, 透過配過配置 kapok.web.response.headers.trace 下的參數, 可以控制更多細節:

  • enabled - 是否啟用此功能 (Default: true)
  • show-details - 是否要輸出詳細訊息; 若否只會輸出 trace-id (Default: false)
  • header-name.trace-id - 要輸出的 trace-id 的 header name (Default: x-trace-id)
  • header-name.span-id - 要輸出的 span-id 的 header name (Default: x-span-id)
  • header-name.parent-span-id - 要輸出的 parent-span-id 的 header name (Default: x-parent-span-id)
  • header-name.sampled - 要輸出的 sampled 的 header name (Default: x-sampled)

例如, 預設只有輸出 trace id, 若我想要得到 span id 等完整資訊, 則範例如下:

# application.yml
kapok:
  web:
    response:
      headers:
        trace:
          show-details: true

Error Handling

一般我們在寫 Java 時, 我們會視需求或情境在程式中加上一些預期的例外 (Exception) 擷取及對應的處理方式, 舉例如下:

try {
  // 處理邏輯
} catch(IllegalArgumentException iae) {
  // do something to iae
} catch(/* other exception we care */) {
  // do some specific thing to the exception
} catch (Exception e) { // if none of above
  // do something general, ex: translating, sending mail or logging out
  log.error("some general wording goes here", e);
}

這樣會讓每個 Controller 都要不斷的去實作這些重複的處理邏輯, 除了影響閱讀外, 也會造成維護上的困難! 在 Kapok 中是不太建議用這種模式處理例外.

Exception Handling Process

在 Web 擴充模組啟動的過程中, 會自動的啟動一個 Global 例外處理器, 每當 Exception 發生且被丟出 Controller 後, 就會被這處理器攔截到, 並依序執行以下步驟:

  1. 封裝 Exception 成標準的錯誤結構 (Error Response Structure)
  2. 發佈抓取了 Exception 的事件
  3. 印出 Exception 內容

Important

例外處理器是使用 AOP 機制的, 因此 Exception 一定要被丟出 Controller 才會被攔截

Structure of Error Responses

Web 擴充模組中定義的錯誤結構, 有實作標準 RFC 7807 - Problem Details for HTTP APIs, 內容範例如下:

{

  "title": "E004: Binding error",
  "status": 400,
  "detail": "E004: Binding error: [field_error/must be greater than 0/error in object 'profile' on field 'age'/rejected value [0]]",
  "instance": "/hello",

  "code": "E004",
  "message": "Binding error",
  "details": [
    {
      "code": "field_error",
      "message": "must be greater than 0",
      "object": "profile",
      "field": "age",
      "rejectedValue": 0

  ],
  "trace": [
    "org.springframework.web.bind.MethodArgumentNotValidException: Validation failed for argument [1] in public java.lang.String tw.com.softleader.kapok.examples.gettingstarted.GreetingController.greeting(java.lang.String,tw.com.softleader.kapok.examples.gettingstarted.Profile): [Field error in object 'profile' on field 'age': rejected value [0]; codes [Positive.profile.age,Positive.age,Positive.int,Positive]; arguments [org.springframework.context.support.DefaultMessageSourceResolvable: codes [profile.age,age]; arguments []; default message [age]]; default message [must be greater than 0]] ",

    "\tat org.springframework.web.method.support.InvocableHandlerMethod.getMethodArgumentValues(InvocableHandlerMethod.java:181)",
    "\tat org.springframework.web.method.support.InvocableHandlerMethod.invokeForRequest(InvocableHandlerMethod.java:148)",
    ...

}
  • type: 本次錯誤說明文件的 URI reference, 預設: about:blank
  • title: 描述本次錯誤的簡短說明, 即呼叫 APIError#title()
  • status: Http Status
  • details : 描述本次錯誤的簡短描述, 即呼叫 APIError#shortSummary()
  • instance: 本次錯誤的 URI reference, 放的是 API path
  • code: 主要的錯誤代碼
  • message: 主要的錯誤說明
  • details[]: 更進一步的錯誤資訊
  • details[].code: 更進一步的錯誤代碼
  • details[].message: 更進一步的錯誤說明
  • details[].*: 更進一步的錯誤資訊中所延伸擴充的欄位
  • trace[]: 錯誤的 stacktrace (預設不回傳, 有幾種開啟方式)

對應此結構的 Java 物件為:

  • APIError
  • APIErrorDetail

Mapping Exception to APIError

APIErrorExceptionHandler 負責將 Exception 封裝成 APIError, Web 擴充模組預設已經註冊了一系列預設的 Exception 處理邏輯, 請參考這邊

這配置預設是啟用的, 也透過 properties 中的 kapok.web.error.default-handlers.enabled 可以控制是否啟用, 如想要關閉:

# application.yml
kapok:
  web:
    error:
      default-handlers:
        enabled: false

預設的 Exception 處理邏輯中所使用的錯誤代碼/訊息, 可以透過 properties 中的 kapok.web.error.default-handlers.*.[code/message] 來調整

例如, 未預期錯誤預設的錯誤代碼/訊息為 E999/Unexpected error, 我想要調整成 OOPS/You cannot pass!, 則:

kapok:
  web:
    error:
      default-handlers:
        unexpected-error:
          code: OOPS
          message: You cannot pass!

Note

由於 kapok.web.error.default-handlers.* 的 key 較多, 建議使用支援 properties 自動補齊的 IDE (如 IntelliJ) 查看, 或直閱讀原始碼

Customizing Exception Handler

如果自己的應用程式想要增加更多的 Exception 邏輯, 則可以透過實作 APIErrorExceptionHandler, 並在將其註冊成 Spring Bean, 就可以讓 Web 擴充模組在啟動期間動態的進行配置

例如我有一個自定義的 InvalidPasswordExceptionHandler, 想要針對這個 Exception 轉換成錯誤代碼: E900, 訊息: Invalid password, 以及一些 detail 的錯誤結構

程式範例:

@Component
class InvalidPasswordExceptionHandler implements APIErrorExceptionHandler {

  @Override
  public boolean supports(Exception exception) {
    return exception instanceof InvalidPropertiesFormatException;
  }

  @Override
  public APIError buildError(Exception exception, WebRequest request) {
    return APIError.builder()
        .code("E900")
        .message("Invalid password")
        .detail(detail -> detail.message("Password too short"))
        .build();
  }
}

APIErrorExceptionHandler#builder() 也提供了許多方便的建置方法, 以不同的風格進行設定, 例如, 上述的範例, 也可以使用以下方式來設定:

@Configuration
class MyConfig {

  @Bean
  APIErrorExceptionHandler invalidPasswordExceptionHandler() {
    return APIErrorExceptionHandler.builder()
        .supportInstanceOf(InvalidPropertiesFormatException.class)
        .buildError(
            (exception, request) ->
                APIError.builder()
                    .code("E900")
                    .message("Invalid password")
                    .detail(detail -> detail.message("Password too short"))
                    .build())
        .build();
  }
}

Ordering Exception Handlers

Global 例外處理器在挑選 APIErrorExceptionHandler 的邏輯是設計成 FIFO (First In, First Out) 的, 也就是當多個 APIErrorExceptionHandler#supports(Exception) 成立的情況下, 排序越前的將會被優先被使用, 排序是用數字來排: 由小到大, 換言之越小的將越優先使用.

Web 擴充模組中的預設處理邏輯 都是被設定成最低優先度, 你可以透過這個機制在自己的應用程式中去複寫預設處理方式.

例如 IllegalArgumentException 在 Web 擴充模組中已經有個預設的處理邏輯了, 只要在你的應用程式中在註冊一個 handler 就可以複寫, 程式範例如下:

@Component
class MyIllegalArgumentExceptionExceptionHandler implements APIErrorExceptionHandler {

  @Override
  public boolean supports(Exception exception) {
    return exception instanceof IllegalArgumentException; // 這樣就可以複寫 Web 擴充模組中的預設邏輯
  }

  ...
}

Note

預設的優先度就已經比最低優先度還高的, 也就是你只要有註冊自己的處理器都可以複寫掉預設配置

若想要更精確控制可以複寫 getOrder() 排序方法, 如:

@Component
class InvalidPasswordExceptionHandler implements APIErrorExceptionHandler {
  ...

  @Override
  public int getOrder() {
    // Parent 有以下常數可參考使用:
    // APIErrorExceptionHandler.HIGHEST_PRECEDENCE
    // APIErrorExceptionHandler.DEFAULT_PRECEDENCE
    // APIErrorExceptionHandler.LOWEST_PRECEDENCE
    return MYORDER;
  }
}

I18n for Error Messages

現在，Web 擴充模組已經支援對 Error Structure 中的 message 欄位進行多國語系的轉換。預設提供的多國語系訊息代碼 Pattern 如下：

# APIError
apiError.[APIError.code]

# APIErrorDetail
apiError.detail.[APIErrorDetail.code]

相對應的 Java 方法如下：

  • APIError.getDefaultMessageCode(...)
  • APIErrorDetail.getDefaultMessageCode(...)

在 Mapping Exception to APIError 的過程中，所註冊的預設 Exception 處理邏輯中，都包含了多國語系的轉換，步驟如下：

  1. 首先，它會根據 Request 中的 Accept-Language 來決定要使用的翻譯語系
  2. 如果請求中未指定語言，或者指定的語言不受支援，則將使用系統的預設語系
  3. 決定語系後，將使用 Pattern apiError.[APIError.code] 來進行翻譯
  4. 如果翻譯成功，將覆蓋原本設定的 message 欄位，否則將保持原本的 message 內容輸出

在預設的邏輯中，不處理 details[].message

舉個例子，未預期錯誤預設的錯誤代碼/訊息為 E999/Unexpected error，如果要轉換成多國語系，則可以按照以下步驟進行設定：

首先在應用程式的 resources 目錄下建立多國語系檔案，例如：

  • src/main/resources/message.properties - 預設語系
  • src/main/resources/messages_zh_TW.properties - 中文語系

接著在各個語系檔案中，增加內容如下：

<!-- message.properties -->
apiError.E999=You cannot pass!

<!-- messages_zh_TW.properties -->
apiError.E999=你不能通過!

這樣就完成了多國語系的設定。

當然，你也可以完全的客製化，就像在 Customizing Exception Handler 中一樣去實作多國語系的轉換，首先，修改 InvalidPasswordExceptionHandler 如下：

@Slf4j
@Component
@RequiredArgsConstructor
class InvalidPasswordExceptionHandler implements APIErrorExceptionHandler {

  final SafeMessageSource messageSource; // 從 Spring 注入語系檔

  @Override
  public APIError buildError(Exception exception, WebRequest request) {
    var error =
        APIError.builder()
            .code("E900") // 錯誤代碼
            .message("Password invalid") // 預設的訊息
            .detail(detail -> detail.message("Password too short")) // 預設的 detail
            .build();

    // 這邊進行 error.message 翻譯
    messageSource
        .getMessage(
            APIError.getDefaultMessageCode(error, null), // 指定多國語系檔中的訊息代碼, 當然你也可以完全自定義
            null, // 自定義參數, 用於 format 訊息, 可以設計成從 exception 中取, 讓使用者可以從 runtime 中指定丟出
            request.getLocale())
        .ifPresent(error::setMessage);

    // 若需要, 你也可以再對 error.details[].message 翻譯
    // 可以使用 APIErrorDetail.getDefaultMessageCode(detail, null), 或完全的自定義多國語系檔中的訊息代碼

    return error;
  }
}

然後，在語系檔案中設定如下：

<!-- message.properties -->
apiError.E900=Invalid password

<!-- messages_zh_TW.properties -->
apiError.E900=密碼錯誤

Handling Exception Events

Global 例外處理器在攔截到 Exception 後, 會發佈 ExceptionCaughtEvent, 讓自己的應用程式可以統一的監聽感興趣的 Exception 來做更多的邏輯處理

例如我想要當 InvalidPasswordException 發生後寄信給指定人員, 則我可以撰寫一個 Spring event listener 去監聽, 完整的程式範例如下:

@Slf4j
@Component
class InvalidPasswordExceptionListener {

  @Async
  @EventListener
  public void onException(ExceptionCaughtEvent<InvalidPasswordException> event) {
    log.warn("error=[{}], time=[{}]", event.getError().shortSummary(), event.getCaughtTime());
    // send email
  }
}

Controlling APIError Logging

Global 例外處理器在將攔截到的 Exception 轉換成 APIError 後, 會將該錯誤資訊印出, 預設的 logging 邏輯為:

  • 若為呼叫端的例外 (Client Error), 則印 INFO 且不輸出 stacktrace
  • 以外則印 ERROR, 且輸出 stacktrace

你可以透過以下方式做調整:

  1. Logging Control in Exception Handler (優先參考)
  2. Logging Control based on Strategy

Logging Control in Custom Exception Handler

透過 Customizing Exception Handler 可以做完整的 logging 控制, 程式範例如下:

@Component
class InvalidPasswordExceptionHandler implements APIErrorExceptionHandler {
  ...
  @Override
  public APIError buildError(Exception exception, WebRequest request) {
    return APIError.builder()
        ...
        // 指定將這個錯誤印到 warn, 且要輸出 stacktrace
        .logging(logging -> logging.level(Slf4jLevel.WARN).includeStacktrace())
        .build();
  }
}

Logging Control based on Strategy

透過配過配置 kapok.web.error.logging-strategy 下的參數, 可以控制錯誤代碼 APIError#code 所對應的 logging level:

  • overlay-strategy - 若匹配了多個 Logging 等級的挑選策略, 支援 highest (等級最高者) 及 lowest (等級最低者) (Default: highest), 請參考 Slf4jLevel 的順序高低定義
  • exact.<level>:<codes> - 設定一或多組 Logging 等級對應錯誤代碼的完整比對規則, 一組規則中可設定一或多個錯誤代碼, 若多組以逗號(,)隔開, 比對時區分大小寫 (case sensitive)
  • regex.<level>:<codes> - 設定一或多組 Logging 等級錯誤代碼對應的 regex 比對規則, 一組規則中可設定一或多個 regex, 若多組以逗號(,)隔開

Important

exact 比對的結果將更優先於 regex 比對

例如我想要做以下邏輯調整

  1. 錯誤代碼為 E000 的印 warn
  2. 將開頭為 T 的錯誤代碼印 trace
  3. 將開頭為 D 的錯誤代碼印 debug
  4. 將開頭為 I 的錯誤代碼印 info
  5. 將開頭為 W 的錯誤代碼印 warn
  6. 將開頭為 O 的錯誤代碼不印 (也就是 off)

則完整的設定範例如下:

# application.yml
kapok:
  web:
    error:
      logging-strategy:
        exact:
          "info": E000
        regex:
          "trace": ^[Tt].+
          "debug": ^[Dd].+
          "info": ^[Ii].+
          "warn": ^[Ww].+
          "off": ^[Oo].+

Note

此模式是配置 “等級” 的邏輯, 而不是 “等級與錯誤代碼” 的邏輯

CORS

Web 擴充模組對於 CORS 的配置預設是 Permit All, 透過 properties 中的 kapok.web.cors.* 下的參數可以做調整:

  • allowed-origins - 允許的來源白名單, 可設定多組, 區分大小寫, 預設為 * (即全部允許)
  • allowed-origin-patterns - 允許的來源白名單, 可設定多組, 區分大小寫, 支援 * 或 [] 等更靈活的配置方式, 無預設值, e.g.
    • https://*.domain1.com – domains ending with domain1.com
    • https://*.domain1.com:[8080,8081] – domains ending with domain1.com on port 8080 or port 8081
    • https://*.domain1.com:[*] – domains ending with domain1.com on any port, including the default port
  • allowed-headers - 允許的 Http Header 白名單, 可設定多組, 預設為 * (即全部允許)
  • allowed-methods - 允許的 Http Method 白名單, 可設定多組, 預設為 * (即全部允許). e.g. “GET”, “POST”, etc.

例如, 我想設定只能允許來源為 http://my-app:8080 的服務呼叫, 設定範例如下:

# application.yml
kapok:
  web:
    cors:
      allowed-origins: 
        - http://my-app:8080

Disallowing Methods

Web 擴充模組預設使用 Undertow 作為 embedded web server, 並且提供了一些簡單的方式來設定禁用的 HTTP methods, 你可以通過 properties 中的 kapok.web.server.disallowed-methods 來設定一至多組

例如, 如果你想要禁用 TRACE HTTP method, 這類 method 比較常用於 debug 情境, 而在某些弱點掃描中可能會被要求關閉, 設定範例如下:

# application.yml
kapok:
  web:
    server:
      disallowed-methods: trace

這樣當 Client 發送 TRACE 請求時, 就會收到 405 Method Not Allowed, 例如:

$ curl -X TRACE localhost:8080 -I

HTTP/1.1 405 Method Not Allowed
Connection: keep-alive
Content-Length: 0
Date: Tue, 24 Sep 2024 03:11:10 GMT

Important

此處理階段發生在 web server 層級, 早於 Spring 的處理, 因此 Spring 中的設定都不會生效, 例如: Customizing Error for HTTP APIs
