1 - Apply project resource

申請項目所需資源

只要你有 oidc:developer 權限, 你應該可以操作 default namespace 了, 例如建立或刪除 deploy, service, 或 ingress 等!

但 default namespace 資源配額是有限的, 通常只會拿來做些簡單的測試, 不適合用於專案開發! 如果專案要使用, 必須事先規劃相關的資源配額, 請準備以下資訊後請向 R&D 或 PD 任一成員提出:

Resource Units Description Example
Project 專案名稱, 可以視為 Namespace 群組, 若沒填則使用 Namsepace 名稱, 用於公司的監控系統及 Harbor
Namespace 名稱, 僅可以是英文小寫及或 dash (-) 組成 mimosa
Request cpu Core 總 cpu 最小需求, 若沒填則使用 Limit cpu 10
Request monory Mi/Gi 總 memory 最小需求, 若沒填則使用 Limit monory 10Gi
Limits cpu Core 總 cpu 最大需求 20
Limits monory Mi/Gi 總 memory 最大需求 20Gi
Container image storage Gi 在 Project 下, 總 container image 儲存空間的最大需求 50Gi

完成申請後, 你應該會取得對應的:

  • SLKE Namespace - 專案部署的 Namespace
  • Harbor project - 專案使用的 Container registry project
  • 權限 - 你的帳號應該可以瀏覽及操作該 namespace, 若發生權限上的問題請依照 Delete Local Cache 章節內容來試著排除

What’s next

接著你就可以試著部署程式了!

2 - Deploy first app

部署第一個應用程式

一切就緒後, 你可以部署第一個 app 了!

首先要先切換到你申請的 namespace (或使用 default), 如果你有安裝 kubectl ns plugin, 你可以執行:

kubectl ns {{ namepsace }}

若沒有安裝, 可以透過以下指令來設定多組 context + namespace 來達到換速切換, 首先設定新的 context, 綁定 namespace:

kubectl config set-context oidc@slke#{{ namepsace }} --cluster=slke --user=oidc --namespace={{ namepsace }}

然後切換到新建立的 context:

kubectl config use-context oidc@slke#{{ namepsace }}

接著 apply nginx 部署檔:

kubectl apply -f https://raw.githubusercontent.com/kubernetes/website/master/content/en/examples/service/networking/run-my-nginx.yaml

執行後你可以透過 get pod 命令來查看部署狀況:

kubectl get pod --watch

當然你可以透過以下指令移除部署:

kubectl delete -f https://raw.githubusercontent.com/kubernetes/website/master/content/en/examples/service/networking/run-my-nginx.yaml

接著我們要建立 Service:

kubectl apply -f https://raw.githubusercontent.com/kubernetes/website/master/content/en/examples/service/networking/nginx-svc.yaml

檢查 Service 建立結果

kubectl get svc

完成後我們可以到其中一個 pod 中試著 access 剛剛建立好的 service:

# 找出其中一個 pod
kubectl get po

# 在其中一個 pod 中對 curl 剛剛建立的 service, 若成功你應該可以看到 Welcome to nginx! 等文字
kubectl exec {{ pod name }} -- curl my-nginx

到這邊基本部署也算完成了!

Ingress

如果你的服務需要對外開放存取, 你就需要設定 Ingress! 開始設定前最重要的是: 要先決定你的服務對外開放的 Host!

由於 Ingress Host 在整個 SLKE 中不可重複, 就算在不同的 namespace 也是, 因此建議的 Pattern 為:

{{ ingress-name }}-{{ namespace }}.cloud.softleader.com.tw

例: 在 namespace test 下的 ingress my-nginx, 建議的 Ingress Host 為:

my-nginx-test.cloud.softleader.com.tw

決定 Host 以後, 就可以 apply 以下 config 了:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-nginx
spec:
  ingressClassName: istio
  rules:
  - host: my-nginx-test.cloud.softleader.com.tw
    http:
      paths:
        - backend:
            service:
              name: my-nginx
              port:
                number: 80
          path: /
          pathType: Prefix

完成後, 你可以透過瀏覽器, 或執行以下命令看到 Welcome to nginx!!

curl http://my-nginx-test.cloud.softleader.com.tw

What’s next?

SLKE 中有自動化的 Ingress 管理功能, 包含了 Host 的產生或 TLS 的憑證套用等, 請閱讀 Auto managed Ingress 取得更多說明.

3 - Auto managed Ingress

自動管理 Ingress

在專案應用中, Ingress 配置時常需要一些特別的管理設定, 如:

  • 我想要使用公司的憑證
  • 我專案的 App 會同時被部署在不同的 Namespace 以提供不同環境的測試, 但同時都要對外, 需要自動的區分網址
  • …等等

為了簡化專案配置合適的設定, 以及更加的自動化, 在 SLKE 中我們會監控 Kubernetes 中的 v1 版的 Ingress 物件, 在建立或修改 Ingress 物件時, 自動的介入該物件的配置, 依據不同模式注入更多的控制.

透過註記 ingress.softleader.com.tw/automanaged: "true" 來指定該 Ingress 為管理目標, 例如:

apiVersion: networking.k8s.io/v1 # 請注意版本
kind: Ingress
metadata:
  name: my-nginx
  namespace: default
  annotations:
    ingress.softleader.com.tw/automanaged: "true" # 標記是管理目標
spec:
  ingressClassName: istio
...

這些被管理的 Ingress 將會依照狀況:

  • 自動產生 Host 設定, 規則是: 
    ${metadata.name}-${metadata.namespace}.cloud.softleader.com.tw
  • 自動提供 HTTPS 連線服務, 規則是符合 .cloud.softleader.com.tw 的 Host (包含手動設定或自動產生的 Host)

Try it out

首先 apply 以下設定:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-nginx
  namespace: default
  annotations:
    ingress.softleader.com.tw/automanaged: "true"
spec:
  ingressClassName: istio
  rules:
    - host: "" # 此欄位 Key 不出現, 或 Value 為空或 '*', 就會被自動產生
      http:
        paths:
          - backend:
              service:
                name: my-nginx
                port:
                  number: 80
            path: /
            pathType: Prefix

完成後, 透過指令可以查詢到產生的結果:

$ kubectl get ingress

NAME        CLASS    HOSTS                                      ADDRESS         PORTS     AGE
my-nginx    <none>   my-nginx-default.cloud.softleader.com.tw                   80        2s80

這時候你就可以透過瀏覽器或指令連到該網址, 例如:

curl http://my-nginx-default.cloud.softleader.com.tw

同時你也可以透過 SSL 連線

curl https://my-nginx-default.cloud.softleader.com.tw

以上大概是最常使用的設定說明，而除此之外還有很多細微的地方可以控制, 請到 Ingress Manager 詳細閱讀說明書!

4 - Assigning Pods

安排 Pods

在部署 Deployment 時, 有些情況我們會希望 Kubernetes 依照我們的需求來安排部署的 Node, 例如:

  • 當我們開多份 Replicas 時, 希望這些 Replicas 時儘量不要安排到同一個 Node 上
  • 不同的部署但性質相雷同的程式, 例如資源需求 (如 CPU 運算) 較高等, 希望儘量不要安排到同一個 Node 上

Affinity

在 spec.affinity 下一共有 podAffinity (正向) 或 podAntiAffinity (反向), 這是用來約束 Kubernetes 該怎麼安排 Pod 到 Node 上, 這兩種 affinity 中都有兩種 type 可以使用:

  • requiredDuringSchedulingIgnoredDuringExecution - Hard requirement, 要求 Kubernetes 依照設定安排, 沒滿足就不部署 Pod
  • preferredDuringSchedulingIgnoredDuringExecution - Soft requirement, 建議 Kubernetes 儘量滿足設定安排, 無法滿足仍要部署 Pod

Use Case

以下我們範例是一個常見的需求: 建議 Kubernetes 將多個 replicas 儘量分散到不同的 Node 中

首先我們在 SLKE 中部署一個 deployment 作為範例, 先設定一個 replica 就好:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  selector:
    matchLabels:
      run: my-nginx
  replicas: 1
  template:
    metadata:
      labels:
        run: my-nginx
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            # 可設多條件, 其中 weight 範圍為 1-100
            # 部署於 k8s 會將滿足條件的 weight 累加, 總分最高的 node 視為 most preferred 
            - weight: 1
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                  - key: run
                    operator: In
                    values:
                      - my-nginx
                # 設定 Node 分群的依據
                # 可透過 kubectl get nodes --show-labels 查看有哪些 label 可用
                topologyKey: "kubernetes.io/hostname"
      containers:
      - name: my-nginx
        image: nginx
        ports:
        - containerPort: 80

以上設定會建議 Kubernetes 在部署時, 以 Node 的 kubernetes.io/hostname 做群組, 在每個群組中都儘量不重複部署 label 為 run: my-nginx 的 pod, 由於 Node kubernetes.io/hostname 不可能重複, 也就是上述設定以白話文來說, 一但開多個 replicas, 就是儘量將不同的 pod 分散在不同的 node 中

接著我們查看一下現在 SLKE 有多少 Node:

$ kubectl get node

5 - Claim Storage

申請持久性存儲空間

當你的 App 需要一個儲存空間時, 一般在 Kubernetes 中你需要定義 PersistentVolume (PV) 及 PersistentVolumeClaim (PVC), 然後你的 Deployment 才能使用, 而其中 PV 的設定又涉及實際的儲存設備, 也可能會有架構面上的規劃跟考量, 較為複雜且通常是負責 Infrastructure 的成員建置的!

因此在 SLKE 中我們支援了動態的 PV, 也就是說你只要定義好 PVC, 剩下的會由 SLKE 自動的分配一個儲存路徑給你!

SLKE 專用的 Shared Server 在公司的 192.168.1.55, 走的是 NFS, 自動分配的儲存路徑 Pattern 為:

/var/nfs/{{ namespace }}/{{ storage-path }}

{{ storage-path }} 爲 Optinoal 選項, 可填可不填, 若有給應爲相對路徑, 不可使用 / 開頭

範例如下:

Namespace PVC name Storage-Path Include-PVC-Name 實際 Path (192.168.1.55)
mimosa mimosa-0 無 無 /var/nfs/mimosa
mimosa mimosa-0 tech/address/etl 無 /var/nfs/mimosa/tech/address/etl
mimosa mimosa-0 無 true /var/nfs/mimosa/mimosa-0
mimosa mimosa-0 tech/address/etl true /var/nfs/mimosa/mimosa-0/tech/address/etl

PVC

要使用動態 PV 功能, 只需要在 PVC 中加入相關的設定如下:

kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: {{ pvc-name }}
  namespace: {{ namespace }}
  annotations:
    volume.beta.kubernetes.io/storage-class: "managed-nfs-storage" # 宣告要使用 SLKE 動態 PV, 固定文字不可修改
    nfs.io/storage-path: "{{ storage-path }}" # 自定義在 namespace 後的 sub-path, 可有可無, 亦可多層
    nfs.io/include-pvc-name: "true"  # 任何非空值時, 會在 namespace 後 storage-path 前增加 PVC 的 name, 當使用 PVC Template 的時候建議啟動此選項, 否則不建議啟動
spec:
  ...

Try it out

首先 apply 以下 PVC 及 Pod 設定:

kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: test-claim
  namespace: default
  annotations:
    volume.beta.kubernetes.io/storage-class: "managed-nfs-storage"
    nfs.io/storage-path: "my-main-path/my-sub-path"
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 1Mi
---
kind: Pod
apiVersion: v1
metadata:
  name: test-pod
  namespace: default
spec:
  containers:
  - name: test-pod
    image: gcr.io/google_containers/busybox:1.24
    command:
      - "/bin/sh"
    args:
      - "-c"
      - "touch /mnt/SUCCESS && exit 0 || exit 1"
    volumeMounts:
      - name: test-pvc
        mountPath: "/mnt"
  restartPolicy: "Never"
  volumes:
    - name: test-pvc
      persistentVolumeClaim:
        claimName: test-claim

完成後, 你應該會在 192.168.1.55:/var/nfs/default/my-main-path/my-sub-path 下看到 SUCCESS 檔案

你可以透過 ssh root@192.168.1.55 指令連進去查看 (密碼 You know!!)

測試完後刪除 PVC 及 Pod:

kubectl delete po/test-pod pvc/test-claim -n default

6 - Creating CronJob

建立 CronJob

有些重複性的 Job, 使用傳統的方式r交由 App 去實作排程 (如建立一個 Spring App 透過 Schedule 定期執行), 這樣除了平常空閒時有可能會浪費資源外, 你還會需要處理多個 Replicas 的問題, 如 Leader election 等

因此建議使用 Kubernetes 所提供的 CronJob, 在指定時間到的時候才會去建立 Pod 執行, Job 內容可能是 REST 呼叫一隻由 App 所提供的 API, 或是由 Job 本身去執行一些邏輯後就結束 (如透過 Spring 的 ApplicationRunner 或 CommandLineRunner 實作).

所有執行完的 Job 在 Pod 列表中會被標注 Completed, 也代表著該 Job 也經釋放了 Kubernetes 相關的資源

Try it out

Apply 以下設定, 你會發現每 1 分鐘都會被建立一個 Pod

apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "*/1 * * * *"
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 100
      template:
        spec:
          containers:
          - name: hello
            image: busybox
            imagePullPolicy: IfNotPresent
            args:
            - /bin/sh
            - -c
            - date; echo Hello from the SLKE cluster
          restartPolicy: Never

你可以透過以下指令觀察被建立起來的 Pod 的 log, 應該都會印出一行當前時間及一段文字: Hello from the SLKE cluster

kubectl get pod | grep hello
kubectl logs { pod-id }

測試完後刪除 CronJob:

kubectl delete cj hello

Timezone

SLKE 中的 localtime 已經調整成 Asia/Taipei 了, 也就是說在 CronJob 中使用的是台北時區 (GMT+8)

apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "0 3 * * *" # 台北時間每天晚上凌晨3點執行
  jobTemplate:
    ...

Tip

可以到 crontab guru 測試 cron schedule expression

The Problem with CronJobs and Istio Sidecars

Kubernetes CronJobs 這類的 resource type 的設計是 Short lived Tasks, 而 Istio Sidecar 基本上是長期一直啟動的, 兩者的設計上是衝突的, 這可能會造成 CronJobs 被 Kubernetes 誤認為一直在執行中而沒有結束!

在開啟 Isito Sidecar 的 namespace 中的 CronJobs, 若在執行上有任何問題, 建議可以單獨關閉 Sidecar:

apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: hello
spec:
  jobTemplate:
    spec:
      template:
        metadata:
          annotations:
            sidecar.istio.io/inject: "false" # 註記不要被 Istio inject Sidecar
  ...

ref: Handling Istio Sidecars in Kubernetes Jobs

What’s next?

所謂的排程, 其實就是 觸發 與 執行邏輯 的組合結果! 在公司專案的系統架構中, 我們已經都把邏輯 API 化了, 也就是要完成一個排程, 你還會需要的只是一個觸發的方式而已.

在 SLKE 中提供了一個觸發 REST API 的方式, 方便大家操作使用, 請閱讀 Api Trigger 取得更多說明.

7 - Api Trigger

API 觸發控制

API Trigger 設計在 Kubernetes CronJob 及 Job 之上, 提供了週期性的 RESTful API 的觸發控制

Creating a ApiTrigger

下面的 ApiTrigger 範例, 會在每 1 分鐘呼叫 GET https://www.softleader.com.tw

apiVersion: batch.softleader.com.tw/v1
kind: ApiTrigger
metadata:
  name: hello
  namespace: default
spec:
  api:
    method: GET
    url: https://www.softleader.com.tw
  cron: '@every 1m'
  env:
    LOGGING_JSON_ENABLED: "false"

執行以下指令執行此 ApiTrigger 範例:

kubectl create -f /path/to/apitrigger.yaml

輸出類似於:

apitrigger.batch.softleader.com.tw/hello created

ApiTrigger 全名為 apitrigger, 縮寫為 at, 選擇其一並使用下面的指令觀察其事件:

Deleting a ApiTrigger

8 - Auto Scaling

自動擴展

SLKE 支援以 CPU 使用率為觀察基礎的 Pod 自動擴展, 觀察變化量的週期是每 15 秒一次, 使用的是 Kubernetes 的 HorizontalPodAutoscaler (HPA)

HPA 的公式為:

desiredReplicas = ceil[currentReplicas * ( currentMetricValue / desiredMetricValue )]

例如, 當前 replicas 為 2, 當前 CPU 總共使用率 200m, 預期是 100m, 則總共 replicas 會 double 成 4:

4 = ceil[2 * (200m / 100m)]

Before you begin

首先準備測試用的 Image

# Dockerfile
FROM php:5-apache
COPY index.php /var/www/html/index.php
RUN chmod a+rx index.php

# index.php
<?php
  $x = 0.0001;
  for ($i = 0; $i <= 1000000; $i++) {
    $x += sqrt($x);
  }
  echo "OK!";
?>

以上也可以直接使用 harbor.softleader.com.tw/slke-examples/hpa

接著部署 php-apache

apiVersion: apps/v1
kind: Deployment
metadata:
  name: php-apache
spec:
  selector:
    matchLabels:
      run: php-apache
  replicas: 1
  template:
    metadata:
      labels:
        run: php-apache
    spec:
      containers:
      - name: php-apache
        image: harbor.softleader.com.tw/library/hpa-example
        ports:
        - containerPort: 80
        resources:
          limits:
            cpu: 500m
          requests:
            cpu: 200m
---
apiVersion: v1
kind: Service
metadata:
  name: php-apache
  labels:
    run: php-apache
spec:
  ports:
  - port: 80
  selector:
    run: php-apache

Create Horizontal Pod Autoscaler

服務準備就緒後, 就是設定 HPA

apiVersion: autoscaling/v1
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  maxReplicas: 10
  minReplicas: 1
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  targetCPUUtilizationPercentage: 30

Increase load

透過以下指令進行無限迴圈的呼叫

kubectl run -i --tty load-generator --rm --image=busybox --restart=Never -- /bin/sh -c "while sleep 0.01; do wget -q -O- http://php-apache; done"

透過以下指令來觀察 HPA 即產生了幾個 Replicas

kubectl get hpa
kubectl get deployment php-apache

現在你學會了許多撰寫許多 Kubernetes 的設定檔 (YAMLs), 這些設定檔越來越多後, 我們會需要一些工具讓維護這些設定檔們更加的方便.

撰寫第一個 Kustomization

  • deployment.yaml
  • service.yaml
  • ingress.yaml

並在該從目錄中, 建立一個名為 kustomization.yaml 的檔案, 內容為:

namespace: default

- deployment.yaml
- service.yaml
- ingress.yaml

.
├── deployment.yaml
├── ingress.yaml
├── kustomization.yaml

9.2 - Labels and Selectors

理解 Kustomize 如何簡化 Labels 與 Selectors

現在讓我們專注於 deployment.yaml 跟 service.yaml 這兩個設定檔中, 資源跟資源們之間是如何綁定關聯 (本節著重在說明關聯, 非各資源自身的介紹)

當我們部署了 Deployment 跟 Service 之後, Kubernetes 一共會產生以下資源:

                      +----------------+        +---------+         +----------------+
                      |                |  (a)   |         |    (c)  |                |
                      |   ReplicaSet   |-------->   Pod   |<---------    Service     |
                      ^                \        |         |         |                |
                     /+----------------+\       +---------+        /+----------------+
                    /                    \                        /                   
                   /                      \                      /                    
                  /                        \ (b)                / (d)                 
                 /                          \                  /                      
+--------------+/                            \                /                       
|              /                              \ +---------+  /                        
|  Deployment  |                               \|         | v                         
|              \                                v   Pod   |                           
+--------------+\                               |         |                           
                 \                              +---------+                           
                  \                                                                   
                   \                                                                  
                    \+-----------------+                                              
                     |                 |                                              
                     |  ReplicaSet...  |                                              
                     |                 |                                              
                     +-----------------+

上圖中:

  • (a), (b) - 描述了 ReplicaSet 要管理的 Pod 之間的關聯
  • (c), (d) - 描述了 Service 將流量要轉導的 Pod 之間的關聯

在 Kubernetes 架構中就是使用 Labels 及 Selector 來描述上述關聯

Without Kustomize

Labels 及 Selector 的描述在 YAMLs 中都會被定義出來:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  selector:
    matchLabels:
      run: my-nginx
  replicas: 2
  template:
    metadata:
      labels:
        run: my-nginx
    spec:
      containers:
      - name: my-nginx
        image: nginx
        ports:
        - containerPort: 80
  • .spec.selector - 定義 ReplicaSet 如何找到這些要管理的 Pod, 上面範例中定義了 label 符合 run=my-nginx 的 Pod 就會被管理
  • .spec.template.metadata.labels - 定義了 Pod 的 label, 上面範例中定義了 Pod 都會打上 run=my-nginx
apiVersion: v1
kind: Service
metadata:
  name: my-nginx
  labels:
    run: my-nginx
spec:
  ports:
  - port: 80
    protocol: TCP
  selector:
    run: my-nginx
  • .spec.selector - 定義 Service 如何將流量轉導到哪些 Pod, 上面範例中定義了 label 符合 run=my-nginx 的 Pod 就會被轉導

在大部分使用情境中, 你會發現這幾個 selector 跟 labels 一定要配對, 畢竟我們需要的就是 Service 要轉導到 Deployment 所產生的所有的 Pod, 若每個地方都要宣告其實還滿瑣碎的且有出錯的機率, 而這邊也是 Kustomize 可以幫助我們簡化的地方!

With Kustomize

現在我們把 YAMLs 修改一下, 把 selector 跟 labels 有關的都刪除掉:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: my-nginx
        image: nginx
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: my-nginx
spec:
  ports:
  - port: 80
    protocol: TCP

接著在 kustomization.yaml 上做點加工, 增加 commonLabels 區塊:

namespace: default
commonLabels:
  run: my-nginx
resources:
- deployment.yaml
- service.yaml
- ingress.yaml

透過以下指令產生出 YAMLs, 你會發現那些 labels 和 selectors 都被正確無誤的加回來了!

kubectl kustomize .

9.3 - Overlays

組織並制定各環境的分層架構

Kustomize 沒有一個強制性的規定 YAMLs 要怎麼來放, 最簡單且快速的方式就是鋪平就好, 如:

.
├── deployment.yaml
├── ingress.yaml
├── kustomization.yaml
└── service.yaml

但若你的環境複雜需要多組設定時, 這樣鋪平擺放的方式就會開始難以維護, 這時候就應該導入官方推薦 Overlays 的分層式結構

Overlays Structure

在官方的建議中, Overlays 應該區分成:

  • base/ - 此 app 的基礎設定
  • overlays/*/ - 各個環境設定

資料夾結構類似於:

.
├── base
└── overlays
    ├── dev
    ├── uat
    └── ...

假設 my-nginx 這個 app 在不同的環境中, 只有 ingress.yaml 的設定網址不同, 其餘的都是一樣的, 這時候我們可以這樣設計分層:

.
├── base
│   ├── deployment.yaml
│   ├── kustomization.yaml
│   └── service.yaml
└── overlays
    ├── dev
    │   ├── ingress.yaml
    │   └── kustomization.yaml
    └── uat
        ├── ingress.yaml
        └── kustomization.yaml

我們來看一下在 my-nginx 中, 各個環境的 kustomization.yaml 內容:

# base/kustomization.yaml
commonLabels:
  run: my-nginx
resources:
- deployment.yaml
- service.yaml

---
# overlays/dev/kustomization.yaml
namespace: dev
commonLabels:
  env: dev
bases:
- ../../base
resources:
- ingress.yaml

---
# overlays/uat/kustomization.yaml
namespace: uat
commonLabels:
  env: uat
bases:
- ../../base
resources:
- ingress.yaml

這邊我們可以看到, 現在進入點已經是 Overlays, 再從 Overlays 關聯回 base.

使用以下命令來產生 dev 的設定:

kubectl kustomize overlays/uat

What’s next?

會有分層的結構設計, 就是為了在各個環境配置中設定不同的內容, 若都跟 ingress.yaml 一樣抽離 base/ 放到 overlays/*/ 下, 那似乎就失去了分層覆蓋的意義, 下一節將說明在專案常見的組織及制定各分層的設定

9.4 - Customizing

如何客製各分層中的配置

延續上一節的 Kustomize Overlays, 在不同的分層結構中一定有各自的配置, 本節說明常見的範例

Images

不同的 Overlays 中基本上 Image 都不盡相同, 這是定義在 Deployment 中的, 為了不要因此把 Deployment 又放到 overlays 下, 這時候我們可以使用 Kustomize 提供了 images 替換功能:

首先先記下 base/deployment.yaml 中的 image:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
spec:
...
    spec:
      containers:
      - image: nginx # <- 記下這個名稱
...

接著在每個 overlays/*/kustomization.yaml 中都加上

# overlays/dev/kustomization.yaml
namespace: dev
commonLabels:
  env: dev
bases:
- ../../base
resources:
- ingress.yaml
images:
- name: nginx
  newTag: 1.23-alpine

---
# overlays/uat/kustomization.yaml
namespace: uat
commonLabels:
  env: uat
bases:
- ../../base
resources:
- ingress.yaml
images:
- name: nginx
  newName: nginxinc/nginx-unprivileged
  newTag: 1.23-alpine

使用以下命令來產生 uat 的設定:

kubectl kustomize overlays/uat

10 - Logging

集中管理日誌

SLKE 使用 Fluentd 收集 log, 任何跑在 SLKE 的 container log 都可以在公司的 Kibana 上查到: https://kibana-elastic.cloud.softleader.com.tw

Fluentd 會將收集到的 log 依照下述 index pattern 推到 Elasticsearch 中:

slke-{{ namespace }}-%Y.%m.%d

你可以自由的建立 Kibana index 去關聯你感興趣的 Elasticsearch index

JSON Logging Format

SLKE 的 Fluentd 會將你的 stdout 訊息的每一行, 都視為純文字, 以 log 欄位收集到 Elasticsearch 中, 也就是在 Kibana 上都是針對一段文字去操作, 例如要查 traceId 或是 log_level 都是針對 log 欄位的內容去下 contains 一段字串.

而 SLKE 也同時支援處理 JSON format, 每一行的 log 欄位會嘗試以 Fluentd 的 JSON Parser 作轉換, 並以 parsed 欄位收集到 Elasticsearch 中, parsed 就是一個 JSON 物件包含了你的 stdout 欄位, 而不在是一段純文字.

使用 JSON format 的好處是你可以依照各個專案的需求定義不同的 stdout 結構輸出, 並以JSON 格式被收集到 Elasticsearch 中, 如此你就可以針對特定欄位來過濾增加查詢效率, 如 stdout 中的 log_level 就可以透過 parsed.log_level=debug 的條件來過濾, 有了結構性的 stdout 後甚至還可以加以統計並畫出各式圖表!

Applying JSON Format

若你想要以結構性的形式被處理 stdout, 請依照你的專案類型, 參考以下連結試著將你的 stdout 轉成 JSON 格式的輸出!

Framework Reference
Spring Framework / Spring Boot 目前沒有官方的套件, 但可以參考 softleader-training-course/fluent-bit 文章來配置
SoftLeader Platform v2 / ROSE 同上
Kapok 透過設定即可轉換
Quarkus 使用官方套件 quarkus-logging-json, 或社群的 quarkiverse/quarkus-logging-json 套件
Nginx 啟動 ngx_http_log_module, 並調整 log_format=json

11 - Export Metrics

提供監控指標

說到監控, 一切都是由數據 (metrics) 開始, 而 metrics 則是由 exporter 提供, 有了 metrics 以後才有辦法再進一步的去繪製監控圖表, metrics/exporters 大致上可以區分成兩類:

Platform

這類的 exporters 滿多都已經在建置 SLKE 時就規劃了, 如 node-exporter, kube-state-exporter 等, 如果你還有任何需求也歡迎反映給 R&D

Application

在開發 App 時就必歸規劃提供的 metics API, 如 JVM 資訊等, 這邊推薦 micrometer.io 套件, 該套件可以讓 App 本身也當作 exporter 來暴露 metrics

如果是使用 Spring Boot / ROSE Framework 基本上 Actuator 就整合了 micrometer, 只要專案放入了 micrometer-registry-prometheus 依賴, 再開啟 prometheus endpoint 即完成設定

<!-- pom.xml -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>

# application.properties
management.endpoints.web.exposure.include=* # 開啟所有 endpoints 的範例

# API 預設在 `GET /actuator/prometheus`

如果使用的是 Kapok Framework, 那麼就更簡單了你什麼都不需要調整, 在底層都已經幫你設定好了

當 App 有了 metrics API 並部署到了 SLKE 之後, 有可能被開啟多個 replicas, 甚至設計 auto scaling 被動態的開啟更多 replicas, 在這些情境中要提前知道並監控所有的 Pod 是有難度的

SLKE 監控機制是使用 Prometheus, 因此我們需要一個方式來告訴 SLKE Prometheus, 該如何主動發現所有的 Pod 並打到每一個你所設計的 metrics API 上收集 metrics

ServiceMonitor

SLKE 支援了 ServiceMonitor, 透過 ServiceMonitor 可以讓 SLKE 的 Prometheus 發現所有關聯到的 Service 及其背後的 Endpoints, 並持續到這些 Endpoints 上收集資訊

Try it out

我們使用到的範例是 harbor.softleader.com.tw/slke-examples/actuator-prometheus, 其中包含了一個 Spring Boot App 及開啟了 actuator prometheus endpoint, 首先我們部署到 SLKE 中並開啟 2 個 replicas

kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  selector:
    matchLabels:
      run: my-app
  replicas: 2
  template:
    metadata:
      labels:
        run: my-app
    spec:
      containers:
      - name: my-app
        image: harbor.softleader.com.tw/slke-examples/actuator-prometheus
        ports:
        - containerPort: 8080
EOF

我們可以測試一下 metrics api

kubectl get pod -l run=my-app
kubectl port-forward {{ one-of-pod-id }} 8080:8080

開啟 port-forward 後, 你就可以從你的電腦打 localhost:8080/actuator/prometheus, 看到一推 metrics 這代表著 app 已經正常的運作了! 接著我們部署 Service 及 ServiceMinitor

kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: my-app
  labels:
    run: my-app
spec:
  ports:
  - name: http
    port: 8080
    protocol: TCP
  selector:
    run: my-app
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-app
  labels:
    release: prometheus # 必要且不可更改
    run: my-app
spec:
  endpoints:
  - path: /actuator/prometheus
    port: http
    interval: 15s
  selector:
    matchLabels:
      run: my-app
EOF

這樣就完成了所有設定, 接著請繼續往下一節: 我們到 SLKE Prometheus 中檢查是否成功

Remove Demo

請執行以下指令移除範例:

kubectl delete deploy,svc,servicemonitor my-app

SLKE Prometheus

Note

SLKE Prometheus 在 http://192.168.1.241:9090, 只開放公司內網連線

進到 SLKE Prometheus 後點選 Status > Servivce Discovery, 該頁會顯示所有被 SLKE Prometheus 所監控的 Service Monitor, 你自定義的 Service Monitor 會依照以下 Pattern 被列出

{{ namespace }}/{{ service-monitor-name }}/0

在前一節的範例中, 在部署後等個幾分鐘後, 你應該可以找到 {{ namespace }}/my-app/0, 接著透過以下步驟來確認 2 個 replicas 都有被收集到資訊:

kubectl get endpoints my-app

NAME     ENDPOINTS                               AGE
my-app   10.244.21.92:8080,10.244.52.135:8080    8m22s

透過 endpoints 資訊我們發現了 my-app service 背後的一共有兩個 IP 10.244.21.92 及 10.244.52.135, 這也分別是 2 個 replcias pod 的 IP

kubectl get pods -l run=my-app \
    -o go-template='{{range .items}}{{.status.podIP}}{{"\n"}}{{end}}'

10.244.21.92
10.244.52.135

這時我們再回到 Prometheus 的 Servivce Discovery, 點開 {{ namespace }}/my-app/0 旁邊的 show more

在 show more 清單中, 我們可以確認到 __address__ 包含到了 10.244.21.92 及 10.244.52.135 兩個 IP

最後我們再回到 Graph 頁籤, 試著收尋一下從 port-forward 中看到的任一 metric, 如 system_load_average_1m

以上代表著部署在 SLKE 中個兩個 replicas, 都自動的被 Prometheus 發現且持續的收集 metrics 了!

Tips

由於 Prometheus 在監控到 ServiceMonitor 的創建或移除時, 基本上是需要重啟 Prometheus 本身服務去載入新的配置, 這個載入的過程是比較耗時的且耗資源的, 因此 ServiceMonitor 最好不要隨著開發的 App 經常的去部署或移除!

建議可以在一個專案中, 讓同一種 endpoint 集中在一個 ServiceMonitor 就好, 我們可以設計一個 label, 如 exporter={{ type }}

# servicemonitor.yaml
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: actuator-service-monitor
  labels:
    release: prometheus # 必要且不可更改
spec:
  selector:
    matchLabels:
      exporter: actuator # 這邊定義只去收集 actuator exporter 類型的 Service
  endpoints:
  - path: /actuator/prometheus
  ...
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: quarkus-service-monitor
  labels:
    release: prometheus # 必要且不可更改
spec:
  selector:
    matchLabels:
      exporter: quarkus # 這邊定義只去收集 quarkus exporter 類型的 Service
  endpoints:
  - path: /metrics
  ...

接著我們只需要在需要被監控的 Service 打上對應的 label 就好

# service.yaml
---
apiVersion: v1
kind: Service
metadata:
  name: my-spring-service
  labels:
    exporter: actuator
    ...
spec:
  ...
---
apiVersion: v1
kind: Service
metadata:
  name: my-quarkus-service
  labels:
    exporter: quarkus
    ...
spec:
  ...
---
apiVersion: v1
kind: Service
metadata:
  name: dont-collect-metrics
  labels:
    ...
spec:
  ...

Example of SpringBoot Application

首建置一個 Spring 專案, 下載後解開匯入你的 IDE, 接著開啟 pom.xml, 加入相關的依賴:

<!-- 這個是 demo 用的 -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- opentracing -->
<dependency>
  <groupId>io.opentracing.contrib</groupId>
  <artifactId>opentracing-spring-jaeger-cloud-starter</artifactId>
  <version>3.3.1</version>
</dependency>

上述版本請勿直接照抄, 建議到 opentracing-contrib/java-spring-jaeger 找最新的版本

接著我們加一些程式 for demo 用:

@RestController
public class DemoController {

  @GetMapping
  public String getTraceId() {
    if (!GlobalTracer.isRegistered()) {
      return "tracer not registered!";
    }
    return GlobalTracer.get().activeSpan().context().toTraceId();
  }
}

# application.properties

spring.application.name=tracing-demo
opentracing.jaeger.enable-b3-propagation=true

完成後, 如果你的 SpringBoot 是 2.4+, 直接執行以下命令打包成 image:

mvn spring-boot:build-image -Dspring-boot.build-image.imageName=harbor.softleader.com.tw/demo/tracing

若小於 2.4 的 SpringBoot, 請用 Jib 打包吧
